# Agent Bundles & Installs

## Purpose

Replace the clone-based sharing model with a desktop-app-style **bundle / install** system. An agent developer packages their agent as a versioned, publisher-owned **bundle** identified by a stable reverse-DNS string. Other users **install** the bundle, each receiving their own running copy. A separate per-user **App Data** area survives uninstall and reattaches on reinstall, so publishers can ship updates without ever overwriting user state.

## Core Concepts

- **Bundle** (`AgentBundle`) — canonical metadata record owned by a publisher. Uniquely identified by a reverse-DNS `bundle_id` (e.g. `io.opencinna.cinna.a1b2c3d4`). One bundle per published agent on this instance
- **Bundle Revision** (`AgentBundleRevision`) — immutable snapshot of a bundle's content taken at publish time. Contains workspace folder copies, prompts, SDK selection, `required_credential_specs`, agent schedules, and an optional human-friendly `version` label entered by the publisher. Revisions are append-only; the latest is pointed to by `AgentBundle.latest_revision_id`
- **Install** — every `Agent` row is an install in the new model. The publisher's working copy (`is_publisher_install=True`) and every foreign user's copy are all `Agent` rows, distinguished by `is_publisher_install` and `bundle_uuid`
- **Publisher Install** — the `Agent` row owned by the bundle publisher. This is the source of truth for the next publish snapshot. The publisher develops the agent here as normal; clicking "Publish" snapshots its current workspace state
- **App Data** — a per-user, per-bundle persistent volume mounted at `/app/workspace/app-data` inside the container. Keyed by `(user_id, bundle_id, catalog_type)`. Survives uninstall; reattaches on reinstall. See [Agent App Data](../agent_app_data/agent_app_data.md)
- **Bundle ID** — reverse-DNS string, auto-generated on agent creation. Format: `<reversed-host>.<8-hex-chars-of-agent-uuid>` (e.g. `io.opencinna.cinna.a1b2c3d4`). The publisher can override the auto-generated value inside the **first** publish dialog (it's the moment the bundle is defined); after the first revision is recorded, the bundle ID is locked
- **Version label** — optional, user-supplied string captured per revision (e.g. `1.0`, `1.1`, `2.0`). Independent from the internal monotonic `revision_number` — `revision_number` continues to drive snapshot paths and ordering. The publish dialog defaults the field to `1.0` on the first publish and suggests a minor bump from the previous revision afterwards
- **Visibility** — controls catalog access: `private` (publisher only), `users` (explicit allowlist via `BundleAccessGrant`), `public` (all users on this instance)
- **Update Mode** — per-install setting controlling how revisions are applied: `manual` (user applies explicitly) or `automatic` (applied by the suspension scheduler while the environment is idle)
- **Provided-by-publisher (PBP), Provided-by-user (PBU), and Provided-by-template (PBT)** — per-spec metadata recorded on each `AgentBundleRevision.required_credential_specs` entry as `provided_by` ∈ `{"publisher", "user", "template"}`. 
  - **PBP** — the publisher intends to share their own live `Credential` row with every installer. At install time `InstallService` validates that the publisher's row exists, still has `allow_sharing=True`, and is owned by the bundle publisher, then materialises a `CredentialShare` (publisher → installer) and links the credential to the install via `AgentCredentialLink`.
  - **PBU** — each installer is expected to bring their own credential, or accept a placeholder that can be filled in later.
  - **PBT** — the publisher ships non-private credential fields as defaults. At install time `InstallService._materialise_template_credential` creates a fresh `Credential` row owned by the installer, seeded with `template_data` (the non-private values from the publisher's credential at publish time). The row is marked `is_placeholder=True` and carries `template_private_fields` (the list of field names the installer must fill in). The runtime gate keeps the install in `needs_setup` until all required fields pass the per-type completeness check.
  
  The revision spec for a PBT entry looks like:
  ```json
  {
    "name": "Odoo",
    "type": "odoo",
    "provided_by": "template",
    "template_data": {"url": "https://myodoo.example.com", "database_name": "prod"},
    "template_private_fields": ["login", "api_token"]
  }
  ```
  The private fields are **never** stored in the revision JSON; `PublishService._template_payload_for` strips them before writing `template_data` to the manifest.

  When using the `service_uri` pattern (see below), the spec also carries a `service_uri` field:
  ```json
  {
    "name": "Company Scope Token",
    "type": "api_token",
    "provided_by": "user",
    "service_uri": "agent-b://company-scope-token"
  }
  ```
  The `service_uri` steers the auto-prefill matcher to the correct per-user credential regardless of credential name differences.

  For all three modes, if a PBP credential is unavailable at install time the install still activates — a placeholder is created instead and `last_update_status="degraded"` is recorded. The runtime gate (see below) surfaces degraded and incomplete installs the first time the user tries to use the agent. The publisher can explicitly override the `provided_by` assignment for each linked credential from the **Credential provisioning** panel on the bundle tab — this override is persisted as `Agent.publish_settings.credential_overrides[<spec_name>].provided_by` and is consulted by `PublishService._collect_credential_specs` before falling back to flag-based inference. Resolution order: (1) override if present; (2) `allow_sharing=True` → `"publisher"`; (3) `allow_template_sharing=True` → `"template"`; (4) `"user"`. The security invariants are enforced by `PublishService._validate_publisher_provides` at publish time: an override to `"publisher"` fails if `allow_sharing=False`; an override to `"template"` fails if `allow_template_sharing=False`
- **Publisher-provided AI credentials** — two optional FK columns on `AgentBundle` (`publisher_ai_credential_conversation_id`, `publisher_ai_credential_building_id`) record which of the publisher's `AICredential` rows to use for conversation and building modes respectively. At install time `InstallService` materialises an `AICredentialShare` (publisher → installer) for each non-null FK, then passes the publisher's credential id directly into `AgentEnvironmentCreate` — bypassing the installer's own AI credential selection for that mode. The `AICredentialShare` is also re-asserted on every idempotent re-install so a previously deleted share is automatically self-healed. When the installer IS the publisher, no share-with-self row is created
- **Runtime gate** — `InstallReadinessGate` runs synchronously on every user-message-to-LLM dispatch (chat, MCP, A2A, webhook session trigger) before any LLM call is made. It inspects the install's credential link state and returns one of three statuses:
  - `ready` — all credentials are in order; the message is forwarded to the LLM.
  - `needs_setup` — one or more user-provided credentials are still placeholders (the installer hasn't filled them in yet). A setup-needed reply is synthesised without engaging the LLM. Lead copy: "Setup needed before this agent can run. Open the agent's Credentials tab and fill in the missing values one by one."
  - `publisher_broken` — one or more publisher-provided credentials are missing or have had sharing revoked. The synthesised reply instructs the installer to contact the publisher. Lead copy: "This bundle's publisher-provided credentials are unavailable. The publisher needs to fix this, or you can supply your own credentials from the agent's Credentials tab."
  
  Each channel renders the gate result in its native idiom: chat persists a `system`-role message with `install_setup_required=true` metadata and the Cinna chat UI renders it as a distinct warning block with a link to the Credentials tab (not derived from the message body); MCP returns a structured tool reply `{response, context_id, setup_url}`; A2A synthesises a completed Task with the message and a `data` part carrying `{type: "cinna.setup_required", setup_url, missing}`; webhook session triggers log `status="setup_required"` with the structured payload in the invocation log. The LLM is never engaged when the gate blocks. When the user fills in the last placeholder, `INSTALL_SETUP_COMPLETED` fires over WebSocket and the banner on the install detail page clears automatically.

  The `setup_url` field (returned in all structured channel payloads — MCP, A2A, webhook) now points at the agent detail page's Credentials tab: `{FRONTEND_HOST}/agent/{install_id}#credentials`. External MCP/A2A/webhook clients receive this URL in the structured payload; the Cinna chat UI renders its own inline link independently.

  Incomplete credentials are fixed directly from the agent's **Credentials tab** (`/agent/{id}#credentials`), where each placeholder or incomplete row is highlighted with a "Setup needed" badge. The user navigates to the credential detail page (`/credential/$credentialId`) to fill in the missing values one at a time. There is no dedicated setup-credentials page in the web UI (the backend endpoints remain for cinna CLI use).

## User Stories / Flows

### Publishing a Bundle (agent-developer)

1. Developer opens an agent they own and navigates to the **Bundle tab**
2. Before publishing, the **Credential provisioning** panel (visible only on the publisher install) lets the publisher choose, per linked credential, whether it will be user-provided, publisher-provided, or template-provided. Template mode additionally requires the publisher to mark which `credential_data` fields are private (the remainder become the pre-filled template data for each installer). A toggle also controls whether the publisher provides AI credentials (conversation and/or building mode). These choices are saved immediately and consulted at the next publish step
3. Clicks "Publish" — the `PublishDialog` opens with three fields (four on the first publish):
   - **Bundle ID** — only on the first publish; prefilled with the auto-generated value, editable. Locked once the first revision exists
   - **Publish in Public Catalog** — switch shown only on the first publish, directly below the Bundle ID. Defaults to off. When on, the bundle is made public and listed in the catalog immediately after the revision is recorded (visibility → `public`, `is_listed` → `true`). The publisher can always change either of these later in Bundle settings
   - **Version** — required; defaults to `1.0` on the first publish, otherwise suggests a minor bump from the previous revision (e.g. `1.0` → `1.1`). Manually editable for major releases
   - **Release notes** (optional)
4. On submit: the entire `app/workspace/` tree (except per-user/runtime/secret paths — `app-data/`, `credentials/`, `logs/`, `databases/`, `uploads/`, the `__init__.py` package marker, and the plugins-root derived files `settings.json`/`manifest.json`) is captured under the snapshot's `workspace/` subtree (schema_version 2; legacy v1 allowlist snapshots remain readable). Symlinks anywhere in the workspace are never followed or copied. The publisher's agent schedules are snapshotted into the revision; a new `AgentBundleRevision` row is created with the user-entered `version`; `BUNDLE_PUBLISHED` WebSocket event fires. If "Publish in Public Catalog" was on (first publish only), the frontend chains a `PATCH /bundles/{uuid}` setting `visibility="public"` and `is_listed=true` immediately after the publish response. The chained call is best-effort — a failure surfaces an error toast pointing to Bundle settings but does not roll back the publish
5. On first publish the `AgentBundle` row is also created; the `bundle_id` value submitted in the publish form is applied to the agent before the snapshot. Subsequent publishes append a new revision
6. All existing foreign installs receive `INSTALL_UPDATE_AVAILABLE` events (manual mode) or are marked for next-idle-cycle update (automatic mode)
7. The revision appears in the revisions list on the Bundle tab with a "current" badge — labeled `v<version>` when present, falling back to `rev <revision_number>` for legacy revisions. Only catalog publishes appear in this list; internal git baseline revisions (created automatically when git operations such as push, connect, checkout, and pull run) carry `origin="git"` and are filtered out server-side

### Installing a Bundle (any user)

1. User opens the **Catalog** page; sees all public bundles and any bundles explicitly granted to them. The catalog's `is_installed` flag reflects only consumer installs (`is_publisher_install=False`) — publishers see their own bundles with "Quick Install" / "Install Page" buttons until they perform an actual consumer install of their own bundle
2. Two entry points on each catalog card:
   - **Click the card body** — opens the full **Install Page** for custom setup (described below)
   - **Click the "Quick Install" button** in the card footer — skips the Install Page entirely and submits the install with the same defaults the form would use unchanged (PBP → `publisher_provides`, auto-prefill suggestion → `use_existing`, otherwise → `skip`; publisher AI credentials are accepted when offered). The button shows an inline spinner while pending and is disabled to prevent double-submit. Card body clicks are no-op while a Quick Install is in flight. On completion, the same post-install redirect logic applies (gate `ready` → dashboard with `?selectAgentId`; otherwise → Credentials tab)
3. The **Install Page** opens — a single screen with two columns:

After a successful install, the platform automatically creates an **App MCP route** for the installer so the agent is reachable from Claude Desktop or any other MCP client immediately (see [App MCP Server](../../application/app_mcp_server/app_mcp_server.md)). If the installed revision has no `router_trigger_prompt`, the route is skipped and the install is marked `last_update_status="degraded"`. The installer can set or regenerate the trigger prompt from the Configuration tab's **Agent Prompts** card, after which applying an update creates the route retroactively.

After the route is created, a non-blocking **conflict toast** may appear on the install page if the new route's trigger prompt closely matches an existing route the installer already has. This helps the user spot near-duplicate intents that could confuse the App MCP router.
   - **Left (sticky)**: agent header card showing the bundle icon, display name, version, publisher, description, required credentials summary, and Bundle ID
   - **Right (scrollable)**: a setup form with a service credentials section first (each spec rendered as an accordion item leading with the credential type pill and a secondary name caption, mirroring the publisher's "Credential provisioning" panel) followed by an AI credentials section. Conversation and Building selectors (and the publisher-provided summary variant) use the same icon-block row pattern as Settings → AI Credentials → Default SDK Preferences (blue `MessageCircle` tile for Conversation, orange `Wrench` tile for Building)
   - For PBP specs the accordion item is collapsed by default and shows "Shared by publisher — no action needed"
   - For PBT specs the accordion item lists the field names the installer must supply after install (from `template_private_fields`); the non-private values are already arranged. The installer can accept the template materialisation or choose "use existing" to link their own complete credential instead
   - For PBU specs the system runs the **auto-prefill matcher**. The matcher tries tiers in order, returning on the first hit: **(Tier 0a) `service_uri` — owned**: if the spec carries a `service_uri`, the matcher first looks for an owned credential with the same `service_uri` and type (most recent by id). **(Tier 0b) `service_uri` — shared**: same lookup through `CredentialShare`. Tiers 0a and 0b short-circuit the remaining tiers — they win even over the PBT value-anchor check. When no `service_uri` is set on the spec, these tiers are skipped and the remaining tiers run as before. **(Tier 1) Name + type**: case-insensitive `(name, type)` match across owned credentials. **(Tier 2) Shared name + type**: same match through `CredentialShare`. **(Tier 3) Type-only fallback** (PBU only): if the installer owns exactly one credential of the right type (any name), that row is used as a suggestion; two or more type matches return no suggestion so the user disambiguates via the dropdown. For PBT specs the matcher also requires **exact value matching**: after finding name+type candidates it decrypts each candidate's `credential_data`, strips the fields listed in `template_private_fields`, and requires the remaining values to equal `template_data` exactly (also stripped of private fields). Only the first candidate that passes this value comparison is surfaced as a suggestion. The type-only fallback (one credential of the right type) is **not available** for PBT specs — a name+type match that does not also pass the value check yields no suggestion. This means a credential pointing at a different server, database, or URL than the spec's `template_data` is never auto-linked; Quick Install falls through to `mode: "skip"` for that spec, the install activates in `needs_setup`, and the runtime gate guides the user to fill in the correct credential from the Credentials tab. (For OAuth-style PBT specs where all fields are private, `template_data` is effectively empty; any candidate whose non-private slice is also empty matches.) When a suggestion is surfaced, the item shows "Use my `<name>` (auto-detected)" with options to accept, fall back to the spec's default path (placeholder for PBU, template materialisation for PBT), or pick another from a type-filtered dropdown. Accepted suggestions are sent as `mode="use_existing"` with the matched credential's UUID. This means: uninstalling a bundle whose PBT credential the installer already filled in, then reinstalling, reuses the existing row instead of materialising a duplicate
   - When all specs are PBP and AI is publisher-provided, the form shows three short informational paragraphs and Install is one click
   - A single primary **Install** button at the bottom of the form; no "Next / Back" steps and no step indicator
4. On submit: a new `Agent` row is created seeded from the latest revision; `CredentialShare` rows are automatically created for any PBP service credentials in the revision and `AICredentialShare` rows are created for any publisher-provided AI credentials; PBT specs materialise a fresh installer-owned `Credential` row seeded with the publisher's non-private template data (`is_placeholder=True`); an environment is provisioned and started using the resolved credentials; the App Data volume for `(user, bundle_id, "server")` is created (or reattached if previously orphaned); the revision's snapshotted schedules are materialised as `AgentSchedule` rows on the install (best-effort — failure marks the install degraded but does not abort). Install never blocks on incomplete credentials — PBU specs for which the installer skipped or deferred, and PBT specs awaiting private-field input, both create placeholder `Credential` rows that the runtime gate detects at first use
5. Loading state with environment progress display; on activation the install page checks the runtime gate via `GET /agents/{id}/setup-status` and branches:
   - **Gate ready** — the install needs no further configuration. The user is sent to the **dashboard** (`/`) with the new agent's pill auto-selected via a one-shot `?selectAgentId=<install_id>` search param, and a toast confirms "*<agent name>* installed — you can chat with it now." The dashboard route consumes the param, applies the selection in conversation mode, then strips the param from the URL.
   - **Otherwise (`needs_setup` / `publisher_broken` / status call errored)** — the user is redirected to the **Credentials tab** of the install detail page (`/agent/$agentId#credentials`), where the `SetupNeededBanner` and per-row "Setup needed" badges guide them through the missing fields.

### Applying an Update (install owner)

Updates can be applied from three surfaces:

- **Install detail page** — the `UpdateAvailableBanner` appears when `INSTALL_UPDATE_AVAILABLE` arrives over WebSocket. The banner shows the from→to version labels (e.g. `v1.0 → v1.1`, falling back to revision numbers when labels are absent). The apply button reads "Update to v\<latest\>" (or "Apply update" when the latest revision has no version label). Clicking it confirms and applies the update.
- **Catalog card** — when the viewer has a consumer install that is behind the latest revision, the card footer shows an amber "Update to v\<latest_version\>" button in place of "Open". Clicking it applies the update in-place (inline spinner → success toast → card reverts to "Open").
- **Agent list card** — an amber footer strip at the bottom of the agent card indicates a pending update. Clicking the strip applies the update in-place (spinner → success toast → strip disappears once `pending_update` clears).

In all cases the same `POST /agents/{id}/apply-update` endpoint is called:
- If automatic mode: the suspension scheduler applies the update the next time the environment goes idle (the manual-surface buttons are not shown for automatic-mode installs)
- If manual mode: environment stops, bundle folders replaced from the new revision snapshot, environment restarts; app-data and credentials are preserved

`INSTALL_UPDATE_APPLIED` event fires; banners and strips clear; `installed_revision_id` advances.

During apply-update, `Agent.router_trigger_prompt` is refreshed from the new revision's snapshot. The install's **auto-managed App MCP route** (`AppAgentRoute.is_auto_managed=True`) also has its `trigger_prompt` and `name` refreshed. **Routes where `is_auto_managed=False` are left untouched** — manual edits via the PUT endpoint flip that flag and the user's custom value is preserved forever after.

Schedules are also merged against the new revision using a behavioral signature. Behaviorally-unchanged schedules retain the user's enable/disable preference and execution history; changed, added, or removed schedules are synced from the publisher (see [Agent Schedulers](../agent_schedulers/agent_schedulers.md)).

### Uninstalling (install owner)

1. User opens the header kebab menu on the install detail page and clicks **Uninstall** (available for any foreign install — `bundle_uuid` set and `is_publisher_install=False` — regardless of the user's role)
2. Confirmation dialog explains: the install and its environment are removed; per-bundle App Data is preserved and reattaches automatically on reinstall
3. Environment stopped and removed (bundle workspace volume removed; app-data volume preserved)
4. `Agent` row deleted; `AppDataVolume.is_orphaned` set to `true`
5. App data remains visible in Settings → App Data as an orphaned entry

Publisher installs cannot be uninstalled via this flow — the backend returns 400. The publisher manages their install via the Bundle settings (delete agent / delete bundle).

### Reinstalling the Same Bundle

The install wizard is re-entered; when `InstallService` calls `AppDataService.get_or_create_volume`, it finds the orphaned row, clears `is_orphaned`, and reattaches it — preserving all previous user data.

### Managing Visibility and Grants (publisher)

1. Publisher opens Bundle tab → sets visibility to `users`
2. The Bundle settings card shows a hint pointing at the **Permissions management** card below for managing who can see the bundle; the allowlist itself is no longer edited inline on the settings card
3. In the **Permissions management** card (see below), publisher clicks "Add user", picks a user, and checks "Bundle access"
4. The `BundleAccessGrant` row is created; the target user now sees the bundle in the catalog
5. Publisher can revoke individual grants from the same card; revoking all grants leaves the bundle in `users` visibility but invisible to everyone except the publisher

### Managing Permissions Across Bundle Access and Producer Scopes (publisher)

A bundle that ships a connection to another agent's [Agent REST API](../agent_api/agent_api.md) (the "two-credential bundle pattern") forces a publisher to manage access in two independent places: who can see/install the bundle, and which scopes each installer holds on the producer agent's API. The **Permissions management** card on the Bundle tab unifies both into one table and one "Add user" modal, so the publisher does not have to remember to also visit the producer agent's own page.

- **Where it lives** — rendered on the **publisher's working install** only (`is_publisher_install=True`, developer-gated), directly below the Credential provisioning section. It subsumes the bundle's former inline Grants picker (the `UserAllowlistPicker` previously shown when `visibility === "users"`) — that picker no longer appears on the Bundle settings card.
- **When it shows** — the card renders only when `bundle.visibility === "users"` (bundle-level allowlist is active) **or** the install consumes at least one `agent_api` connection credential whose producer agent has `agent_api_identity_enabled` turned on. If neither condition holds, the card is absent entirely.
- **What it shows** — one row per relevant user, with:
  - A **Bundle access** column (present only when `visibility === "users"`) showing a granted/not chip, revocable independently.
  - One column per connected, identity-enabled **producer** the install consumes via an `agent_api` credential. For producers the publisher owns (or when the publisher is a superuser), the column is editable: scope chips per user, click-to-edit, independent removal. For producers owned by someone else, the column is **read-only** — labeled "Managed by `<owner email>`" — because that owner's grants are never readable through this surface; the publisher manages their own producer's scopes here, but a connected third-party producer's scopes remain that producer owner's exclusive business.
- **Degradation modes** — when only bundle access applies (no identity-enabled producers connected), the card behaves like the old inline picker with a single column. When only producer scopes apply (bundle is `private` or `public`, not `users`), the Bundle access column is omitted and only producer scope columns render.
- **Add user flow** — a single modal lets the publisher pick one user, optionally grant bundle access, and assign scopes per manageable producer in one step. Submission fans out sequentially to the existing, already owner-gated mutation endpoints (bundle grants, producer scope grants) and reports success/failure per section — a failure on one producer's scope assignment does not roll back a successful bundle-access grant or another producer's scopes.
- **Removal is independent per section** — removing a user's bundle access does not touch their producer scopes, and vice versa; there is no single "remove entirely" action, by design (avoids accidental over-revocation across two unrelated authority domains).
- **Relationship to the producer's own management page** — the producer agent's own **Integrations → Agent REST API → Access & Scopes** card (see [Agent REST API](../agent_api/agent_api.md#caller-identity--producer-scopes)) remains unchanged and fully functional; the unified card is additive convenience for a publisher who already owns that producer, not a replacement for producer-side management.

### Deleting a Revision (publisher)

1. Publisher opens the Bundle tab; each row in the Revisions list shows a delete button and an install count. The count **excludes the publisher's own working install** (`is_publisher_install=True`) — that copy is the source of the revision, not an install of it. The delete button is disabled and shows a tooltip ("Cannot delete — N installs reference it") whenever the displayed count is greater than zero (i.e. any consumer install is still on that revision)
2. Clicking it opens a confirmation dialog explaining what happens (snapshot tree removed, `bundle.latest_revision_id` rewired to the previous revision when needed, publisher install detached)
3. On confirm: the `AgentBundleRevision` row is deleted, the on-disk snapshot tree at `<BUNDLE_STORAGE_DIR>/<bundle_id>/<revision_number>/` is removed best-effort, any publisher install pointing at the revision has its `installed_revision_id` cleared, and — if the deleted revision was the bundle's current revision — `latest_revision_id` is moved to the most-recent remaining revision (or `NULL` when none remain)
4. **When the last revision is removed, the bundle row is auto-deleted** — grants are cascaded, and the publisher install's `bundle_uuid` is cleared by the FK `ON DELETE SET NULL`. The agent reverts to "unpublished" (Bundle ID becomes editable again, catalog settings are gone, the next publish creates a fresh `AgentBundle`)
5. Foreign installs are never affected because the API refuses the call while any are still on the revision

### Deleting a Bundle

The API rejects deletion when any foreign install (non-publisher) references the bundle (409). The publisher must have those users uninstall first. On successful deletion, all `AgentBundleRevision` rows and `BundleAccessGrant` rows are cascade-deleted; the publisher's `Agent` row has `bundle_uuid` set to `NULL` by the FK `ON DELETE SET NULL`.

## Business Rules

- **Bundle ID is set inside the first publish dialog and immutable afterwards** — there is no separate edit modal; the publisher enters the final ID alongside the version label and release notes when publishing the very first revision. Changing it post-publish would silently orphan installed app-data volumes on all foreign installs (app-data keyed on the string `bundle_id`, not the `AgentBundle` UUID), so the API rejects post-publish overrides with 409
- **`AgentBundle.display_name` and `description` refresh from the publisher install on every publish** — `bundle.display_name = display_name or install.name` and `bundle.description = description if description is not None else install.description` are written in step 5 of every publish, not just the first. `display_name` is the source for the catalog entry name (`CatalogService._bundle_to_entry`) and the seeded `Agent.name` of any **new** consumer install (`InstallService` uses `name=bundle.display_name`). This means a publisher who renames their agent and republishes sees the new name in the catalog and on subsequent installs starting with that publish. **Existing foreign installs keep their own `Agent.name` across apply-update** — the revision snapshot deliberately does not carry `name`, and `_apply_revision_metadata` never touches it — so a rename never silently renames an installer's already-installed copy
- **Publisher install cannot be uninstalled** — use the bundle management UI (delete agent + delete bundle) instead
- **One publisher install per bundle** — enforced by partial unique index on `bundle_uuid WHERE is_publisher_install = true`
- **One consumer install per user per bundle** — `install_bundle` is idempotent for consumer installs (`is_publisher_install=False`); returns the existing consumer install if already present. The publisher's own working copy (`is_publisher_install=True`) lives in a separate slot — a publisher can therefore install their own bundle as a consumer, receiving a fully independent copy with its own App Data volume
- **Publish requires agent-developer role** and ownership of the install
- **Workspace separation on update** — `replace_bundle_content` uses the denylist model: it overwrites every bundle-owned top-level path in the new snapshot **and** removes any top-level path that existed in the install workspace and was bundle-owned (not in `BUNDLE_EXCLUDED_TOPLEVEL`, not runtime-denylisted, not `plugins/`) but is absent from the new revision snapshot. `app-data/`, `credentials/`, `logs/`, `databases/`, and `uploads/` are never touched. `plugins/` is merged (never delete-swept) to preserve the consumer's own marketplace plugins. Schedules are merged separately via behavioral signature (not blindly replaced). This prune rule applies only to v2 snapshots (schema_version 2); v1 legacy snapshots retain the old overwrite-only behaviour.
- **Empty workspace publish is allowed** — if the publisher's environment exists but its workspace contains no bundle-owned content, the revision is created with an empty `workspace/` subtree; the UI shows a warning. However, if the publisher has an active environment but its `app/workspace/` directory is missing or unreadable on disk, publish fails with a 400 error naming the environment and path. This fail-loud rule prevents silently shipping empty bundles due to workspace materialisation failures.
- **`uploads/` is per-install runtime data, not bundle content** — files placed in `uploads/` by the agent at runtime are preserved across apply-updates (they are in the denylist) and are copied during environment switch (`ENV_MIGRATION` profile includes them), but they are never snapshotted into a bundle revision. The channel for shipping static assets with a bundle is `files/`.
- **Pre-flight validation failures leave no orphan directory** — all validators (`_assert_workspace_readable`, `_validate_publisher_ai_credentials_sdk`, `_ensure_publisher_plugin_files`) run before the `<rev>.tmp` directory is created, so a validation failure produces no partial directory. Filesystem failures that occur during the snapshot phase may leave a partial `<snapshot_path>.tmp` directory available for debugging; the bundle's `latest_revision_id` is unchanged in all failure cases
- **Per-bundle publish lock** — an in-process `asyncio.Lock` serialises concurrent publishes for the same bundle ID; the DB unique constraint on `(bundle_id, revision_number)` catches the cross-process race
- **Credential specs carry metadata only (with a controlled exception for template non-private fields)** — `required_credential_specs` in a revision contains `{name, type, allow_sharing, allow_template_sharing, description, provided_by, publisher_credential_id, service_uri?}` pairs from the publisher's linked credentials at publish time. For `provided_by="template"` specs, two additional fields are present: `template_data` (the publisher's non-private credential values, safe to include) and `template_private_fields` (the list of field names the installer must supply). Private field *values* are never stored in a revision — `PublishService._template_payload_for` strips them before writing the manifest. The optional `service_uri` field is a plaintext audience/slot identifier (see "Two-credential bundle pattern" below) and is never secret
- **Two-credential bundle pattern for per-user scoped access** — a bundle that exposes a producer agent's capability-narrowed REST API with per-user authority ships two credentials. First, a PBP `agent_api` connection credential shared to all installers (one shared token, one producer environment serves all installs' traffic; no per-install isolation in the current implementation). Second, a PBU `api_token` second token carrying each installer's specific scope (e.g. allowed company set), pre-shared by the publisher to each installer individually before they install. Both the connection credential and the per-user tokens carry the **same** `service_uri` value; their names and token values differ. The Tier 0b matcher at install time finds the pre-shared token by `service_uri + type` rather than by name, so differently-named per-user tokens auto-detect without manual selection. Authority lives entirely in the second token, validated server-side inside the producer agent; the `service_uri` is a non-secret routing hint only. Revoking a user = revoking the `CredentialShare` for that user's second token. See [Credential Sharing — `service_uri` Slot ID](../agent_credentials/credential_sharing.md#service_uri-slot-id-and-the-per-user-token-pattern) for the full matcher tier table and the share-before-install ordering constraint
- **`provided_by` resolution order** — at publish time, `PublishService._collect_credential_specs` resolves the `provided_by` value for each linked credential as follows: (1) consult `Agent.publish_settings.credential_overrides[<spec_name>].provided_by` if an override exists and it is one of `"user"`, `"publisher"`, or `"template"`; (2) infer: `allow_sharing=True` → `"publisher"`; else `allow_template_sharing=True` → `"template"`; else `"user"`. Inference is always the fallback when no override is present
- **Publisher-provided spec requires a shareable credential** — a spec can only be recorded as `provided_by="publisher"` if the underlying `Credential` row has `allow_sharing=True`. The publish-time `_validate_publisher_provides` check enforces this regardless of whether the value came from an override or inference; a publisher cannot publish a non-shareable credential as publisher-provided
- **Template-provided spec requires template sharing enabled** — a spec can only be recorded as `provided_by="template"` if the underlying `Credential` row has `allow_template_sharing=True`. The same `_validate_publisher_provides` check enforces this. Private fields (`template_private_fields`) are never stored in `template_data` inside the revision JSON — `PublishService._template_payload_for` strips them before writing the manifest
- **PBT auto-prefill matcher requires exact non-private value match** — for PBT specs, `CredentialsService.find_match_for_spec` filters name+type candidates by decrypting each candidate and comparing its non-private field values against the spec's `template_data` (both sides stripped of `template_private_fields`). Only an exact match is accepted; no type-only fallback is attempted. A credential pointing at a different server, database, or URL than the template intends is presumed wrong and produces no suggestion; the install proceeds with `mode: "skip"` and lands in `needs_setup`. PBU specs are unaffected: they continue to use the name+type match with type-only fallback
- **Install request payload accepts only the typed shape** — `POST /catalog/{bundle_id}/install` no longer accepts the legacy `dict[str, str]` credentials payload. Only `dict[str, InstallCredentialSelection]` (each entry having a `mode` field) is accepted. The legacy shim that was present in Phase 3 was dropped in Phase 5; submitting the old format returns HTTP 422
- **Publisher AI credentials must be owned by the publisher** — `PATCH /bundles/{bundle_uuid}` validates that any non-null `publisher_ai_credential_conversation_id` or `publisher_ai_credential_building_id` references an `AICredential` row owned by `bundle.publisher_user_id`; the endpoint raises 400 otherwise. Setting either field to explicit `null` clears the publisher-provides state for that mode and reverts to "user provides at install time"
- **Publisher AI credential type must match the env's SDK provider** — the same `PATCH /bundles/{bundle_uuid}` (and the pre-publish draft `PATCH /agents/{id}/publish-settings` and the publish call itself) validate that the credential's `type` matches the publisher install's env SDK provider for that mode. An `opencode/anthropic` conversation SDK only accepts an `anthropic`-typed credential — not any of the engine's other compatible providers. The check applies the strict full-SDK-id rule from `SDK_TO_CREDENTIAL_TYPE`; without it, a publisher could pair `opencode/anthropic` with an OpenAI key and ship a bundle that writes the wrong key into the wrong provider slot at install time. The check is skipped only when the publisher install has no active environment yet (the "incomplete install" warning shows instead)
- **AI credential resolution order at install time** — for each mode (conversation / building) the install resolves: (1) the bundle's `publisher_ai_credential_*_id` FK if non-null; (2) the installer's explicit selection in the `InstallRequest.ai_credential_selections`; (3) `None`, leaving the env-side resolver to fall back to the installer's defaults. When the bundle provides an AI credential for a mode, the installer's selection for that mode is ignored entirely
- **Degraded install on PBP credential failure** — if a PBP service credential is unavailable at install time (deleted publisher row, `allow_sharing` revoked, credential owned by a different user than the bundle publisher), the install activates anyway: a placeholder `Credential` is created for that spec and `last_update_status="degraded"` is written on the `Agent` row. The install is not blocked; the degraded state is surfaced via the runtime gate's `publisher_broken` status the first time the installer tries to use the agent
- **Deleting a PBP credential is blast-radius-gated** — a publisher who tries to delete a service credential that is publisher-provided in a published bundle with active foreign installs receives HTTP 409 (not a silent cascade). The response body is a structured `CredentialDeletionImpact` listing the affected bundles and the count of active installs. The publisher can pass `?force=true` to override the block; doing so deletes the credential, cascades to delete the underlying `CredentialShare` rows, and leaves affected installs in the `publisher_broken` runtime-gate state. See [Credential Sharing — Deletion Impact Gate](../agent_credentials/credential_sharing.md) for the full tier model. Publisher-provided AI credentials follow the same pattern: a force-deleted AI credential nulls the bundle's `publisher_ai_credential_*_id` FK via `ON DELETE SET NULL`, reverting affected bundles to "user provides" mode.
- **`provided_by` is frozen at publish — republish to apply changes** — the `provided_by` value for each credential spec is snapshotted into `AgentBundleRevision.required_credential_specs` at publish time and is **immutable** for that revision. Revisions are never mutated retroactively. When the publisher changes a credential's sharing mode (or override) after the last publish — for example, enabling `allow_sharing=True` on a connection credential that was created with `allow_sharing=False` — the live config screen immediately reflects the new mode, but all existing installers continue to receive the previously published `provided_by` until the publisher publishes a new revision. This is the expected and correct contract: revisions are immutable snapshots. The platform makes this gap visible rather than silently hiding it (see Credential Sharing Drift Detection below).
- **Credential sharing drift detection and republish nudge** — the Bundle tab's **Credential provisioning** panel now queries `GET /agents/{agent_id}/bundle-credential-drift` (publisher-install owner-only, `require_developer`-gated, 404 leak-safe) to diff each linked credential's live `provided_by` (recomputed from current `allow_sharing`/override state) against the latest published revision's snapshot. When any credential drifts, two surfaces show the gap: (1) an amber per-row inline hint in the provisioning panel, "Installers still receive the previously published setting (`<snapshot_label>`). Republish the bundle to apply `<live_label>`.", (2) an amber warning callout in the **Revisions block** of the same tab listing all drifted credentials with the message "Credentials `<name>` sharing differs from the latest published bundle (bundle: `<snapshot_label>`)". Publishing a new revision writes a fresh snapshot that matches the live state, clearing the drift. The drift computation deduplicates by credential name, and credentials removed since the last publish fold into the `stale=True` flag without emitting an empty-type row. Label mapping: `"user"` → "user-provided", `"publisher"` → "embedded (shared)", `"template"` → "template" (via the shared `providedByLabel` helper). `agent_api` credentials are the most common trigger because the "Connect Agent API" helper always creates them with `allow_sharing=False` and the publisher enables sharing afterwards. See [Credential Sharing — `provided_by` is frozen at publish](../agent_credentials/credential_sharing.md#provided_by-is-frozen-at-publish--republish-to-change-it) for the full rationale.
- **Revision delete blocked by foreign installs** — `DELETE /bundles/{uuid}/revisions/{revision_id}` rejects (409) when any consumer install (`is_publisher_install=False`) still has `installed_revision_id` pointing at the revision. The per-revision install count shown in the Revisions list already excludes the publisher's working install, so the delete button is enabled whenever the displayed count reaches zero. Only the publisher's own working install is auto-detached. Deleting the bundle's current revision rewires `latest_revision_id` to the previous remaining revision (or `NULL`); the on-disk snapshot directory is removed best-effort and a leftover failure is logged but does not block the DB delete
- **Last revision auto-unpublishes the bundle** — when revision delete leaves a bundle with zero revisions, the empty `AgentBundle` row is deleted in the same transaction. Cascades remove `BundleAccessGrant` rows; the publisher install's `bundle_uuid` is cleared via FK. This re-enables the "Bundle ID is immutable after first publish" gate (it becomes editable again because the publisher install is no longer linked to a bundle row)

## Architecture Overview

```
Publisher's Install (Agent row)
  is_publisher_install = True
  bundle_id = "io.opencinna.myagent.a1b2c3d4"
  bundle_uuid → AgentBundle.id
         │
         └── POST /agents/{id}/publish
                   │
                   ├── snapshots workspace folders
                   ├── writes <BUNDLE_STORAGE_DIR>/<bundle_id>/<rev>/
                   ├── inserts AgentBundleRevision
                   ├── updates AgentBundle.latest_revision_id
                   └── notifies foreign installs
                                  │
                                  ▼
                        Other User's Install (Agent row)
                          is_publisher_install = False
                          bundle_uuid → same AgentBundle.id
                          installed_revision_id → AgentBundleRevision.id
                          pending_update = True (if behind)
                                  │
                                  └── app-data/ (persistent, per-user×bundle)
```

| [Agent Schedulers](../agent_schedulers/agent_schedulers.md) | The publisher's `AgentSchedule` rows are snapshotted into the revision at publish time.
