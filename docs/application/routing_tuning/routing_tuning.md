# Auto Routing Tuning

## Purpose

Give a superuser the tools to answer "why didn't it find my agent?" for any LLM-mediated routing decision the platform makes. Before this feature, a routing miss left exactly one line in a process-local, in-memory ring buffer ([Channel Debug Monitor](../server_channels/channel_debug_monitor.md)) and nothing else — no candidate list, no rendered prompt, no record of which providers were tried, and nothing that survived a backend restart or a second worker process. Auto Routing Tuning makes every routing decision **observable, durable, reproducible, and advisory**: it is recorded in full, it outlives the process, an admin can re-run it after a change, and the feature never edits anyone's agent on their behalf — it only ever hands back a recommendation.

**Status: Phases 1–5 shipped and tested.** Traces are captured, persisted, browsable, superuser-simulatable, replayable, and diagnosed in plain language on `/admin/routing-tuning`, reached from the "Server Debug Tools" card on `/admin/server-configuration#channels`. Phase 5 unified the classifier behind every routing consumer, fixed the `prompt_examples` gap, added confidence/reason/runner-up (recorded only, never gating), and completed identity Stage-2 candidate capture in code — measured before/after against a live model rather than merely asserted; see [Phase 5 — Classifier Unification, `prompt_examples`, and Confidence](#phase-5--classifier-unification-prompt_examples-and-confidence). **`origin="app_mcp"` / `origin="identity"` capture is still not built, and the Stage-2 capture Phase 5 completed has no path to run on either** — the channel routing scope split closed the delegation that used to reach it from an open trace; see [Still Not Built](#still-not-built).

## Core Concepts

- **Routing decision / routing trace** — one LLM-mediated choice of "which agent or bundle should this message go to", captured end-to-end: every candidate considered (including the ones dropped, and why), the rendered classifier prompt, the raw model response, every provider/model the cascade tried, the verdict, the latency, and an optional confidence. Captured in memory by `RoutingTrace`, persisted as one `routing_decision` row.
- **Origin** — which caller produced the decision: `server_channel` (the only origin actually reachable today — see [Server Channels](../server_channels/server_channels.md)), `simulate` (an admin's what-if run), or the reserved-but-unreachable `app_mcp` / `identity` — declared in the trace vocabulary but never opened by any code path yet; see [Still Not Built](#still-not-built).
- **Stage** — one pass within a decision: `pass_1` (the sender's own installed agents), `pass_2` (the server-wide auto-install catalog), or `identity_stage2` (the Identity MCP Server's person→agent handoff). One decision can carry more than one stage — a Pass-1 miss that falls through to Pass 2 is still one decision and one row.
- **Candidate** — one agent, identity owner, or bundle the router looked at during a stage, eligible or not. An ineligible candidate carries a `skip_reason` (out of the channel's agent scope, no trigger prompt or example prompts, already installed, not installable, an identity currently unavailable, a foreign owner, and a couple of data-integrity cases). This is the single highest-value idea in the feature: a trace that only lists the finalists cannot explain the failure that actually bites — the expected agent was never a candidate at all. **As of Phase 5 of the channels & identity unification, no live routing decision produces a route-flavored `skip_reason`** — the entire `AppAgentRoute` family is deleted. `SKIP_IDENTITY_ROUTE` and `SKIP_ROUTE_INACTIVE` survive only as rendering constants so the admin UI can still show decisions captured before this phase; see [The reachability verdict](#the-reachability-verdict) below.
- **Reachability verdict** — a plain-language sentence, computed on the backend, saying why a decision went the way it did and what to do about it. The headline output of the feature; see [Business Rules](#the-reachability-verdict).
- **Near-miss ranking** — a Jaccard token-overlap score between the routed message and each candidate's trigger prompt **and `prompt_examples`, scored together as one document** (Phase 5 — this is what the classifier itself now receives), so a `no_match` verdict can say "closest: Equation Assistant (0.31)" instead of just "nothing matched."
- **Simulate** — an admin routes a hand-typed message as if they were a chosen user, with no effect on that user's account. **Replay** re-runs a *stored* decision's message against current configuration and diffs the two. **Recommendation** drafts a replacement trigger prompt for one candidate of a trace.
- **The message-text gate** (`ROUTING_TRACE_STORE_MESSAGE_TEXT`) — the setting that decides whether the sender's own words are stored and shown at all. See [The message-text gate](#the-message-text-gate) below; this is the part of the feature most worth reading carefully before touching it.
- **Retention** (`ROUTING_TRACE_RETENTION_DAYS`) — how long a decision row survives before an hourly scheduler purges it.

## User Stories / Flows

### 1. An admin diagnoses "the bot didn't find my agent"

1. Superuser opens **Admin → Server Configuration → Channels** and scrolls to the **Auto Routing Tuning** card.
2. The recent-decisions table shows every routed message, filterable by channel and outcome — `no_match` is the filter an admin actually wants.
3. Expanding a row shows the full candidate table (name, owner, source, trigger prompt, eligible/skip-reason, which one was chosen), every provider/model attempt with latency and error, the rendered classifier prompt, and the raw model reply.
4. The card's headline is the **reachability verdict** — a sentence like *"This user has 3 eligible candidates; Equation Assistant is not among them because it has neither a router trigger prompt nor example prompts, so there is nothing for the classifier to match a message against. Set a router trigger prompt (or example prompts) on the agent's Configuration tab."* (the channel wording — Server Channels is the only origin that actually produces traces today, so this is what an admin sees in practice; an App MCP decision, once that origin exists, would say the identical thing with "App MCP" in place of "a channel" — the two origins now share every branch of this diagnosis — see [Business Rules](#the-reachability-verdict)).
5. If the verdict is a near-miss rather than a total miss, the near-miss ranking shows which agent came closest and by how much.

### 2. An admin tests whether a routing fix actually works

1. From a `no_match` trace, the admin clicks **Draft a recommendation**. The card returns a copyable, improved trigger prompt for the agent's owner — generated from the failed message plus the agent's current configuration. Nothing is written; the admin (or the agent's owner) applies the wording themselves.
2. Once the owner (possibly the admin, possibly someone else) updates the trigger prompt, the admin clicks **Re-run** on the original trace. This replays the exact same message against current configuration and shows a before/after diff: did the outcome change, did the selection change, which candidates appeared or disappeared.
3. If the change didn't help, the diff says "nothing changed" out loud rather than rendering an empty panel — an unchanged replay is itself a real answer.

### 3. An admin diagnoses a user who has never messaged the channel at all

1. Someone reports that a colleague's message never got a response, or an admin wants to check a user's routing state before onboarding them to a channel.
2. The admin opens **Try a message**, types the message, picks the user from a picker, and toggles whether to include the auto-install catalog.
3. **Simulate** runs the same routing pipeline that a real message would, with no side effects whatsoever — no thread binding, no session, no install, no outbound reply — and returns the same trace view a stored decision would show.
4. This is the tool's only way to inspect a user who has never triggered a real decision, and it is treated as real reach: every simulate run is superuser-only, rate-limited, and audited (see [Business Rules](#simulate-replay-and-the-hard-boundary)).

## Business Rules

### The reachability verdict

The reachability verdict is computed **on the backend**, not assembled by the admin UI from whatever fields happen to be handy. Three reasons this matters: the wording is testable (every branch has a test pinning both a machine-readable code and the exact sentence it produces); the wording lives beside the routing rules it paraphrases (so the two files cannot drift silently the way two copies of the same logic would); and a wrong diagnosis here is actively harmful — this surface tells an admin what to change on *somebody else's* agent, so a plausible-but-wrong sentence is worse than no sentence.

The verdict draws on two sources of truth, deliberately in this order: the trace itself (what the router actually considered at the time) wins whenever it has an answer, because it describes the decision being diagnosed. Current database configuration is consulted only for an agent the trace never mentions at all — which is precisely the case the trace cannot explain on its own.

**The verdict is split by origin for *wording*, never for *findings*** — and **as of Phase 5 of the channels & identity unification, that split has shrunk to a single clause.** `server_channel` and `simulate` decisions get **channel wording**; every other origin (including the reserved-but-unreachable `app_mcp` and `identity` — see [Still Not Built](#still-not-built)) gets **App MCP wording**. But `_verdict_from_configuration` — the function that answers "why was this expected agent never a candidate" — is now **one function for both origins**, not two: it used to be a channel half asking three questions and an App MCP half asking four more about routes, assignments, and the `channel_app_mcp` flag before it even reached ownership. All four of those questions were about a switch that no longer exists — App MCP builds its ballot from `ChannelCandidateProvider` + `IdentityCandidateProvider`, exactly as a channel does — so the two halves collapsed onto the same three branches, against the same two facts that make an agent a candidate on **either** surface: **who owns it**, and **whether its owner wrote anything for the classifier to match on**. The `channel` flag today does exactly one thing inside that function: it picks which two words — "a channel" or "App MCP" — a sentence names as the surface. See channel routing scope split §2.4 and §5 Phase 4 for why the split existed at all: the verdict used to prescribe an App MCP remedy for a Google Chat miss.

**The motivating case that split existed to fix — a standalone agent invisible to App MCP because it had no `AppAgentRoute`** — no longer exists as a *distinct* case. Before Phase 5, a non-bundle ("standalone") agent got no auto-route by construction, so App MCP's classifier never saw it even with a trigger prompt set, and the fix was to diagnose it in words rather than auto-create a route with different consent implications. With the route mechanism deleted outright, "invisible to routing" now means exactly the same thing on both surfaces: an owned agent with neither a router trigger prompt nor example prompts, diagnosed by the identical sentence either origin gets: *"…it has neither a router trigger prompt nor example prompts, so there is nothing for the classifier to match a message against. Set a router trigger prompt (or example prompts) on the agent's Configuration tab. That pair is the whole of it — there is no route, assignment or per-agent toggle to configure anywhere."* (`CODE_EXPECTED_CHANNEL_NO_TRIGGER_PROMPT` — its wire value keeps the word "channel" for a historical reason explained below.)

**A pre-Phase-5 trace can still carry route-flavored skip reasons** — an inactive route, an identity-contact route — from when channel Pass 1 read `AppAgentRoute` (before the earlier scope split) or when App MCP's own six route-based verdict codes existed (before this phase). `SKIP_IDENTITY_ROUTE` and `SKIP_ROUTE_INACTIVE` survive purely as rendering constants so the admin UI can still show those decisions; nothing in the current pipeline produces either. The six App-MCP-only verdict codes those old decisions could carry — a route that was inactive, not on the App MCP channel, unassigned, or absent on a standalone / bundle install — are **deleted outright**, not renamed: `CODE_EXPECTED_STANDALONE_NO_ROUTE`, `CODE_EXPECTED_BUNDLE_NO_ROUTE`, `CODE_EXPECTED_NO_TRIGGER_PROMPT`, `CODE_EXPECTED_ROUTE_INACTIVE`, `CODE_EXPECTED_ROUTE_NOT_APP_MCP`, `CODE_EXPECTED_ROUTE_UNASSIGNED`. A stored diagnosis computed from one of those codes before this phase keeps whatever text it was written with (verdicts are not retroactively recomputed); a **fresh** diagnosis of any trace, old or new, now always comes from the current, unified branch table.

**Why `CODE_EXPECTED_CHANNEL_NO_TRIGGER_PROMPT`'s wire value still says "channel."** The code serves both origins as of Phase 5, but its string value (`expected_agent_channel_no_trigger_prompt`) is a wire value a stored diagnosis and a client both read, and only the *audience* widened — renaming it would silently reinterpret every historical row that carried it. The "channel" in the spelling is therefore historical, not a claim about which origin the code applies to today.

Every branch names a remedy, not just a description of what's wrong. The verdict for an agent that was genuinely eligible but simply lost to the classifier points at widening its trigger prompt, or drafting a recommendation. The verdict for an agent belonging to a different account points at sharing its bundle and having them install it — or, in a parenthetical, notes that reaching somebody else's agent directly is what identity contacts are for, a different question from this one.

### The trace records rejections, not just winners

Every candidate the router looked at is recorded, whether or not it was eligible to be chosen. An ineligible candidate carries a `skip_reason` explaining why it was dropped before the classifier ever saw it (already installed, not installable by this user, no trigger prompt to match against, reached only through an identity contact route, owned by a different account, or an inactive route — plus two data-integrity cases where a bundle's revision or an agent behind a route has gone missing). This is stated in the implementation as the single highest-value rule in the whole feature: a trace listing only the finalists cannot diagnose the failure mode that actually bites, because the expected agent was frequently never a candidate at all.

`match_method` on a decision answers "how did the *last* stage match", not "how was the decision reached" — and it deliberately survives a `no_match` outcome. A row reading `outcome=no_match, match_method=ai, selected_agent_id=NULL` says the classifier *did* pick something and a later filter (the ownership check, the identity handoff) rejected it — a materially different and more useful diagnosis than "nothing matched at all."

### Simulate, replay, and the hard boundary

Simulate and replay both run a message through the same routing logic a real message would, and both are read/write-audited, superuser-only, and rate-limited per admin — because both spend a real LLM call and both can reveal which agents another account has installed, which is real information about that account. The rate limit is shared across simulate, replay, and the recommendation draft (one bucket per admin), so rotating between the three routes cannot spend three times the configured budget.

**Simulate has no side effects by construction, not by a flag.** The routing decision itself was split out of the real inbound pipeline into a pure function — `ChannelRoutingService.decide()` — that takes a user id and a message and returns an agent/bundle id plus its trace. It creates no thread binding, opens no chat session, installs nothing, and sends no reply, not because a `simulate=True` parameter suppresses those effects at each call site, but because none of that code is reachable from `decide()` at all: no thread-binding model, no outbound-delivery service, and no install service are even imported into the module that implements it. The real inbound pipeline composes `decide()` → bind → ingest; simulate calls `decide()` and stops. A flag threaded through two hundred lines would make "no side effects" a property somebody has to keep true at every future branch; making it a property of the *call graph* means a side effect can only be reintroduced by adding an import that would show up in any diff.

**The admin surface is read-only with respect to agents, and this is a hard boundary, not an implementation detail.** No route, no service call, and no button anywhere in this feature edits another user's agent, its trigger prompt, or a bundle. When a foreign agent routes badly, the output is a **copyable recommendation for its owner** — generated text the admin can hand over, never a change the admin makes on the owner's behalf. The fix path is unchanged from before this feature existed: tune your own agent, or update the bundle and republish it. This boundary is why the recommendation-draft endpoint is explicitly documented as writing nothing at all — not to the trace, not to the agent, not to the bundle.

### The message-text gate

Server Channels otherwise deliberately keeps inbound message text out of the database entirely (see [Server Channels](../server_channels/server_channels.md)). A routing trace without the message is close to useless for tuning, so this feature makes a documented, deliberate exception: it stores the sender's message, clamped in length, retained for a bounded window, superuser-only — governed by `ROUTING_TRACE_STORE_MESSAGE_TEXT` (default on).

The mechanism, not a list of fields, is what enforces this. When the gate is off, the stored/served stage payload is projected through an **allowlist**: a field is written and served only if it has been explicitly declared free of the sender's own words. Anything not on that allowlist — including a field added to the trace after the gate was written — is withheld by default. This is the opposite of a denylist, and the difference is not cosmetic: the gate used to work by naming the fields known to carry sender text, and that approach failed three separate times in a row, each time missing exactly one field that had started carrying the sender's words through an ordinary, reviewable-looking change (a rendered prompt, a raw classifier reply, then a provider SDK's error message that happened to echo the request payload back). An allowlist inverts the question from "did we remember every field" — which is structurally unanswerable — to "is this field safe", which whoever adds a new field can actually answer at the moment they add it. The one exception admitted onto the allowlist deliberately is a candidate's own trigger prompt and prompt examples: those are the *agent owner's* configuration, not the sender's words, and a superuser can already see them through ordinary platform surfaces, so admitting them costs nothing and their absence would degrade a diagnosis (the near-miss ranking) that has nothing to do with sender privacy.

The gate applies to both directions from one shared definition — what gets *written* to the database and what gets *served* back out — so the property holds regardless of the byte length of any prompt template, and regardless of whether an operator flips the setting after some rows were already captured with it on.

**The gate hides; it does not erase.** Turning `ROUTING_TRACE_STORE_MESSAGE_TEXT` off stops rows from carrying the sender's words going forward and stops already-stored text from being served — but the underlying database rows keep their data. Exactly two things actually remove stored text: waiting out the retention window (`ROUTING_TRACE_RETENTION_DAYS`), or an admin explicitly clearing the traces (`DELETE /api/v1/admin/routing/traces`). This is deliberate: an accidental toggle must not be able to irreversibly destroy diagnostic data, and a privacy control whose misfire is unrecoverable is its own hazard. The same "hides, does not erase" property and the same two erasure paths apply to `ROUTING_TRACE_ENABLED` — turning that off stops the admin API from *serving* any stored decision, but does not delete anything either.

### The retention sentinel

`ROUTING_TRACE_RETENTION_DAYS` must be `>= 1`, or exactly `-1` to mean "keep forever" — the escape hatch for a debugging session that needs to outlive the normal window. Every other value, including `0`, is **rejected at server startup**, and the validation error names `-1` by name as the only spelling of "unbounded."

This is deliberate and not an arbitrary restriction: `0` reads, to an operator, like "keep nothing" — but the feature's design intent is the opposite of "let it default to unbounded." A value that *reads* as "no retention" but actually *means* "unbounded retention" would invert exactly the property this setting exists to protect (the case for storing message text at all is that it bounds the *duration* of an exposure the live debug feed already grants, not that it removes the exposure class), and it would fail toward keeping *more* of external senders' text, silently, for whoever mistypes it. An operator who wants "don't keep message text" has two settings that actually say that (`ROUTING_TRACE_STORE_MESSAGE_TEXT=False`, or `ROUTING_TRACE_ENABLED=False` to stop writing rows at all) — `RETENTION_DAYS` is not one of them, and the startup validator says so.

## Architecture Overview

```
Server Channels inbound  ──▶ ChannelRoutingService.decide()  ──┐
   (the only reachable      Pass 1: sender's own agents        │
    origin today)           Pass 2: auto-install catalog       │
                                    │                           │
                       RoutingTrace.capture(origin=…) ──────────┤
                              candidates + skip_reason ─────────┤
                              rendered prompt + raw response ───┤
                              provider/model attempts ──────────┤
                                    │                           ▼
                        routing decision (agent/bundle/None)   routing_decision row
                                    │                       (superuser-only, TTL'd,
                    ┌───────────────┴──────────┐             message-text gated)
                    ▼                           ▼                     │
        bind + session + reply        ChannelDebugBuffer (live)       │
        (real path only —                  detail.trace_id ──────────┘
         simulate stops here)

Admin ──▶ GET/DELETE /admin/routing/traces[/{id}]  ── list, detail + reachability verdict
      ──▶ POST /admin/routing/simulate             ── decide() for another user, no effects
      ──▶ POST /admin/routing/traces/{id}/replay   ── re-run + diff against current state
      ──▶ POST /admin/routing/traces/{id}/recommendation ── copyable draft, writes nothing
```

## What This Feature Taught

The implementation surfaced a set of engineering lessons the plan records at length (`docs/plans/auto_routing_tuning_plan.md` §7 and §11a) because they were each learned the expensive way — by shipping the mistake first. They are recorded here in full because they are rules for how to build *this kind of feature* (an observability layer that must never become the thing that breaks what it observes), not just trivia about this one.

**Verification is a different activity from review, and a review pass will not substitute for it.** Reading code tells you it does what it claims to do. It does not tell you whether the claim itself is true. Three of the four original instances of "a dangerous state that looks routine" (below) were caught not by someone reading the code for bugs, but by someone independently *checking whether a specific claim was actually true* — the retention sentinel's claimed meaning, whether a routing pass that found nothing had actually run, and whether a note in this very planning document describing a setting as "removed" matched what `config.py` actually contained at that moment. None of the three would have been caught by a normal code review, because in each case the code did exactly what its author believed it did — the belief was wrong, not the execution. The practical consequence: budget time for verification as its own line item on a change like this, distinct from and in addition to review. A team that reviews thoroughly and never independently re-checks a load-bearing claim will still ship this class of bug.

**Rule 1 — a dangerous state must not be able to look routine, and a control must not appear to do more than it actually does.** These are two faces of the same failure. The retention sentinel is the first face: `ROUTING_TRACE_RETENTION_DAYS = 0` originally meant "keep forever" — the single most consequential configuration this feature has, rendered as an unremarkable integer with no visual distinction from any other setting. The second face showed up in the startup log line itself: the purge scheduler used to log `-1` as "retention -1 days," a plain number sitting among ordinary output, when it is in fact the one setting that keeps every external sender's message text indefinitely; it now reads `retention DISABLED (keeping routing traces forever)` in words. A third instance was found in the *read* path rather than in configuration: a routing pass that ran and genuinely found nothing was, for a while, indistinguishable in the stored trace from a pass that never executed at all, because nothing forced a stage to exist until some mutator happened to be called on it — and the Pass-2 short-circuit on an empty auto-install list (the default state of every fresh deployment) hit exactly that gap. It is fixed by making stage creation happen eagerly, on capture entry, so "this pass ran" is a structural fact rather than a coincidence of which code paths a given message happened to touch. A **fourth** instance was found inside the planning document that describes this very feature: a setting was written up as struck-through and already-removed while it was, at that moment, still live in the settings file — two independent readers took the written plan at face value and believed a change had shipped when it had only been decided. The corollary of Rule 1 is symmetric: a control must not appear to do *more* than it does, either. `ROUTING_TRACE_STORE_MESSAGE_TEXT=False` hides existing sender text; it does not erase it — so the setting's own documentation, the operator-facing notice, and this doc all say exactly that, and all name the two things that genuinely do erase it.

A related shape, found later and worth naming on its own: **a safe state that is entirely routine and quietly stops being safe.** The classifier prompt template that renders on every routing decision happened, for a while, to be long enough that the rendered prompt overran the trace's text-clamp *before* the sender's message got appended to it — so the field the recorder captured for the "rendered prompt" never actually contained the sender's words, purely as a side effect of the template's byte length. Nothing about that was labeled dangerous, because nothing about it looked unusual: it was an ordinary markdown file of an ordinary length. An entirely reasonable future edit — trimming that template, which is exactly what Phase 5's confidence/reason/runner-up prompt-contract change went on to do — would have silently turned that field into a full-text leak with no code change to review and nothing that would fail a test. The fix was to stop relying on the accident and gate the field on the *write* path as well as the read path, so the privacy property no longer depends on how many characters a markdown file happens to contain.

**Born-false claims need a different defence than decayed ones.** A claim can be true when it is written and become false later — that is decay, and the defence against decay is to describe a mechanism instead of a fact, because a mechanism does not fall out of date the way a snapshot of the world does. But a claim can also be **born false**: never true even at the moment it was written. One docstring in this codebase asserted four structural facts about a module's purity in the same commit that shipped a test enforcing only three of them — the fourth fact was never actually checked by anything, from day one. A helper function's docstring described itself as computing a "total" the very day it was written, while its first line of code sat outside its own error-handling and could, in fact, raise. Mechanism-wording is no defence against a born-false claim, because the claim was never true regardless of how it is phrased — the only real defence is to write the claim and the test that enforces it in the same change, and to treat any guarantee stated only in prose as unverified until something actually executes it and fails when it's wrong.

**The clearest illustration of "born false" in this work is a refusal to fix something, not a fix.** While auditing which parts of the routing code could be safely called "read-only," a developer declined to add that guarantee for two functions one layer removed from the routing entry point, even though doing so would have been the locally obvious next step in a cleanup pass. The reason: those two functions are also called from outside the routing feature entirely, by code this work has no visibility into and no authority to reason about — so asserting "nothing in these ever writes" would not have been a description of anything actually verified, it would have been exactly the kind of prose guarantee this whole set of lessons exists to eliminate. Declining to add a fix because making the fix would recreate the precise failure mode the surrounding work exists to remove is the rule *understood*, not merely *followed* — it is easy to apply "verify claims" everywhere except to the claim you are about to add yourself.

**A mutation check has exactly one honest exception, and the exception has to be named out loud rather than silently taken.** A *regression guard* asserts a behavior the surrounding code could plausibly break by accident, and such a guard is worthless — not weak, worthless — until someone has actually broken it on purpose and watched the guard fail. A *precondition assertion* is different in kind: it pins a fact that the surrounding design already fixes by construction (for example, "a standalone agent never gets an automatic route" — that is a deliberate design choice this feature diagnoses rather than a bug it guards against), and deliberately breaking that fact to "prove" the assertion would mean breaking a rule the current phase has placed out of scope, for no benefit. The rule that keeps this honest is to say, in the test or the comment beside it, which kind of assertion is being skipped and why — a blanket policy of "always demand the mutation, no exceptions" invites people to either fake mutations that prove nothing or quietly skip the check altogether, and from the outside those two failures look identical.

**An instrument error is a distinct and more persistent failure mode than a wrong claim, because re-running the check reproduces the same wrong answer.** A plain factual mistake gets caught the moment someone re-measures. An instrument error survives re-measurement, because the measurement itself is honest — it simply answers a different question than the one being asked, and asking it again just gets the same honest, irrelevant answer again. Four instances turned up in this body of work alone: a test count reported "for a whole directory" that was actually the count from a single file inside it, because the counting command happened to be scoped one level too narrow; a search for a generated symbol pattern that matched nothing, reported as "zero regenerated," when the actual generator in this codebase emits a different naming convention than the one the search was looking for; a `git checkout --` invocation against a path containing both tracked and untracked files, which exits with status 0 — a fully "successful" exit code — while silently skipping every untracked file in that path, so a caller who trusts the exit code believes a restore happened that didn't; and a frontend typecheck filter (of exactly the kind this codebase's own guidance recommends, using a symbol-name grep against `tsc` output) that matched only 2 of 11 files known to contain a deliberately injected type error, because `tsc` keys its output lines on file *paths*, not on the symbols the filter was written to catch. The common thread, and the lesson to generalize: when a measurement is load-bearing for a decision, check what the instrument actually matched, not just whether it reported success — an honest tool answering the wrong question looks exactly like a correct answer until someone checks.

**A test exists in this codebase specifically to prevent a debugging aid from ever being misread as having solved a problem it only partially solves — `test_a_failed_write_makes_the_error_reportable_but_not_durable`.** It documents a real, deliberate limit in the same family this feature's own instrumentation lives in: guarding a diagnostic write against raising makes a failure **reportable** — the caller gets to keep running, and the failure is visible in the log and in the in-memory debug feed — but a guard that only prevents a crash does not make that failure **durable**. When the actual database commit for the diagnosis fails, the transaction rolls back, and whatever record of the failure was about to be written (a binding's `last_error`, in the concrete case this test pins) is discarded along with everything else in that transaction — the system is left with no persisted trace that anything went wrong at all, even though nothing crashed. The test exists so that nobody reading the surrounding guard code concludes it has solved durability, when what it has actually solved is a narrower and more modest problem: making a failure legible in the moment, not making it survive. The distinction matters directly for Auto Routing Tuning's own recorder, which makes the identical trade for the identical reason — `RoutingTraceService.persist` swallows its own failures so a broken diagnostic write can never take down a real routing decision, and that guard makes the failure reportable (it is logged) without making it durable (a `persist` failure produces no `routing_decision` row at all, by design, because a diagnostic must never hold the routing pipeline's transaction hostage).

## Integration Points

- [Server Channels](../server_channels/server_channels.md) — the only wired producer of routing decisions today. `ChannelInboundService` opens the two routing-trace captures (Pass 1 and Pass 2) and is the sole caller of `ChannelRoutingService.decide()` on the real (non-simulate) path. The live [Channel Debug Monitor](../server_channels/channel_debug_monitor.md) feed carries a `detail.trace_id` pointing at the durable row this feature writes, published only when a row was actually persisted.
- [App MCP Server](../app_mcp_server/app_mcp_server.md) — shares the same `AgentClassifier` every routing consumer now goes through (unified in Phase 5), but App MCP requests still do not open a `RoutingTrace` capture of their own — see [Still Not Built](#still-not-built).
- [Identity MCP Server](../identity_mcp_server/identity_mcp_server.md) — its Stage-2 person→agent handoff runs inside the `identity_stage2` trace stage; that stage's recorder captures the rendered prompt, the raw response, **and its full candidate list** — `IdentityRoutingService._binding_candidates()` is the single builder feeding both the classifier and the trace, and a binding with no assignment for the caller is recorded as a `no_assignment` skip rather than dropped. Since Phase 3 of the channels & identity unification the recorder has somewhere to write: `ChannelRoutingService.decide` opens the stage from inside Pass 1's capture, so identity routing over a Server Channel is fully traced. The App MCP path is still untraced for the unrelated reason that `AppMCPRequestHandler` opens no capture at all — see [Identity Stage-2 capture is reachable](#identity-stage-2-capture-is-reachable) and [Still Not Built](#still-not-built).
- [Agent Bundles & Installs](../../agents/agent_bundles/agent_bundles.md) — **as of Phase 5, the reachability verdict reads nothing bundle-specific at all.** The standalone-vs-bundle branching this bullet used to describe — reading `Agent.bundle_uuid` and `AppAgentRoute` directly — is deleted along with the route mechanism it diagnosed. `_verdict_from_configuration` now reads only `Agent.owner_id`, `router_trigger_prompt` and `example_prompts`, identically for a channel and an App MCP origin, and has nothing to say about whether an agent came from a bundle install one way or the other.
- [Agent Activities & Security Events](../agent_activities/agent_activities.md) — every simulate/replay run and every trace-clear writes a `SecurityEvent` (`ROUTING_SIMULATE_RUN`, `ROUTING_TRACES_CLEARED`), the durable audit trail alongside the disposable diagnostic rows this feature owns.
- [AI Functions](../../development/backend/ai_functions_development.md) — the recommendation draft calls `AIFunctionsService.generate_router_trigger_prompt`. As of Phase 5, all four routing consumers (Channel Pass 1, Channel Pass 2, App MCP Stage 1, Identity Stage 2) classify by calling `AgentClassifier.classify` directly rather than `AIFunctionsService.route_to_agent` — that wrapper still exists (`app_agent_router.route_to_agent` is now a thin adapter over the same classifier) for callers outside routing.

## Phase 5 — Classifier Unification, `prompt_examples`, and Confidence

Phase 5 shipped, and it is a *behavior-changing* phase by design (plan §5, §10) — the previous four phases existed specifically so this one could be measured rather than asserted.

**What changed:**

- **One classifier.** `AgentClassifier.classify(candidates, message)` (`backend/app/services/routing/agent_classifier.py`) now owns prompt rendering, parsing, and trace emission for every routing consumer — Channel Pass 1, Channel Pass 2, App MCP Stage 1, and Identity Stage 2. The three hand-rolled copies (`app_mcp_routing_service._ai_classify`, `identity_routing_service._ai_classify`, and Channel Pass 2's use of `AIFunctionsService.route_to_agent`) collapse into it. `app_agent_router.route_to_agent` is now a thin `list[dict]`-in adapter over the same classifier, kept because `AIFunctionsService.route_to_agent` and `app.agents`'s own export still publish that dict shape to callers outside routing; `RouteToAgentResult` is an alias of `ClassificationResult`, not a second class kept in step.
- **`prompt_examples` now reaches the model.** `AgentClassifier.render_prompt` emits an `**Example messages**` sub-list under each candidate, built from up to 10 non-empty lines of `prompt_examples`. Before this change the field was validated, stored, and documented as a routing aid, but was silently dropped before the prompt was ever rendered.
- **`confidence` / `reason` / `runner_up` are requested and parsed defensively.** Absent or malformed ⇒ `None`, never a parse failure — smaller/local models routinely ignore added JSON fields, and a strict parse would turn a tuning feature into a routing outage. **They are recorded only; routing is not gated on confidence.**
- **`stages[].reason` moved off the message-text allowlist in the same change that started populating it from the model.** It held nothing but this codebase's own parse literals through Phases 1–4 and was safe on those terms; the moment a model's own justification for a choice lands in it, it is a rewrite of the sender's words exactly like `raw_response`, and the mechanism — an allowlist of fields declared safe, not a list of fields known to be tainted — is what makes moving it a one-line change rather than an audit of every reader. See [The message-text gate](#the-message-text-gate).
- **Near-miss ranking now scores `prompt_examples` alongside `trigger_prompt`**, joined as one document, so the tuning card ranks candidates on what the classifier actually sees rather than a stale subset of it.
- **Identity Stage-2 candidate capture was completed here and became reachable in Phase 3 of the channels & identity unification.** `IdentityRoutingService._binding_candidates()` is the single builder feeding both the classifier and the trace's candidate capture, and the `only_one` branch calls `record_match` — before Phase 5, a Stage-2 hit could persist as `match_method=None`, a lying field rather than a missing one. Phase 5 left it with no capture to write into; that is no longer true — see [Identity Stage-2 capture is reachable](#identity-stage-2-capture-is-reachable) below.

**What was measured, and how the measurement was kept honest.** Against this project's default provider cascade (`granite4` via Ollama), 12 messages × 3 reps (36 runs) were routed before and after Phase 5:

- **Intended-target hits: 17/36 → 33/36. No-match: 8 → 3. Zero regressions** — no message's intended target was hit less often after the change than before it.
- These numbers come from a *single instrument applied to both sides*, and that is load-bearing here, not a footnote. The original before/after harness pinned the model provider by wrapping `route_to_agent`; Phase 5 moves every routing consumer off that function onto `AgentClassifier.classify` directly, so the pin would have silently stopped applying, and the "after" run would have measured a *different provider cascade* than the "before" run while producing output that looked entirely normal — a before/after invalidated with no symptom. This was caught before it corrupted the comparison: the pin was rewritten at the settings level (provider-cascade-independent of which function does the calling), the pre-change tree was restored from a `cp` snapshot, and the identical script was re-run against it — so both sides of the 17→33 comparison are read off one instrument, not two runs that merely happen to be adjacent. The re-run baseline reproduced the original per-message results within normal model variance (one message differed by one rep of three). A reader who assumed the first pass alone had produced these numbers would be trusting a comparison that was never valid — this feature exists to make routing decisions verifiable rather than assumed, and the same standard applies to its own evidence.
- **One lateral move deserves its own sentence rather than disappearing into "zero regressions."** One message with no correct owner among the candidates moved from one wrong agent to a different wrong agent — toward the example-rich one. That is the exact shape a real regression from this change would take: an agent with richer examples becomes more attractive across the board, not only for the messages it should actually win. A control message with no correct owner held at `NO_MATCH` 3/3 on both sides, which bounds the concern without eliminating it. A summary that reported "17→33, zero regressions" and dropped this message would be true and would hide the one direction this class of change can go wrong.
- **The two behaviors plan §8 predicted are now measured facts, not arguments made in advance.** The defensive parse fired on roughly 1 in 3 calls: the model omitted `runner_up` on 12 of 36 calls and `confidence` on 7 of 36 — exactly the shape a strict parse would have turned into an outage. And confidence is uncalibrated by direct observation, not by assumption: of the calls that answered, 26 scored `1.0` and 3 scored `0.95`, with 7 of 36 omitting the field entirely. Both numbers are now the evidence behind "record only, do not gate," not a decision made on instinct and left unverified.

## Identity Stage-2 Capture Is Reachable

Until Phase 3 of the channels & identity unification, this document said Stage-2 capture was complete in code but unreachable — dead instrumentation on a surface no capture was ever open around. **That is no longer the case, and the correction matters more than most because it was a claim about *coverage*: a reader had no way to spot it as false from the trace UI, which simply showed nothing.**

What changed: `ChannelRoutingService._route_installed` now composes `IdentityCandidateProvider` into the channel Pass-1 ballot (gated on the sender's `allow_identity_routing`), and `ChannelRoutingService.decide` calls Stage 2 itself when a person wins — from **inside** Pass 1's `RoutingTrace.capture()`. So a channel decision that touches identity now carries, durably:

- the identity candidates on the Stage-1 ballot, each with the namespaced `ref_id` `identity:{owner_id}`, alongside the sender's own agents;
- `SKIP_IDENTITY_UNAVAILABLE` rows for identity owners who were on the ballot's input but had nothing reachable;
- the whole Stage-2 decision under the `identity_stage2` stage — its candidate list, rendered prompt, raw response, and a `match_method` of `"only_one"` or `"ai"` (glob/pattern matching was deleted in Phase 1 of the same refactor, so `pattern` is no longer part of the Stage-2 vocabulary).

Two limits, stated precisely so this does not over-claim in the other direction:

- **Reachable from the channel/webhook path, and from a replay of a stored channel trace** (which resolves that trace's own `channel_id` back into a real policy). **Not reachable from `POST /admin/routing/simulate`:** `RoutingSimulateRequest` carries no `channel_id`, so the run resolves `ResolvedChannelPolicy.for_no_channel()`, whose `allow_identity_routing` is `False` — permissive on everything else, deliberately not on this one, because the absence of a channel is not a person's consent. Closing that is deferred to Phase 6 of the channels & identity unification refactor.
- **`origin` is still `server_channel`.** Phase 3 did not add `origin="identity"`; identity Stage 2 is a *stage within* a channel decision, not a decision of its own. `ORIGIN_IDENTITY` and `ORIGIN_APP_MCP` remain reserved values no trace has ever carried.
- **A channel decision can now carry `SKIP_IDENTITY_UNAVAILABLE`, but a channel user cannot yet read the explanation for it.** `RoutingReachabilityService` has the channel-voiced remedy text (landed in the same change, per that file's convention that adding a reason to a surface and adding its override for that surface are one change), but the only branch that renders a skip explanation is keyed by a `uuid.UUID` `expected_agent_id`, and an identity candidate's `ref_id` is `identity:{owner_id}`. *Producible* and *explainable* are facts about different layers; only the first is true today, and the second is Phase 6's.

## Still Not Built

`origin="app_mcp"` and `origin="identity"` **capture do not exist.** Phase 5 unified the *classifier* every routing consumer calls into; it did not touch the set of places that open a `RoutingTrace.capture()`, which remains exactly the two `server_channel` sites (Pass 1 and Pass 2) plus `simulate`. `ROUTING_TRACE_APP_MCP_MODE` stays removed for the reason it was removed in the first place — nothing opens a capture it could gate — and is reintroduced only in the same change that starts emitting `ORIGIN_APP_MCP`, never before. So **App MCP requests still leave no durable trace of their own.**

Identity is no longer in that position, and the two facts should not be confused: identity Stage 2 is fully captured *on the channel surface*, as a stage inside a `server_channel` decision (see [above](#identity-stage-2-capture-is-reachable)). What is still missing there is a Stage-2 trace on the **App MCP** surface, for the same single reason App MCP has no traces at all — its request handler opens no capture. `ORIGIN_APP_MCP` and `ORIGIN_IDENTITY` remain declared in the trace vocabulary as reserved values that no trace has ever actually carried — see the tech doc's [Configuration](routing_tuning_tech.md#configuration) section.

Two smaller gaps, both deferred to Phase 6 of the channels & identity unification: `POST /admin/routing/simulate` cannot reach identity routing (no `channel_id` on the request ⇒ a policy with `allow_identity_routing=False`), and a `SKIP_IDENTITY_UNAVAILABLE` skip explanation, though written for the channel voice, cannot be rendered because the skip-explanation branch is keyed by a `uuid.UUID` agent id.

Phase 6 (a curated `(message, expected_agent)` eval set replayed as a batch to score a trigger-prompt change before it ships) remains deferred, as the plan describes it — Phases 1–5 are its prerequisite, not a substitute for it.
