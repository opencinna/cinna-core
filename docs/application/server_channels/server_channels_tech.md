- `backend/app/services/routing/channel_candidate_provider.py` — `ChannelCandidateProvider`: Pass 1's candidate set, built from `select(Agent).where(Agent.owner_id == user_id)`, narrowed to the resolved channel `agent_scope`. - `backend/app/services/server_channels/channel_stream_relay.py` — **new.** `ChannelStreamRelay`, `ChannelStreamRegistry`, `ChannelRelayEventHandler`, `maybe_attach_channel_relay` — the rolling status-notice draft a streaming turn writes. ## Database Schema

### `server_channel`
One row per configured channel instance. Key fields: `channel_type` (indexed, must resolve in `CHANNEL_ADAPTERS`), `name` (unique), `enabled` (disabled ⇒ webhook 404s / App MCP token refused, same treatment as unknown), `config` (JSON, adapter-specific non-secret config — Google Chat: `{"project_number": "..."}`; Email: `{"incoming_server_id", "outgoing_server_id", "incoming_mailbox", "from_address"}`, see [Email Integration tech](../email_integration/email_integration_tech.md#config); App MCP: always `{}` — `validate_config` rejects any non-empty value), `encrypted_secrets` (Fernet-encrypted, nullable, write-only — always empty for a transport that declares `needs_outbound_credentials=False`, e.g. email (credential lives in `mail_server_config` instead) and App MCP (no outbound credential exists at all)), `email_whitelist` (Text, nullable — null/empty is fail-closed deny-all; always `NULL` for App MCP, which has no external sender to whitelist), `webhook_token` (unique, 64 chars, `secrets.token_urlsafe(32)`, **nullable since migration `ca0192122e0c`** — `NULL` for every channel whose transport declares `needs_webhook_token=False`, i.e. a `polled` transport like email or the `authenticated` App MCP transport; driven by `ChannelCapabilities.needs_webhook_token`, not hardcoded per type), `created_by` (FK `user.id`, `ON DELETE SET NULL`). Unique constraints on `name` and `webhook_token` (PostgreSQL `UNIQUE` permits any number of `NULL`s, so multiple tokenless polled/authenticated channels coexist without collision). A **second** unique index, `uq_server_channel_singleton_type` (partial, `postgresql_where=channel_type IN ('app_mcp')`), caps a singleton type at one row — see [Migration](#migration) above; adding a future singleton transport requires a new migration that rebuilds this index with the extra type in the `IN`-list, since the predicate is a hardcoded SQL literal rather than derived from `registry.singleton_channel_types()` at runtime.

**Four policy columns** (added by `458913091bd5`, on `ServerChannelBase` so create/update/read all carry them), the admin-owned defaults `ChannelPolicyService` resolves per user:

| Column | Type | Default | Meaning |
|---|---|---|---|
| `visibility` | `varchar(32)` | `"public"` | `"public"` = every user; anything else (including `"restricted"` and any unrecognised value) is treated as restricted — the permissive branch is deliberately the narrow one |
| `default_enabled_for_users` | `bool NOT NULL` | `true` | whether a user with no `channel_user_setting` row is switched on |
| `default_agent_scope` | `varchar(32)` | `"all"` | `"all"` / `"list"` / `"none"` inherited by a user with no explicit `agent_scope` |
| `allow_auto_install` | `bool NOT NULL` | `true` | whether routing Pass 2 (catalog auto-install) may run for this channel at all |

Plain `VARCHAR`, not Postgres enums — the same status-string convention `channel_type`, `ChannelThreadBinding.status` and `RoutingDecision.origin` already use: adding a value is a code change, not a migration, and every reader degrades an unrecognised value conservatively (see `ChannelPolicyService`'s module docstring for exactly which direction "conservative" means for each column). Every default reproduces the channel's pre-Phase-2 behaviour exactly, so an existing channel is unchanged by the migration that adds them.

### `channel_user_setting`
One row per `(server_channel_id, user_id)` — a user's explicit overrides for one channel. **Absence is meaningful**: see [Availability and per-user settings](server_channels.md#availability-and-per-user-settings) and the model's own module docstring, which is the canonical statement of the rule.

- `server_channel_id` — FK `server_channel.id`, `ON DELETE CASCADE`
- `user_id` — FK `user.id`, `ON DELETE CASCADE`, indexed
- `is_enabled` — `bool`, **nullable, no server default**. `NULL` = inherit `default_enabled_for_users`
- `agent_scope` — `varchar(32)`, **nullable, no server default**. `NULL` = inherit `default_agent_scope`; one of `CHANNEL_AGENT_SCOPES` when set
- `pinned_agent_id` — FK `agent.id`, `ON DELETE SET NULL` — deleting the pinned agent un-pins the channel rather than deleting the whole settings row (which would also discard `allow_identity_routing`)
- `allow_identity_routing` — `bool NOT NULL DEFAULT false`. The one field on this table that is **not** nullable-meaning-inherit — see below
- `created_at`, `updated_at` — naive `TIMESTAMP` (this codebase's convention for this feature; see the migration's own note)
- Unique constraint `(server_channel_id, user_id)`, which is also what makes the write path's upsert an upsert

`is_enabled` and `agent_scope` being nullable-with-no-server-default is not an oversight to "tidy": a server default would silently convert every future row into a frozen explicit choice. `allow_identity_routing` is the deliberate exception — `NOT NULL DEFAULT false`, and it **never inherits** (master plan §3.4 of the channels & identity unification refactor): an admin default must not be able to turn on something that routes a message into another person's workspace.

**Read the direction carefully; it is the easiest thing here to get backwards.** `allow_identity_routing` is the **sender's own** consent, resolved from the *sender's* row: "I accept that a message I send on this channel may be routed into somebody else's workspace, where they can read it." It is not the receiver's gate. Nor is `IdentityBindingAssignment.is_enabled`, which points the same way at a finer granularity — it is the **caller's** per-person opt-out of *reaching* an owner (the row is keyed by `target_user_id`, and `IdentityService.toggle_identity_contact` filters on `target_user_id == current_user.id`). The *receiving* person's controls are `IdentityAgentBinding.is_active` and `IdentityBindingAssignment.is_active`, both edited from the identity-sharing screens. Resolving `allow_identity_routing` from the receiver's row instead would be a real security change wearing the clothes of a comment cleanup — do not "fix" it in that direction.

Read on every message since Phase 3: `ChannelRoutingService` gates the identity half of the Pass-1 ballot on it, and `ChannelInboundService._ingest` re-checks it before ingesting any message on an already-bound identity thread. A change to it (a transition only) writes a `SERVER_CHANNEL_IDENTITY_ROUTING_CHANGED` `SecurityEvent` at severity `medium` via `UserChannelService._audit_identity_routing` — best-effort, and it rolls back its own failed write so a failed audit cannot raise `PendingRollbackError` out of the request it was written never to fail.

### `channel_user_agent`
The per-user agent list for one channel, consulted only when the *resolved* `agent_scope` is `"list"`. Rows may exist while the resolved scope is `"all"` or `"none"` — the previous selection is kept so toggling the scope back does not silently discard it.

- `channel_user_setting_id` — FK `channel_user_setting.id`, `ON DELETE CASCADE`
- `agent_id` — FK `agent.id`, `ON DELETE CASCADE`, indexed
- Unique constraint `(channel_user_setting_id, agent_id)`

### `server_channel_user_grant`
The per-user allowlist for a `visibility="restricted"` channel. Consulted **only** when visibility is not `"public"` — a public channel needs no rows here and never gets any; their absence on a public channel means "the question was not asked," not "nobody is allowed."

- `server_channel_id` — FK `server_channel.id`, `ON DELETE CASCADE`
- `user_id` — FK `user.id`, `ON DELETE CASCADE`, indexed
- `granted_by` — FK `user.id`, `ON DELETE SET NULL` — deleting the admin who issued a grant must not silently revoke access for everyone they granted (same choice as `ServerChannel.created_by`)
- `created_at`
- Unique constraint `(server_channel_id, user_id)`

A grant is **access**, not enablement — being granted does not switch the channel on for the user; that is `channel_user_setting.is_enabled` resolved against `default_enabled_for_users`. Both are resolved together in `ChannelPolicyService`.

### `server_auto_install_bundle`
Server-wide (not per-channel) auto-install candidate list. `bundle_uuid` (FK `agent_bundle.id`, `ON DELETE CASCADE`, unique — one row per bundle), `added_by` (FK `user.id`, `ON DELETE SET NULL`).

### `channel_thread_binding`
The feature's conversation state. `server_channel_id` (FK `server_channel.id`, `ON DELETE CASCADE`), `thread_key` (channel-native thread id, e.g. `spaces/AAA/threads/BBB`; unique together with `server_channel_id` — this is the race guard for two first-messages in one new thread), `user_id` (FK `user.id`, `ON DELETE CASCADE`, indexed), `agent_id` (FK `agent.id`, `ON DELETE CASCADE` — uninstalling the agent cascades the binding away), `session_id` (FK `session.id`, `ON DELETE SET NULL`, indexed, nullable — null before first activation and after the session is deleted), `status` (`pending_install` / `active` / `failed`), `pending_messages` (JSON list of `{text, external_message_id, external_user_id, received_at}`, capped at 20 entries — mutate via reassignment + `flag_modified`, never in-place `.append()`), `last_external_message_id` (webhook redelivery dedup), `status_message_id` (nullable — the thread's live **status notice**: the single progress message the pipeline rewrites in place, and whose last rewrite is the agent's own reply. Released the moment the reply takes the slot, which is load-bearing rather than tidy: a retained id would let the next turn's "working on your message…" be patched straight over the previous answer. NULL between turns, and permanently NULL for any transport without `supports_status_notice`. Since the streaming relay it is also released **mid-turn**, at every seal — a sealed message is final, and the next draft is a fresh post — so on a long answer this column is repointed several times within one turn; it remains the only persisted pointer that feature needs, which is why it adds no migration), `last_error` (Text, nullable).

**`user_id` is the *sender*, never the session's owner.** Since Phase 3 of the channels & identity unification an identity-routed thread has `binding.user_id` = the sender while `session.user_id` = the identity owner, so `binding.agent_id` names an agent the binding's own user does not own. Any consumer that reads `binding.user_id` as "the session's owner" is wrong; `_handle_lost_race` and `_continue_thread` are the two places such an assumption would hide, and both compare it against the *sender* only.

### `channel_turn_delivery`

**One row per external message a channel turn wrote** — the durable half of a mechanism whose live half (`ChannelStreamRelay`) is deliberately in-memory. Added by migration `1367eb81ac66`. `binding_id` (FK `channel_thread_binding.id`, `ON DELETE CASCADE`, indexed — a thread whose binding is gone has no ledger worth keeping), `session_message_id` (FK **`message.id`**, which is what `SessionMessage`'s table is called, `ON DELETE CASCADE`, indexed, **nullable — see below**), `part_index` (int, order of this message within the turn), `role` (`draft` / `sealed` / `final`), `external_message_id` (varchar 255, nullable — the transport's own name for the message, opaque and never interpreted; `NULL` is an honest "delivered, message unknown" rather than a fabricated id), `visible_char_end` (int, nullable) + `content_sha256` (varchar 64, nullable — the two halves of the divergence check), `status` (`delivered` / `failed` / `diverged`), `created_at` / `updated_at`. Unique constraint `uq_channel_turn_delivery_part` on `(session_message_id, part_index)`.

**`session_message_id` is nullable, and that is the feature's one schema deviation from its plan.** It is forced by *when* turn identity becomes knowable: the relay seals mid-stream holding only `session_id` / `binding_id` / `channel_id`, and the id of the agent message the batch is writing is handed over only by the terminal stream event, at the *end* of the batch. Every alternative required the relay to **infer** which row it was writing ("the newest agent message in this session", "the one whose metadata says it is streaming") — the exact inference this whole feature exists to delete. So a boundary write records what it honestly knows and leaves attribution `NULL`, and `handle_stream_completed` **adopts** the pending rows once the emitter has named an id. Every attributed id in this table therefore came from an emitter, never from a lookup. Two consequences: the unique constraint is unenforced while a row is pending (Postgres treats `NULL`s as distinct) and enforced from adoption on, which is when `part_index` becomes meaningful; and a turn that seals and is then interrupted would leave its rows pending for the *next* completion to adopt, which is what the close-out described below exists to prevent.

No changes to any other pre-existing table.

## API Endpoints

All routes in `backend/app/api/routes/server_channels.py`, `tags=["server-channels"]`.

### Public (no auth dependency)
- `POST /api/v1/channels/{webhook_token}/inbound` — the one unauthenticated ingress on the platform. Rate-limited (`SERVER_CHANNEL_WEBHOOK_RATE_LIMIT_PER_MIN` per token) and body-size-capped (`SERVER_CHANNEL_WEBHOOK_MAX_BODY_BYTES`) before the token is even resolved. Returns the adapter's sync-response body (`{}` for most outcomes; Google Chat renders `{"text": ...}` in-thread). 404 for an unknown *or* disabled token / an adapter no longer in the registry; 403 for a failed `verify_inbound`.

### Admin (`get_current_active_superuser`, all)
- `GET /admin/server-channels/channel-types` → `list[ChannelTypePublic]` — registered adapters, for the type picker
- `GET /admin/server-channels/auto-install-list` / `POST .../auto-install-list` (`AutoInstallBundleAdd`) / `DELETE .../auto-install-list/{bundle_uuid}` — declared **before** `/{channel_id}` routes so the literal path wins FastAPI matching
- `GET /admin/server-channels` → `list[ServerChannelPublic]`
- `POST /admin/server-channels` (`ServerChannelCreate`) → `ServerChannelPublic`
- `PUT /admin/server-channels/{channel_id}` (`ServerChannelUpdate`) → `ServerChannelPublic`
- `DELETE /admin/server-channels/{channel_id}` → 204 (bindings cascade)
- `GET /admin/server-channels/{channel_id}/setup-instructions` → `ChannelSetupInstructions`
- `GET /admin/server-channels/{channel_id}/grants` → `list[ChannelGrantPublic]` — the saved allowlist. Returned for public channels too (inert while public, but the round-trip must not lose the list on a visibility toggle)
- `PUT /admin/server-channels/{channel_id}/grants` (`ChannelGrantsUpdate`) → `list[ChannelGrantPublic]` — **replaces the whole grant set**, not a delta: the admin UI edits a picker whose state *is* the complete list, and a delta API against a multi-admin form would silently lose a concurrent revocation. Audited as `SERVER_CHANNEL_UPDATED` with `action="grants_replaced"` and the resulting membership (not the request — an id the service could not resolve was never granted, and auditing the request would claim otherwise)
- Debug-panel and recent-sender routes — see [Channel Debug Monitor tech](channel_debug_monitor_tech.md)
- `POST /admin/server-channels/{channel_id}/test-outbound` (`ChannelTestOutboundRequest`) → `ChannelTestOutboundResult` — always 200; failure travels in `success=false` + `error`, mirroring the mail-server "test connection" pattern, since this endpoint's whole job is surfacing the failure reason

Every admin mutation writes a `SecurityEvent` (`_audit` helper in the route file); update's audit `details` carry field *names* only, never values (the write path can include the secret).

### User-facing (`CurrentUser`, ordinary auth) — `backend/app/api/routes/user_channels.py`

Everything here is scoped to `current_user` by construction — no route takes a user id, so there is no parameter that could be pointed at somebody else's settings. This router must never return `ServerChannelPublic` (the admin projection, which carries `webhook_token`, `config`, `email_whitelist`); every response is `UserChannelPublic`, a separate, deliberately narrower model — see [Availability and per-user settings](server_channels.md#availability-and-per-user-settings) for why a field exclusion on the admin model was rejected in favour of a second model entirely.

- `GET /users/me/channels` → `list[UserChannelPublic]` — every channel the caller may use (channel enabled AND access — **not** the caller's own toggle, so a channel the user switched off for themselves still appears, or they could never switch it back on), each with its fully resolved policy plus provenance flags (`*_inherited`) so the UI can render "following the admin default (on)" without a second request or a second copy of the inherit rules
- `PUT /users/me/channels/{channel_id}` (`UserChannelUpdate`) → `UserChannelPublic` — upsert the caller's settings row; **the only place one is created**. Field semantics follow `model_dump(exclude_unset=True)`: an **omitted** field is left unchanged, an explicit **`null`** clears it (for `is_enabled` / `agent_scope`, "clear" means *revert to the channel default*), and a **value** is stored as the caller's explicit choice. `allow_identity_routing` has no inherited state, so an explicit `null` for it is a 422, not a silent no-op. 404 for a channel the caller may not use, identical to a channel that does not exist
- `DELETE /users/me/channels/{channel_id}` → `UserChannelPublic` — discard the caller's row, reverting to pure inheritance; the only way back to "follow the admin default" once a value has been written. A no-op (not an error) when there is no row, since that is already the end state

## Services & Key Methods

### `ServerChannelService` (`server_channel_service.py`)
- `get_by_webhook_token(session, token)` — **enabled-only** lookup; this is what makes a disabled channel 404 identically to an unknown token
- `create_channel` / `update_channel` / `delete_channel` — `update_channel` pops non-column fields (`secrets`, `regenerate_webhook_token`) before the generic `sqlmodel_update`, only overwrites `encrypted_secrets` when a non-empty `secrets` value is supplied, and invalidates the adapter's cached outbound token on secret rotation
- `webhook_url(channel)` — built from `settings.webhook_base_url` (an alias of `settings.backend_base_url`; see Configuration), never from the inbound request, so the URL shown to an admin is correct regardless of which host they hit the admin UI from
- `list_recent_senders` / `resolve_test_thread_key` — test-send targeting; see [Channel Debug Monitor tech](channel_debug_monitor_tech.md)
- `list_auto_install_bundles` / `add_auto_install_bundle` / `remove_auto_install_bundle` — the joined `AutoInstallBundlePublic` projection resolves `has_trigger_prompt` from each bundle's latest revision in one batched query

### `ChannelPolicyService` and `ResolvedChannelPolicy` (`channel_policy_service.py`)

**The sole place the admin-default / per-user-override inherit rules are resolved.** Nothing else may re-derive them — not the router, not the API projections, not the frontend. Two implementations of an inheritance rule do not stay equal.

- `ChannelPolicyService.resolve(db, channel, user_id) -> ResolvedChannelPolicy` — the narrow, routing-facing form. Delegates to `describe` and returns just `.policy`, so a routing consumer cannot accidentally read a UI-hint field.
- `ChannelPolicyService.describe(db, channel, user_id) -> ChannelPolicyView` — the full resolution, computing the provenance of every inheritable field alongside the policy itself. `is_available` is a conjunction with four possible failure causes ("admin hasn't enabled the channel," "you weren't granted it," "you switched it off," or "nothing's wrong") and a UI that can only show the conjunction's answer cannot tell the user which one applies — `ChannelPolicyView` reports every term separately for exactly that reason.
- `ChannelPolicyService.can_access(db, channel, user_id) -> bool` — terms 1–2 only (channel enabled + access), deliberately excluding the user's own toggle. This is the predicate the user-facing list/address routes use: someone who switched a channel off for themselves must still see and be able to `PUT` it, or they can never switch it back on.
- `_owned_pin(db, pinned_agent_id, user_id)` — re-checks that a stored `pinned_agent_id` still names an agent this user owns. **Load-bearing and non-obvious:** the FK on `channel_user_setting.pinned_agent_id` enforces existence, never ownership, and it survives the agent changing hands — so this re-check at resolution time is what stops a stale pin from routing a channel message into somebody else's workspace. `ChannelRoutingService._route_pinned_agent` re-checks ownership again on top of this, since a pin is data on a settings row rather than a `WHERE owner_id = :user_id` query result, and is one hop further from where the property is established.

**Resolution order for `is_available`** — the conjunction, checked in this order (`ChannelPolicyService.describe`):

1. `channel.enabled` — the admin kill switch, absolute.
2. `visibility == "public"` **or** a `server_channel_user_grant` row exists (public channels skip the grant lookup entirely — see the `server_channel_user_grant` schema note above).
3. `setting.is_enabled` if that row exists and the field is non-`NULL`, else `channel.default_enabled_for_users`.

`ResolvedChannelPolicy` is a `@dataclass(frozen=True)` built only from scalars (ids, bools, a `str`, a `frozenset[uuid.UUID] | None`) — **and this is load-bearing, not a style choice.** It crosses into `ChannelRoutingService.decide`'s worker threads (`anyio.to_thread.run_sync`), which open and close their own short-lived sessions. An ORM row handed across that boundary would turn the caller's next attribute read into a lazy reload against a session that is already closed — exactly the hazard `tests/architecture/channel_routing_purity_test.py` fact #4 ("`decide` returns plain data") exists to catch; that test's allowlist of plain-data types covers `ResolvedChannelPolicy` and every field on it. `ResolvedChannelPolicy.for_no_channel()` is the one escape hatch — an unrestricted-except-identity policy for the one caller shape that runs outside any channel (`POST /admin/routing/simulate` with no `channel_id`); it must never be reached for on a path that *does* have a channel.

Unknown stored values for `visibility` and `agent_scope` (plain `VARCHAR`, not enums) degrade **conservatively**, and both directions are written as the narrow branch being the permissive one: only literal `"public"` skips the grant check (anything else is restricted), and only `"all"` / `"list"` mean what they say (anything else, including `"none"` and an unrecognised string, resolves to `"none"`). Degrading agent scope to `"none"` rather than `"all"` is deliberate — it is the *visible* failure, since every owned agent then lands in the routing trace as a skip with a reason, where degrading to `"all"` would be an over-broad ballot that silently looked like it worked.

### `UserChannelService` (`user_channel_service.py`)

The read/write half behind `/users/me/channels`. The read side holds **no** inheritance logic of its own — it is a thin projection over `ChannelPolicyService.describe`. The write side (`upsert_settings`) is the **only** place in the codebase allowed to create a `channel_user_setting` row; every read path treats a missing row as "the channel default applies," and a read path that materializes one would be a bug, not an optimisation (see the model's own docstring).

- `list_for_user` / `to_public` / `get_accessible_channel` — reads, all built on `ChannelPolicyService`
- `upsert_settings` — the write path. Uses `INSERT ... ON CONFLICT DO UPDATE` (`pg_insert(...).on_conflict_do_update(...)`) rather than insert-then-retry, so two simultaneous first-edits of the same user's row (a double-clicked Save) cannot race into a unique-constraint violation on `(server_channel_id, user_id)` — one statement, one row, nothing to catch. An empty `PUT` body against a caller with no row is a no-op rather than materializing an all-NULL row, so `has_settings` does not flip to `True` for someone who changed nothing
- `delete_settings` — drops the row (a no-op if none exists), returning the caller to pure inheritance in one statement (the agent list cascades away with it)

### `ChannelDebugBuffer` (`channel_debug_buffer.py`)

In-memory, process-local capture of recent channel traffic, feeding the admin debug panel — the buffer itself is never persisted; it dies with the process. That is no longer the whole story for message text at the feature level: the [Auto Routing Tuning](../routing_tuning/routing_tuning_tech.md) feature durably persists a `routing_decision` row per routed message (clamped, TTL'd, superuser-only), and each debug-buffer event links to it via `detail.trace_id` when one was written. `ROUTING_TRACE_STORE_MESSAGE_TEXT` gates that persisted row's exposure of sender text by allowlist rather than by naming the fields that carry it: with it off, the stored/served `stages` payload is projected down to fields explicitly declared free of the sender's words (on both the write path and the read path, from one shared definition), so a field not yet vouched for is withheld by default — including one added after the gate was written — rather than exposed by default until someone remembers to add it to a list. A couple of candidate fields are deliberately admitted despite the gate because they are the *agent owner's* configuration rather than sender-derived. The gate hides, it does not erase: rows keep their data until `ROUTING_TRACE_RETENTION_DAYS` expires them or an admin clears the traces. Documented separately: [Channel Debug Monitor](channel_debug_monitor.md) / [tech](channel_debug_monitor_tech.md).

### `ChannelRoutingService` (`channel_routing_service.py`)

Both routing passes live here, not on `ChannelInboundService` — [Auto Routing Tuning](../routing_tuning/routing_tuning_tech.md)'s Phase 3 split the *decision* away from its *effects* so that `POST /admin/routing/simulate` could reuse the real routing code without a `simulate=True` flag threaded through the pipeline. The guarantee is structural rather than conditional: simulate cannot bind, install or reply because nothing reachable from `decide()` can. `tests/architecture/channel_routing_purity_test.py` fails if an effectful import appears in this module.

- `decide(*, user_id, text, policy, include_catalog=True, origin, channel_id, thread_key, actor_user_id)` — the entry point, and the whole public surface for "which agent or bundle should this message go to". `policy` (a `ResolvedChannelPolicy`) is **required and arrives as a value** — it is never looked up here, since importing `ChannelPolicyService` into this module would put a database resolution on the far side of the boundary whose whole guarantee is that it holds no caller session. `decide` does **not** re-check `policy.is_available` — that is the inbound pipeline's gate, already applied in `ChannelInboundService.handle_inbound` before routing is ever scheduled, and `decide` has no vocabulary for "declined" (only an agent id, a bundle id, or neither). Returns a plain-data `RoutingDecisionResult` (ids and trace recorders, never ORM instances bound to a session that is already closed). Takes no `Session`: it cannot touch a transaction the caller is holding. Pass 2 runs only when Pass 1 found nothing **and** `_catalog_may_run(policy, include_catalog=...)` allows it — see below
- `_catalog_may_run(policy, *, include_catalog)` — the conjunction of four independent switches that must all hold for Pass 2 to run at all: the caller's own `include_catalog` toggle (simulate only — always `True` on the real path), `policy.allow_auto_install`, `policy.agent_scope == "all"` (**a decided product semantic, not `allow_auto_install` re-read** — see [Availability and per-user settings](server_channels.md#availability-and-per-user-settings)), and `policy.pinned_agent_id is None`. Read in two places that must not disagree: here, and inside Pass 1's `only_one` short-circuit, which must not skip the classifier believing the catalog is live when `decide` is about to treat it as barred
- `_route_installed` (Pass 1) — answers a pin first, before anything else runs (see `_route_pinned_agent` below); otherwise builds candidates via `ChannelCandidateProvider.build(db, user.id, policy=policy)` (`select(Agent).where(Agent.owner_id == user_id)`, narrowed to the resolved `agent_scope`; eligible = in scope AND (non-blank `router_trigger_prompt` or non-empty `example_prompts`), else recorded as a `SKIP_NOT_IN_CHANNEL_SCOPE` or `SKIP_NO_TRIGGER_PROMPT` skip, scope checked first), then either short-circuits to the sole eligible candidate (`match_method="only_one"`, only when `_catalog_ballot` shows Pass 2 has nothing to offer) or calls `AgentClassifier.classify` directly. No `AppMCPRoutingService` / `AppAgentRouteService` import anywhere in this module or `channel_candidate_provider.py` — enforced by `tests/architecture/channel_routing_scope_test.py` (AST-based, fails on the import). The `agent.owner_id != user.id` guard is kept as an unreachable-by-construction postcondition assertion.
- `_route_pinned_agent(db, user, pinned_agent_id)` — the sender pinned an agent to this channel; use it and ask nothing. Runs before the candidate provider, before `only_one`, and before Pass 2 — a pin has already answered the question those exist to ask, and installing a bundle over an explicit pin would be the router overruling the person it routes for. Records `match_method="pinned"` (`routing_trace.MATCH_PINNED`) and a full candidate/outcome trace row even though no classifier ran — "a routing decision that leaves no trace" is a defect class this codebase has already had to fix once. Re-checks ownership even though `ChannelPolicyService._owned_pin` already did (see above) — this hands an external sender a session inside a workspace, and the id here came in as data on a settings row rather than a query result, one hop further from where the property is established
- `_route_catalog` (Pass 2) — builds the candidate list from `ServerAutoInstallBundle`, filtering on: not already installed by this user, `CatalogService.user_can_install(db, bundle, user)`, and a non-empty `router_trigger_prompt` on the latest revision; classifies via `AgentClassifier.classify` directly (not `AIFunctionsService.route_to_agent` — routing_tuning's Phase 5 collapsed all four routing consumers onto one classifier)
- `_route_identity(db, user, owner_id, *, message)` (identity Stage 2 dispatch) — reached when the winning `ref_id` parses as `identity:{owner_id}`, from either the classifier branch or the `only_one` short-circuit (a sender who owns no agents and can reach exactly one identity owner is not a rare shape). Opens the `identity_stage2` trace stage via `stage_scope` (not `begin_stage`, so post-return Pass-1 rejections are not misfiled under it), calls `IdentityRoutingService.route_within_identity`, and always returns an `IdentitySelection` — `grant is None` means *Stage 2 ran and selected nothing*, which is what bars Pass 2 without collapsing into "identity was never involved". Total, like Pass 1's own catch-all: an LLM outage here is recorded and declines rather than 500-ing an externally triggerable webhook. Its postcondition (`agent.owner_id == owner_id`) is the identity twin of the ownership guard, unreachable by construction and kept anyway
- `run_in_thread` / `_route_installed_in_thread` / `_route_catalog_in_thread` — offload both passes' blocking LLM HTTP calls via `anyio.to_thread.run_sync`; the thread targets open their **own** DB session and return plain ids, never closing over the caller's session (a cancelled task can't interrupt a running thread). `run_in_thread` is deliberately public: `channel_inbound_service` and `routing_tuning_service` both call it for their trace writes

**`RoutingDecisionResult.identity_grant`** — the one field Phase 3 added, an `IdentityGrant` (a frozen dataclass of three UUIDs: owner, binding, assignment). Set only when Stage 1 picked a person **and** Stage 2 selected one of their agents, in which case `agent_id` names an agent the sender does **not** own and this grant is the only thing that permits a session on it. It is a *claim*, never a conclusion: `ChannelIngestionService.assert_access` re-reads all six conditions behind it (`IdentityService.verify_identity_access`) before anything is created, because the decision and the session are separated by a worker-thread hop and possibly an auto-install wait. It was added to `tests/architecture/channel_routing_purity_test.py`'s plain-data allowlist deliberately, in the same change — that test pins every field on `RoutingDecisionResult` against an explicit type list, and the correct response to it failing on a new field is to extend the allowlist, never to loosen the assertion.

**Trace vocabulary added by this phase**, all in `app/services/routing/routing_trace.py`: `SKIP_NOT_IN_CHANNEL_SCOPE` (an owned agent excluded by the resolved `agent_scope` — checked, and reported, before `SKIP_NO_TRIGGER_PROMPT`) and `MATCH_PINNED` (`match_method` for a pinned decision). Three `stage.reason` notes explain a Pass-2 stage that carries no candidate rows without it reading as "an empty catalog": `PASS_2_NOT_ALLOWED_NOTE` (`allow_auto_install=False`), `PASS_2_SCOPE_RESTRICTED_NOTE` (`agent_scope` is `"list"` or `"none"`), and `PASS_2_PINNED_NOTE` (the sender pinned an agent). All three are written under the `pass_2` stage from inside Pass 1's capture — by the time `decide` applies the gate, Pass 1's recorder is the only one still open, since Pass 2 never opens one of its own when it does not run.

### `ChannelInboundService` (`channel_inbound_service.py`)
- `handle_inbound(db, webhook_token, request, body)` — the entry point; steps 1–6 (channel resolve, verify, dedup, whitelist, user resolution, **channel policy**) run inline and cheap; everything from binding dispatch onward for a **new thread** is scheduled as a background task (`_route_new_thread`) so the webhook can ack immediately — most channels retry a non-2xx response forever, so a slow synchronous reply is treated as a correctness risk, not just a latency one. On a transport with `supports_status_notice` **and** outbound credentials configured (`_status_notice_supported(channel) and _outbound_credentials_configured(channel)`, the latter delegating to `ServerChannelService.has_outbound_credentials`) an **accepted** new-thread message acks with an empty body `{}` and the background task posts the "finding an assistant…" notice through the API instead. That is not a nicety: Chat creates the synchronous message but never returns its id, so a notice answered inline can be neither rewritten nor removed. A channel that declares `supports_status_notice` but has no outbound credential configured keeps the old `build_sync_response(REPLY_WORKING, thread_key)` sync ack instead — the notice provably cannot be posted, and answering with nothing would be strictly worse than the old synchronous reply. **Declines stay synchronous** regardless, which is what lets a channel refuse a sender before its outbound credentials exist
- **Step 6 — channel policy — gates every path below it, not only new threads.** `ChannelPolicyService.describe(db, channel, user.id)` is resolved once, immediately after user resolution; if `not policy.is_available` the sender is declined with `REPLY_DENIED` — the exact same reply and status the whitelist-miss branch uses, on an already-bound `active` thread exactly as on a brand-new one. The resolved `.policy` (plain data) is what gets carried into `_route_new_thread` and `ChannelRoutingService.decide`; nothing re-resolves it downstream, so the decline gate and the routing decision are always answering from the same reading of the sender's settings. The debug feed (superuser-only) records which of the three conjunction terms failed via `policy_view`; the sender-facing reply never does — see Security below
- `_route_new_thread` — the background task: calls `ChannelRoutingService.decide(...)`, then acts on the answer (bind, install, ingest, reply). Routing itself is not implemented here; see `ChannelRoutingService` above
- `_upsert_binding` — the race guard: inserts, and on `IntegrityError` (the unique `(server_channel_id, thread_key)` constraint) rolls back and re-reads the winner's row, returning `(binding, created=False)`
- `_handle_lost_race` / the synchronous ownership check in `handle_inbound` — both branches (an *already-bound* thread receiving a message from a different sender, and a *newly-bound* thread where this caller lost the creation race to someone else) independently re-verify `binding.user_id == sender_user_id` before doing anything with the message. Unchanged by identity: these compare the binding's user against the **sender**, never against `session.user_id`, which on an identity thread is a different person by design
- `flush_pending_bindings(db)` — scheduler/test entry point; iterates all `pending_install` bindings, each in its own try/except; delegates per-row to `_flush_one`
- `_flush_one` — the `critical_state` divergence lives here: `status in {"error", "deprecated"}` fails the binding, `critical_state` does not (falls through to "still waiting"); a binding stuck for more than `_PENDING_MAX_AGE_SECONDS` (30 min) fails regardless of status, so a wedged build doesn't wait forever
- `_ingest` — the actual hand-off to `ChannelIngestionService.ingest_inbound_message`, resuming by `binding.session_id` when the row still exists, otherwise creating fresh (stamping `session_metadata_extra` with `server_channel_id`, `thread_key`, `sender_external_id` on first creation only). Enforces `user.id == binding.user_id` at the top of the body rather than merely asserting it in prose — the invariant that keeps `_verify_resume_sender`'s non-identity arm sound. **Identity, since Phase 3:** the grant comes from `decide` on a thread's first message and from `_resume_identity_grant(session)` (rebuilt from the session row's three identity columns) on every later one — rebuilt, not cached, so `assert_access` re-verifies against current state each turn. When a grant is in play the ingest passes `expected_owner_id=grant.owner_id`, stamps `identity_owner_id` (consumed by `_select_session_owner_id`), `identity_caller_id`, `identity_binding_id`, `identity_binding_assignment_id`, and adds `identity_caller_name` to `session_metadata` (the same key the App MCP identity path uses, so the session view needs one branch, not two; `identity_owner_name` is deliberately *not* stamped here — on this path the owner is the session's own user). `integration_type` stays `channel_{channel_type}`. The sender's own consent is re-checked here too: `grant is not None and not policy.allow_identity_routing` raises a bare, detail-free `PermissionError`, which `_ingest_or_fail` turns into the same generic reply every other refusal gets
- `_resume_identity_grant(session)` — `None` for an ordinary channel session (all three columns NULL); otherwise an `IdentityGrant` whose `owner_id` is `session.user_id`, which is not trusted — condition 6 of `verify_identity_access` pins `binding.owner_id == agent.owner_id == owner_id`, so a row whose `user_id` disagrees with its own binding is rejected rather than honoured. A partially-stamped row degrades to "no grant" and is refused by the ordinary invariant rather than completed by guessing
- Two bounded, TTL-swept, process-local in-memory dicts guard against unbounded growth from attacker-supplied keys: `_recent_message_ids` (pre-binding redelivery dedup) and `_recent_security_events` (throttles repeated denial/verification-failure audit writes to one per 5 minutes per key)

### `ChannelOutboundService` (`channel_outbound_service.py`)
- `handle_stream_completed` / `handle_stream_error` / `handle_stream_interrupted` — registered as event-bus subscribers in `app/main.py`; they fire for every stream on the instance, so each starts with a cheap gate — a dict lookup in the streaming relay's registry (which has to come *first*, so a tail is taken outside the DB session — see below), then `session.integration_type.startswith("channel_")`. All three are relay-aware and all three behave byte-for-byte as they did before the relay existed when there is none. `handle_stream_interrupted` is new with the streaming work: `STREAM_INTERRUPTED` is emitted *instead of* `STREAM_COMPLETED` for a stopped turn, so without it an interrupted channel turn left its notice stranded on "working on your message…" until the next turn. See [Streaming status-notice updates and `/stop`](#streaming-status-notice-updates-and-stop) for the tail contract and the five shapes of the interrupted handler
- `AGENT_MESSAGE_ID_META_KEY` / `_MISSING` / `_UNREADABLE` / `_agent_message_uuid` / `_agent_message_text` / `_settle_turn_ledger` / `_close_out_unsettled_ledger` — the consumer half of **turn identity** and the ledger hooks the three subscribers call. `handle_stream_completed` resolves its reply from the agent message the event *names* rather than from the newest agent row in the session; `handle_stream_error` and `handle_stream_interrupted` use the id only as a key, never to read a row. See [Turn identity and the delivery ledger](#turn-identity-and-the-delivery-ledger)
- `set_binding_status_ex(...) -> (bool, str | None)` and `_deliver_ex(...) -> (bool, str | None)` — the two-value forms of `set_binding_status` and `_deliver`, added so a boundary write can record *which* external message it landed in. The `bool`-returning originals are thin wrappers and keep their signatures deliberately: the relay gates its seal advance on `set_binding_status`'s `bool`, and every other delivery call site would immediately discard the second value. The id is the one the adapter reported, so it is the message actually written whichever path that took — the patched notice, or the fresh post a failed patch degraded to — and `None` accompanies every `False` as well as every transport with no progress surface
- `_binding_row_id(binding)` — the total reader for `binding.id`, a third instance of the `_binding_thread_key` / `_binding_status_message_id` hazard. It looks more like a plain field read than either of them, which is exactly why it has a helper: every caller arrives after a `db.commit()`, so it is a lazy reload that raises `ObjectDeletedError` on a concurrently deleted row. `None` means "no ledger for this turn", which every ledger entry point already accepts
- `set_status(*, channel, thread_key, message_id, text) -> str | None` — **session-free** (no `db` parameter — it never had a use for one, and taking it invited callers to hold a pooled connection open across the HTTP call; the persistence half lives in `set_binding_status`). Posts the thread's status notice, or rewrites it in place when `message_id` is given; returns the notice id. **Thread-keyed, not binding-keyed**, because a new thread's first notice is posted while routing runs, which is strictly before there is anything to bind — the id travels as a plain local through `_route_new_thread` (like `policy` and `origin`) until a binding exists. Returns `None` in three cases: the transport has no progress surface at all; the notice went out as an ordinary message (`supports_progress_updates` without `supports_status_notice`); or the post itself failed (`_route_new_thread` logs this third case at WARNING, since on a transport that just acked the webhook in silence it can mean the sender got no acknowledgement whatsoever). A failed patch degrades to a fresh post, never to a lost update. **Total by contract — it never raises.** Three callers depend on that rather than merely benefit from it: `set_binding_status`, `_settle_notice`, and the outer failure handler in `_route_new_thread`, all of which run on paths (a lazy reload on an expired instance, sometimes a poisoned session) where a raise here would strand the sender's notice with no code path left able to touch it
- `set_binding_status(db, channel, binding, text, settle=False)` / `clear_binding_status(db, channel, binding)` / `adopt_status_notice(db, binding, message_id)` — the bound-thread forms, which persist and read `binding.status_message_id`. `settle=True` rewrites the notice one last time and **releases** the id, for text that IS the answer ("nothing matched", "setup failed") — the message then stays. `clear` *deletes*, and is the **exception, not the end of a normal turn**: an agent's reply takes the notice's slot instead (see `_deliver` below). It survives for the two cases with nothing to put there — a stream that completed with no agent message, and the third branch of `_handle_lost_race`, where the loser's notice has no thread state left to narrate. `adopt_status_notice` is the hand-off for a notice posted before the binding existed
- `_deliver(..., into_status_notice=True)` — delivers the agent's reply **into** the open status notice via `adapter.replace_message`, rather than posting below it and clearing. This is the fix for what the delete-based version looked like in practice: Chat renders a deleted message as a *"Message deleted by its author"* tombstone, so clearing the notice after posting the reply put one above every single answer. The notice id is released whenever `adapter.replace_message` reports `replaced=True` on its `ChannelReplaceResult` — **which includes the case where the patch landed but the remaining chunks failed to post.** That reply is truncated, but it is still reported as delivered and the id is still released, deliberately: the alternative is a *complete* reply being silently patched away by the next turn's "working on your message…", which is worse than a truncated one that stays. The id is kept only when the patch itself never landed (delivery raised, or the adapter fell back to an ordinary post) — the notice is then still standing, unchanged, and the next turn can still rewrite or retry it. `handle_stream_completed` and `handle_stream_error` both use it
- `notify_progress` **has been deleted.** Its old job — a transport that can post progress updates but not edit them (`supports_progress_updates` without `supports_status_notice`) — is now handled inside `set_status` itself: the `message_id` branch is skipped and it falls straight through to `_send_notice`, a bare `send_message` that keeps no id and returns `None`. Callers never branch on transport capability either way
- `_binding_status_message_id(binding)` — the total reader for `binding.status_message_id`, the sibling of `_binding_thread_key` and guarded for the same reason (expired instance ⇒ lazy reload ⇒ `ObjectDeletedError` out of what is only bookkeeping). `None` degrades to "post a fresh notice"
- `_record_notice` — files every notice post/patch in the `ChannelDebugBuffer`. The status notice replaced `_reply` on several pipeline paths and `_reply` recorded all of them; without this the admin panel would go blind exactly where the feature got chattier
- `_deliver` — on failure, records `last_error` on the binding via `_record_error`, which refuses to overwrite an existing `failed` binding's diagnosis with a lesser "and we couldn't tell them either"

### `GoogleChatAdapter` (`adapters/google_chat.py`)
- `verify_inbound` — extracts the bearer token, calls `verify_google_signed_jwt(token, audience=project_number, issuers=[chat@system.gserviceaccount.com], certs_url=<Chat JWKS URL>)`; a `GoogleCertsUnavailable` is caught and re-raised as `ChannelVerificationError` (denies, but is logged distinctly from a bad signature); parses `MESSAGE` / `ADDED_TO_SPACE` events, drops everything else (including the bot's own posts, identified via `sender.type != "HUMAN"`) as `event_kind="ignored"` — deliberately acked rather than errored, since Chat retries a non-2xx event forever
- `send_message` — translates the text from CommonMark via `markdown_to_chat`, then chunks the **translated** text at 4096 chars (preferring a newline split point, and closing/reopening a code fence it has to split — an unterminated fence renders the rest of the message as prose and makes the next chunk's closing fence swallow what follows). Mints/caches a `chat.bot`-scope access token per channel via a JWT-bearer grant (implemented with PyJWT rather than adding `google-auth`), retries 3 times with short backoff, gives up with `ChannelSendError` on a non-429 4xx
- `update_message` / `replace_message` / `delete_message` — `spaces.messages.patch` (`updateMask=text`) twice over and `spaces.messages.delete`, all app-auth-restricted by Google to messages this app posted, which is all the pipeline ever asks of them. `update_message` rewrites a *notice* and **truncates** rather than chunking: a patch addresses exactly one message, and spilling into a second would leave a message the caller does not know the id of. `replace_message` is a *delivery* into an existing message — the agent's reply taking the notice's slot — so it does chunk, and it returns a frozen `ChannelReplaceResult(message_id, replaced)` from `adapters/base.py` rather than a bare id: the first chunk replaces the named message and the remainder is posted after it, and a failed **first-chunk** patch falls back to a plain send (`replaced=False`, re-sending the **untranslated** text, since `send_message` translates and a second `markdown_to_chat` pass over Chat markup corrupts it — `*bold*` reads back as Markdown italics). Once the first-chunk patch has landed, `replaced=True` is not negotiable — **even when the remaining chunks then fail to post**: that failure is swallowed and logged at WARNING, and the reply is delivered truncated rather than reported as a failure that would leave the pre-patch `replaced=False` on record and the notice id un-released. `delete_message` treats 404 as success
- `_message_url(external_message_id)` — validates the `spaces/{space}/messages/{id}` shape before building a patch/delete URL and raises `ChannelSendError` otherwise. The only ids the pipeline stores come from `send_message`, so anything else is a caller holding a stale or foreign value; refusing on the string beats spending a round trip on a request that can only 404
- `_post_chunks` / `_patch_text` — the two primitives `send_message`, `replace_message` and `update_message` compose. `_post_chunks` takes **pre-translated, pre-chunked** text so `replace_message` can post the remainder of a body without running the markdown translation a second time over its own output
- Text formatting: `spaces.messages.create` has **no** `markupSyntax` parameter. The `MARKUP_SYNTAX_CHAT` / `MARKUP_SYNTAX_MARKDOWN` enum exists only as a read-side parameter on `spaces.messages.get`, so posted text is always read as Chat's own markup and translating on the way out is the only option — not a stylistic choice
- `get_setup_instructions` — returns the ordered admin checklist and non-secret details (audience, bot scope) shown in `ChannelSetupInstructionsPanel`
- `build_sync_response(text, thread_key=None)` — renders `{"text": ..., "thread": {"name": thread_key}}` from the webhook's own HTTP response, which is what makes a denial reply possible before any outbound credential exists. **The `thread` field is load-bearing:** a Chat app's sync response without it is posted as a new *top-level message in the space*, not into the conversation that triggered it — so the pipeline's first word landed in the room while every later message, posted through `send_message` with an explicit `thread.name`, landed in a thread. `thread_key` is `None` only for the `added_to_space` welcome, which has no thread yet. Text is translated by `markdown_to_chat` here too

### Local testing against a real Google Chat app

Google Chat only posts to a public HTTPS endpoint, so a local backend needs a tunnel:

1. `make webhook-tunnel` — opens a pinggy HTTPS tunnel to `localhost:8000` (leave it running).
2. `make webhook-set-url URL=https://<tunnel-host>` — writes `BACKEND_BASE_URL` into `.env`, recreates the backend container and health-checks the tunnel.
3. Reopen the channel's setup panel in Admin → Server Configuration → Channels and copy the now-tunnelled webhook URL into the Chat API **Connection settings → HTTPS endpoint URL**.
4. `make webhook-clear-url` when finished, to drop back to `FRONTEND_HOST`.

The tunnel host changes on every restart, so steps 2–3 repeat each session — unless `PINGGY_TOKEN` is set in `.env`, in which case the tunnel runs on a paid pinggy account with a stable subdomain and only needs setting up once (set `PINGGY_URL` to that stable URL and step 2 becomes a bare `make webhook-set-url`). `project_number` must be the numeric GCP project number of the Chat app (the JWT audience) — a wrong value rejects every inbound event with a 403 and no other symptom.

## Security

- **Verification is the single authentication chokepoint** (`ChannelAdapter.verify_inbound`) and the pipeline enforces that nothing before it in `handle_inbound` has parsed or trusted the payload. Every value on `ChannelInboundMessage` is attacker-influenced except fields the adapter took from *verified* JWT claims.
- **`GoogleCertsUnavailable` deliberately does not subclass `ValueError`.** `verify_google_signed_jwt` catches `(JoseError, ValueError)` to turn Authlib's bare `ValueError` (an unknown `kid`, an oversized header — both attacker-reachable on the cheapest possible probe) into "invalid token." If `GoogleCertsUnavailable` were a `ValueError`, that same handler would swallow it, and a genuine Google JWKS outage would be misreported as "this signature is invalid" — collapsing exactly the distinction the webhook needs to tell an outage apart from a forgery. This is enforced by a backend test, not just a comment.
- **The hardening was fixed at `_get_google_certs`, not at each call site.** A JWKS response is only cached when it is both a 2xx *and* shaped like a JWKS document (`{"keys": [...]}`) — without both checks, a Google 5xx carrying a JSON error body would be cached for a full hour and reject every verification against it until the cache expired. `verify_google_token` (the pre-existing Google OAuth login path) catches `GoogleCertsUnavailable` and returns `None`, preserving its exact prior external contract; `verify_google_signed_jwt` lets it propagate so the channel webhook can react to "cannot verify" differently from "invalid."
- **Egress guard on every outbound HTTP call** — `assert_url_allowed` wraps both the Chat API send URL and the OAuth token endpoint URL in the adapter, reusing the platform's existing SSRF/egress protection rather than adding a parallel one.
- **Secrets discipline** — `encrypted_secrets` is Fernet-encrypted via the existing `encrypt_field`/`decrypt_field` helpers, is write-only at every layer (no response DTO carries it, `ServerChannelPublic` exposes only `has_outbound_credentials: bool`), and is never logged.
- **`match_email_pattern`** (`services/common/email_patterns.py`) is shared verbatim between the email integration and the channel whitelist: comma-separated `fnmatch` globs, case-insensitive, blank entries ignored, and **fails closed** — an empty or `None` pattern string matches nothing. `"*"` is the only glob that matches everything; because matching is any-token-in-the-list, a whitelist like `"*, ops@corp.com"` is a blanket allow, not a scoped list — both the backend matcher and the frontend's `parseWhitelist` tokenizer treat it identically, so the admin UI's warning can't disagree with the enforced behavior.
- **`SecurityEvent` audit coverage**: channel create/update/delete/token-regenerate (admin actions, un-throttled), verification failure and whitelist denial (throttled to one per 5 minutes per key, since both are attacker-triggerable at will against a valid token), auto-registration, and auto-install. **Channel-policy denials share the whitelist-miss's throttle bucket and `SERVER_CHANNEL_SENDER_DENIED` event type**, distinguished only by `details.reason` (`"not_whitelisted"` vs. `"channel_unavailable"`) — from the outside these are one event, "a verified sender was turned away," and splitting the feed in two would give an admin hunting a denial two places to search. Audit failures never break the request path — every write is wrapped and logged on failure rather than raised.
- **The decline reply is deliberately indistinguishable from a whitelist miss, for every one of the three channel-policy failure causes as well.** `REPLY_DENIED` is returned verbatim whether the sender was never whitelisted, was never granted a restricted channel, is on an admin-disabled channel, or switched the channel off for themselves. A reply that told these apart would let any authenticated (or, on the whitelist side, any internet) caller enumerate a server's channel configuration one probe at a time — the same reasoning behind the webhook's 404-on-unknown-or-disabled rule and `UserChannelService`'s "404 for not-found and not-permitted alike." The full breakdown (`policy_view.channel_enabled` / `.is_granted` / `.is_enabled_for_user` / `.is_enabled_inherited`) is written to the superuser-only debug feed instead — every value there is a plain `bool` off the frozen `ResolvedChannelPolicy`/`ChannelPolicyView`, so nothing in that diagnostic argument list can reach the database (§11a Rule 2).
- **Known audit gap (deferred, not fixed here):** rejection-path events (`_audit`) are attributed to `channel.created_by`. Since that FK is `ON DELETE SET NULL`, deleting the superuser who created a channel silently stops `SecurityEvent` rows being written for that channel's future denials/verification failures — the event still reaches the application log, just not the audited trail.
- **Message-text logging gap — closed.** Pass 1 used to route through `app_agent_router.py` / `app_mcp_routing_service.py`, which logged inbound message text at INFO level — logging that predates this feature and was written for internal App MCP traffic, but through this feature the same code path also carried externally-sourced, non-platform-user text. The Auto Routing Tuning work (Phase 1) downgraded those lines to `debug`; the durable `routing_decision` trace is the intended replacement observability surface (superuser-only, TTL'd — see `docs/plans/auto_routing_tuning_plan.md` §5), not an INFO log line. Since the channel routing scope split, Pass 1 no longer calls into either App MCP module at all — `channel_routing_service.py` and `channel_candidate_provider.py` do their own message-text logging, deliberately at `debug` throughout, for the same reason.

## Inbound File Attachments

Deep-dive for the feature summarized in [business logic — Inbound file attachments](server_channels.md#inbound-file-attachments): a person attaching a file to a Google Chat or email message, and that file reaching the agent's workspace by the same mechanism a web-chat upload uses. No new tables, no migration, no OpenAPI client regeneration.

### File Locations

Already listed above under their normal headings; gathered here for one-stop reference: `adapters/base.py` (transport contract), `adapters/google_chat.py` (Chat parsing + fetch), `adapters/email.py` + `services/email/polling_service.py` (email extraction), `channel_attachment_service.py` (materialization), `services/files/attachment_limits.py` (shared validator), the `uploader_user_id` parameter on `MessageService.prepare_user_message_with_files` / `SessionService.send_session_message` / `ChannelIngestionService.ingest_inbound_message`, the step-6.5 wiring and sender/transcript/debug helpers in `channel_inbound_service.py`, the two architecture tests, and `server_channels_attachments_test.py`.

### Database Schema

**No new tables.** Two existing JSON-typed columns carry the feature's whole persisted state:

- **`channel_thread_binding.pending_messages`** — each parked entry gains one key, `file_ids: list[str]` (UUIDs as strings, since the column is JSON), holding the ids of files already materialized before the message was parked behind an auto-install. May be **absent** on an entry parked before this feature shipped; every reader uses `entry.get("file_ids") or []`, never `entry["file_ids"]`, so an old parked message still drains as a text-only one instead of raising. Ids only, never bytes — the rows they name already exist as `status="temporary"` `FileUpload`s and are reclaimed by the existing 24-hour abandoned-upload GC if the binding never drains.
- **`file_uploads.file_metadata`** — a channel-materialized upload writes a provenance block: `source="server_channel"`, `server_channel_id`, `channel_type`, `thread_key`, `external_message_id`, `attachment_index` (the attachment's position within its message — the fourth term of an idempotency key, described below), `declared_mime_type`, `declared_filename` (both pre-sanitisation, kept for forensics against what the platform actually decided). `origin` stays `"user"` and `status` starts `"temporary"`, exactly like a web upload; `session_id` stays `NULL` (that column is for agent *output* attachments).

**Redelivery idempotency, beyond what the plan specified.** A webhook redelivery is normally caught upstream by `binding.last_external_message_id` dedup (step 3b) before step 6.5 ever runs — but that stamp is deliberately written only after a *successful* ingest, so a redelivery of a message the platform failed to fully process is a legitimate recovery path that **does** reach materialization a second time. `ChannelAttachmentService` guards that case itself: before fetching or storing anything, it looks up `FileUpload` rows already carrying this exact `(server_channel_id, thread_key, external_message_id, attachment_index)` provenance tuple for this sender, and reuses them verbatim — no second fetch, no second disk write, no second row, no second quota charge. A ref with no matching row is materialized normally, so a retry after a partial store finishes the job, and a previously-*skipped* attachment is retried and named again if it still fails. `marked_for_deletion` rows are excluded from reuse, since resurrecting one would hand the agent bytes the garbage collector is already committed to reclaiming.

### API Endpoints

**No new or changed endpoints, and no request/response model changed shape.** This is why `bash scripts/generate-client.sh` / `make gen-client` is not part of this feature's rollout: `ChannelTypePublic` and the channel Zod schemas deliberately do not gain a `supports_inbound_attachments` field, since nothing in the frontend reads it (the admin form has no attachment toggle — see the no-switch decision in [business logic](server_channels.md#inbound-file-attachments)). The only externally visible surface is the existing debug-events endpoint's `detail` payload gaining three keys — see [Channel Debug Monitor tech](channel_debug_monitor_tech.md#attachment-fields).

### Services & Key Methods

- **`ChannelAttachmentService.materialize(*, db, channel, adapter, inbound, owner_id) -> ChannelAttachmentResult`** (`channel_attachment_service.py`) — the single public method. `owner_id` is always the resolved **sender's** id, never the session owner (see Ownership below). Returns `file_ids: list[UUID]`, `skipped: list[SkippedAttachment]` (`filename`, `reason`), and `accepted_filenames` (parallel to `file_ids`, used only to build a filename-derived classification string for an attachment-only message). **Never raises** — a total `try/except` backstop turns any unexpected failure into "every attachment skipped, message still delivered," rather than losing the message. Internals worth knowing:
  - The per-message count cap (`CHANNEL_ATTACHMENT_MAX_PER_MESSAGE`) is enforced **before** any fetch, so an excess attachment costs nothing.
  - Bytes are resolved concurrently under one shared deadline (`anyio.create_task_group` + `move_on_after`, not `fail_after`, so whatever finishes before the deadline is kept) via a private `_resolve_bytes`, with an `anyio.CapacityLimiter` bounding in-flight fetches (`max(1, min(4, aggregate_budget // per_file_ceiling))`, 2 with the defaults) so peak memory stays proportional to the per-message aggregate rather than to the count cap. A ref still queued behind that limiter when the deadline hits is `fetch_budget_exhausted`; one that was actually in flight is `timeout` — deliberately distinct codes, because an operator's next move differs (concurrency caps vs. Google's latency).
  - Disk writes run on a worker thread (`anyio.to_thread.run_sync(FileStorageService.store_file, ...)`) — the coroutine runs on a uvicorn worker's shared event loop, and a blocking write there would stall every other request that worker is serving, not just this one.
  - MIME resolution: a declared type is used only when non-empty and not `application/octet-stream`; otherwise it is re-derived from the sanitised filename's extension via `mimetypes.guess_type`, and an unresolvable type is a rejection (`type_not_allowed`), never a default to octet-stream (which would smuggle an unknown file past whatever verdict the allowlist happens to have for that generic type). The resolved MIME is additionally shape- and length-bounded before it is ever handed to the database, since `file_uploads.mime_type` is `VARCHAR(127)` and a sender-controlled overlong value would otherwise reach `db.commit()` as a truncation error that took down every accepted attachment in the message.
  - A commit failure after some rows were added rolls back, unlinks the newly-written files from disk, and reports only the *new* rows as `storage_error` — a row that was **reused** from an earlier delivery survives the rollback (it was already committed) and stays in the result.
- **`validate_attachment_bytes(...)`** (`services/files/attachment_limits.py`) — the four-limit policy (MIME allowlist → per-file size → per-message aggregate → owner quota, in that order, cheapest-and-most-specific first) shared verbatim by this feature and `AttachmentMaterializationService`. Returns a rejection code or `None`; the MIME allowlist itself is read from `settings.allowed_mime_types` inside the function rather than passed in, so the two callers cannot drift on what "allowed" means.
- **`_compose_inbound_text` / `_attachments_rejected_reply` / `_reason_phrase` / `_describe_skipped`** (`channel_inbound_service.py`) — the sender/transcript-facing half. `_compose_inbound_text` appends a `⚠️ N attachment(s) could not be accepted: …` note to the **stored** message content (not only agent-bound content) whenever anything was skipped, capped at 500 characters. `_reason_phrase` renders a skip code as a plain sentence fragment for a sender, and an unrecognised code renders as a deliberately vague generic phrase rather than leaking the raw token outward — the raw code is reserved for the admin-only debug feed (`_attachment_detail`, see below).
- **`_attachment_classification_text`** — for an attachment-only message (no text at all) that had at least one accepted file, builds a `"(sent 3 files: a.pdf, b.png, c.csv)"` string used **only** as the routing classifier's input on a brand-new thread; the stored message content is not rewritten to contain it. Routing on an empty string would be a coin flip, and filenames are the only signal an attachment-only sender gave.
- **`_attachment_detail(*, accepted, skipped) -> dict[str, str]`** — the admin debug-feed payload; see [Channel Debug Monitor tech](channel_debug_monitor_tech.md#attachment-fields).
- **Threading `file_ids` and `uploader_user_id`.** `file_ids: list[uuid.UUID] | None = None` rides beside `text` through `_continue_thread`, `_route_new_thread`, `_handle_lost_race`, `_ingest_or_fail`, `_ingest`, `_park_message` / `_append_parked`, and `_drain_parked` (reading back with `entry.get("file_ids") or []`, malformed entries dropped individually with a warning rather than failing the whole drain). `_route_new_thread` classifies on a separate `classification_text` parameter, distinct from the `text` handed to ingest — today usually the same value, but the attachment-only case is exactly why they are two parameters rather than one, and the parameter is named for what it is so a future reader does not "simplify" them back together. `uploader_user_id` is computed once, in `_ingest`, as `binding.user_id if file_ids else None` — see Ownership below.

### Security

- **Ordering is the whole security story, and it is asserted, not just documented.** `ChannelAttachmentService.materialize` (step 6.5) runs after rate-limit + body cap (1), adapter verification (3), redelivery dedup (3b), the email whitelist (4), user resolution (5), and channel policy (6) — see the numbered gate list in [business logic](server_channels.md#inbound-file-attachments). `tests/architecture/channel_attachment_materialisation_ordering_test.py` pins the call site's position in `process_inbound` so a future refactor cannot quietly move it earlier.
- **`uploader_user_id` is the feature's one deliberate ownership widening, and its caller set is pinned.** `MessageService.prepare_user_message_with_files`'s file-ownership check becomes `file.user_id != (uploader_user_id or user_id)` — every existing caller passes `None` and is unaffected. The only non-`None` caller on the whole platform is the channel pipeline (`_ingest`), passing `binding.user_id`, a value `_ingest` has already *enforced* equals the message's own sender before this point is ever reached; the authorization that this uploader may write into this session was established upstream by `assert_access`, which re-reads the whole identity grant on every message. This parameter answers *who uploaded these bytes*, never *may they* — and `tests/architecture/channel_attachment_uploader_user_id_test.py` AST-pins the caller set so a second, less careful caller cannot appear quietly.
- **Google Chat outbound fetch is a server-side request on attacker-influenced input**, and is treated accordingly: the fetch URL is always `https://chat.googleapis.com/v1/media/{resourceName}` — a hardcoded prefix, never a URL built from the event — and `resourceName` is shape-validated (must match the Chat media token shape; must not contain `..`, a scheme, or an authority) *before* a request is built, so a malformed handle costs no round trip. `assert_url_allowed()` (the platform's existing egress/SSRF guard) runs on the built URL and again on every redirect hop. Redirects are followed manually (`follow_redirects=False` on the client) up to a bounded count; each hop must be `https` outright (the egress guard's own allowed-scheme list also permits `http`, so this check is the only thing stopping a downgrade), and the channel's bearer token is **retained** only while a hop stays at the exact same scheme+host+port as the previous one, and is **stripped** the instant a hop leaves that origin — via a one-way latch (`send_authorization` only ever moves from `True` to `False`), so a later hop that happens to land back on the original host cannot resurrect a credential already left behind. A `DRIVE_FILE`-sourced attachment is never fetched — the platform holds no Drive credential and no user consent to use one.
- **What is logged, and what is not.** Filenames are sender-supplied text and are treated exactly like message text elsewhere in this feature: named in the (superuser-only, in-memory, process-local) debug feed and in the sender-visible transcript note, never put in a `SecurityEvent`. Attachment **bytes** are never logged. Fetch failures log a coarse reason class and the sanitised filename, never the media URL or its token. The sender-facing skip prose (`_reason_phrase`) deliberately never echoes a raw reason code — an unrecognised code renders as a generic sentence outward, while the admin debug feed gets the exact token, because a raw internal identifier leaking to an external, unauthenticated sender is worse than a vague sentence.
- **A skipped attachment is not subject to the "decline is deliberately indistinguishable" rule** that governs every other refusal in this feature (whitelist miss, channel policy). "Your 40MB video exceeds the 25MB limit" describes the sender's own message and reveals nothing about who else may use the channel, so it is named plainly rather than folded into the generic `REPLY_DENIED`.
- **Email's `cid:` inline-exclusion is a security-adjacent privacy trade, not a bug to "fix" toward completeness.** Excluding a part whose `Content-ID` is referenced by the HTML body keeps ordinary signature logos out of every agent's workspace; the accepted cost is that a genuinely pasted screenshot carrying its own `Content-ID` (some Outlook/Apple Mail flows) is dropped the same way. Not chased with a size heuristic, which would silently drop real small files instead.

See [business logic — Inbound file attachments](server_channels.md#inbound-file-attachments) for the sender-facing behaviour, the no-admin-switch decision and its full reasoning, and the two residual gaps ([Known Limitations](server_channels.md#known-limitations)): the debug-feed wire format has no consumer-side test (no frontend test harness exists in this repo), and a real Google Chat attachment, a real mailbox signature, and webhook ack latency at the maximum attachment count are still owed as manual validation.

## Streaming status-notice updates and `/stop`

Deep-dive for the feature summarized in [business logic — The status notice](server_channels.md#the-status-notice) and [Channel control commands](server_channels.md#channel-control-commands): while an agent streams, the thread's status notice becomes a rolling draft rewritten in place, and a sender can stop the turn from inside the thread. **No migration, no new endpoint, no OpenAPI client regeneration** — `channel_thread_binding.status_message_id` already existed and is the only persisted pointer, and nothing request- or response-shaped changed.

Gated end to end on `capabilities.supports_status_notice`, so **email and App MCP see zero behaviour change**. That is one gate, in `_build_relay`, rather than a condition repeated per call site.

### The three pieces

- **`ChannelStreamRelay`** (`channel_stream_relay.py`) — one per streaming turn. Holds plain ids (`session_id`, `binding_id`, `channel_id`) plus a `get_fresh_db_session` callable and **no ORM instance at all**: `set_binding_status` commits, which expires every instance in its session, so a held row's next attribute read is a lazy reload that can raise on a concurrently deleted binding — the hazard `channel_outbound_service` documents at length (§11a). The relay stays out of its way by re-fetching per flush.
  - `feed(text)` — synchronous and cheap; appends to a parts list (joined lazily, because a turn can feed thousands of small events and `self._raw += text` on a growing string is quadratic) and wakes the flusher. Text is buffered **even after `stop()`**: `_stopped` governs the flusher, never the buffer, and dropping a late feed would lose it invisibly.
  - The flusher is a single background task: first flush immediate, then rate-limited to `CHANNEL_STREAM_UPDATE_INTERVAL_SECONDS`, and it **retires after five idle minutes**. That backstop is not cosmetic — a *cancelled* stream is the one ending that never reaches `stop()` (`CancelledError` is a `BaseException` and slips past the `except Exception` in both the stream processor and `process_pending_messages`), so an unbounded wait would park one task, one buffer and one session factory per cancelled channel turn.
  - `_flush()` — under the relay's lock: seal what must be sealed, then patch the draft via `ChannelOutboundService.set_binding_status`, which is reused wholesale (it patches the current id, posts fresh when there is none — i.e. right after a seal — persists the id, degrades a failed patch to a fresh post, and is total). **The relay adds only debounce and seal decisions on top of the existing three verbs.**
  - `take_tail(*, partial=False)` — under the same lock, returns `(tail_markdown, delivered_anything)` and advances past it. Idempotent: a second call returns `("", …)`, which is what makes a multi-batch turn correct. `partial=True` additionally hides a control tag that was still arriving when the stream stopped — opt-in, because that stricter stripping would cost a *completed* reply a genuine trailing `"<c"`.
  - `stop()` — a **graceful** stop, deliberately not `task.cancel()`: a cancel landing between the adapter call that sealed a slice and the bookkeeping that advances past it would re-deliver that slice in the tail, showing a paragraph twice.
- **`ChannelStreamRegistry`** — module-level `session_id → relay` dict with the bounded eviction pattern `stream_processor._session_locks` uses. **Written only by `maybe_attach_channel_relay`, never popped by a consumer** (`STREAM_COMPLETED` fires once per LLM batch, and the next batch's handler must still find the relay). A consumer may **not** assume the entry it finds is its own turn's — the key is a session and a session outlives a turn; `SessionStreamProcessor` is also built by the App MCP and A2A paths, which attach no relay at all. The discriminator is `ChannelStreamRelay.spent` ("stopped, consumed once, and nothing new since"), and a spent relay is read as **absent**. Eviction keys off `evictable` (`spent`, **or** retired-without-ever-being-stopped, i.e. the cancelled turn) rather than `stopped` or `retired` alone; the class docstring records which weaker discriminators were tried and why a creation timestamp cannot work.
- **`maybe_attach_channel_relay(...)`** — the one seam `MessageService.process_pending_messages` calls. Returns `base_handler` untouched unless all of: the setting is on, `integration_type` carries the `channel_` prefix, `_resolve_channel_session` finds a binding and an enabled channel, and the adapter declares `supports_status_notice`. **Deciding not to attach for a channel session removes any registry entry** — a leftover relay from an earlier turn would be found by the completion handler, asked for its empty tail, and the full-text fallback skipped, so the reader would get nothing. Removing on decline is what makes the fallback reachable, not tidiness. Total: any failure degrades to "no streaming updates this turn".

`ChannelRelayEventHandler` is the relay-side `StreamEventHandler`: `on_event` feeds only `type == "assistant"` events with non-empty string content, `on_complete`/`on_error` stop the relay, `on_stream_starting` is a no-op. **`thinking` is a distinct event type**, carries the model's reasoning, and never reaches a channel message.

`CompositeStreamEventHandler` (`sessions/stream_event_handlers.py`) fans each protocol method out to a **primary** and isolated **passengers**. The asymmetry is the point: the primary is the handler the stream would have had anyway (`WebSocketEventHandler`, whose `on_complete` writes `pending_messages_count` / `interaction_status` back — swallowing its failure would leave a web client on a stale "streaming" state, a regression visible only on exactly the composed sessions this class was added for), so a primary failure propagates; a passenger's is logged and isolated. A primary failure is *held* until the fan-out finishes, so a passenger never loses an event — including text it is the only holder of — because somebody else's Socket.IO emit failed.

### The seal decision (`adapters/chat_text_chunking.py`)

`find_seal_boundary(text, window) -> int | None` answers "where may this draft be cut so the sealed half reads as a finished message": the last paragraph break in the window, else the last line break, never inside a fence, and walked back off a pipe-table split unless backing out surrenders too much (the table starts at offset 0, or the walked-back slice would fall below the `window // 2` floor — two monospace blocks beat a seal that keeps being deferred). `None` means **"not here, not yet"**, never "cut anyway"; the returned offset consumes the boundary newline run, and the remainder is guaranteed non-empty.

Three facts about the relay's use of it that a reader will otherwise get wrong:

- **Everything is decided in raw markdown; translation is only a measurement.** The buffer is the agent's own markdown, the relay sends raw markdown, and `markdown_to_chat` is called *only* to ask how long a slice will be once the reader's client has it. Actual translation happens one layer down, in the adapter, as it does for every other outbound text. Sealing translated text would cut in a space the next message's remainder does not live in.
- **The window is seeded from the draft, not from the target.** Translation expands — a wide pipe table goes from 1862 raw characters to 8445 translated ones — so a draft far past the target can still be shorter than a window of `target` raw characters, and `find_seal_boundary` answers `None` for "the text fits in the window" with the same `None` it uses for "no boundary here". Seeding at the target meant every expanding draft fell through to the forced cut. The window is also widened by exactly what tag-stripping will remove, since the window is a raw-character budget while the seal trigger is measured on visible text.
- **The per-message cap comes from the adapter, not from a constant here.** `capabilities.max_message_chars` (Google Chat: **4096** — `_MAX_MESSAGE_CHARS`, not 2000), with a conservative 4096 fallback for a transport that declares none, and a 96-character margin kept between a sealed slice and that cap because `update_message` truncates rather than chunks and a truncated seal is text the reader never gets.

A sealed slice is **whole or deferred**: `_clamp_draft` (which trims an over-long *draft*, harmlessly — the next flush rewrites it in full and the tail chunks properly at delivery) is unreachable from the seal path by construction, and a unit test drives a seal with it replaced by a raise to keep it that way. The advance past a sealed slice is gated on a **confirmed** send: advancing on a failed one would leave a hole in the middle of the answer with the tail arriving as if nothing were missing — a silent partial reply, strictly worse than the loud total failure the non-streaming path produces.

### Control tags in the streamed text

The stream carries assistant content **raw**: `<webapp_action>` and `<cinna_attach>` are stripped at *finalize*, long after the relay has seen them. Since the settled reply is the relay's own text (see the divergence policy below), the relay strips them itself — importing `_ATTACH_TAG_RE` / `_WEBAPP_ACTION_TAG_RE` from `message_service` rather than owning a second model of them, so a rename breaks loudly. `_visible` removes complete tags exactly as finalize does; `_visible_draft` additionally hides a tag that is still arriving, so the reader does not watch a path type itself out and vanish. `_has_open_tag` is what keeps a *seal* out of a tag body — a cut through multi-line `<webapp_action>` JSON would strand a half in a message that is final, where nothing can ever strip it.

### The interrupted subscriber and the tail contract

`_take_stream_tail(session_id, *, partial=False)` is the one place the three subscribers ask "did the relay narrate this turn, and what is left?", collapsing the relay's three answers into two:

| `take_tail` answers | What it means | What the subscriber does |
|---|---|---|
| `None` | **the relay broke** | full-text path — **this turn's** stored `SessionMessage`, loaded by the id the stream event carries (`_last_agent_message` survives only on the legacy missing-key arm; see [Turn identity and the delivery ledger](#turn-identity-and-the-delivery-ledger)) — *never* `clear_binding_status`: the reply exists in `SessionMessage` and deleting the notice would throw away text the relay merely failed to read |
| `("", False)` | the stream genuinely produced nothing | full-text path too, which degrades to the delete on its own — and it has to go there for a second reason: a late handler can read the **next** turn's relay, which truthfully reports "nothing yet" |
| `("", True)` | everything is already on screen | no-op |

`_take_stream_tail_ex` is the same thing with one extra fact — whether the `None` came from a relay that *broke* rather than from a session that has no relay — because `handle_stream_interrupted` is the one subscriber that must tell those apart: one is met with silence, the other with the stopped marker. It is called **before the DB session is opened**, since `take_tail` waits on the relay's flush lock and that flush needs a pooled connection of its own.

`handle_stream_interrupted` has **no full-text fallback, and that is forced**: `STREAM_INTERRUPTED` is emitted the moment the interrupted event is seen, inside the streaming loop, while `_finalize_agent_message` runs several hundred lines later — and bus handlers are `create_task`'d, so this handler reaches the database inside that window. What it would read is the last ~2-second checkpoint of `_flush_streaming_to_db`, or (since the row is created on the first assistant event) the *previous* turn's completed answer, which is exactly the shape a `/stop` before the agent speaks would produce every time. Every branch therefore works from what is already on the reader's screen. Its five shapes: a tail → `_deliver` with `STOPPED_SUFFIX` under it (via `_deliver`, which chunks — the notice verb truncates); `""` → `STOPPED_NOTICE` on its own below the sealed text; a **broken relay** → silence, because a bare marker settled over a standing draft would replace an answer the reader watched arrive; a healthy relay with nothing, or no relay at all with a notice standing → the marker settled over the spinner; nothing narrating → silence, which is also what holds email at zero change.

### The `/stop` command

`channel_control_commands.py` is a registry (`dict[str, handler]`) plus `match_control_command(text)`, which strips, casefolds, and does an **exact** dict lookup — no prefix matching, no arguments. A second command is one entry and one handler; the pipeline dispatches on the dict.

Interception lives in `ChannelInboundService.process_inbound` at **step 7a**: strictly *after* the thread-ownership decline and *before* the binding-status dispatch, so every gate (rate limit, verification, whitelist, user resolution, channel policy, ownership) has already run. That placement **is** the authorization argument: `interrupt_stream`'s documented contract is "the caller authorizes first", and `binding_user_id == user_id` was just established — which holds on an identity-routed thread too, where the session lives in the owner's workspace but the *conversation* is the sender's.

Four conditions beyond the match itself, each closing a way for the branch to swallow something:

- `not file_ids` and `not attachments.skipped` — a command takes no files, and intercepting a message whose attachments were *refused* would drop the ⚠️ note that is the only place the sender learns so.
- `outbound_configured` — both answers need to send something; intercepting on a channel that cannot reply turns the message into silence. Same bargain the new-thread ack strikes.
- Its own **redelivery dedup**, in a `{channel}:control:{external_message_id}` key namespace separate from the pre-binding one at step 3. This branch commits nothing and stamps no `last_external_message_id`, so without it a Chat retry runs the command twice and the second `/stop` posts "nothing running" directly under the stopped marker — the doubled acknowledgement the silent-success design exists to avoid.

It matches `inbound.text`, not the composed `text`, which can carry the platform's own attachment note. It runs for **`pending_install` and `failed` bindings as well as `active`** ones — not to do anything there, but so the command does not fall through to `_park_message` (where it would be replayed at the agent once the install finished) or to the failed-binding re-routing self-heal (where the literal string `/stop` would be handed to a classifier).

`handle_stop` opens its own session, hoists every row value to a plain local **before** anything that can commit, and:

- **Re-reads identity consent.** The per-message `allow_identity_routing` check lives in `_ingest`, which this path bypasses, so a sender who has since switched identity routing off could otherwise still interrupt a stream in the owner's workspace. Same condition, read from the same two facts. The owner's side (a withdrawn assignment) is deliberately *not* re-verified here: reproducing `assert_access` to gate an interrupt would duplicate the subtlest authorization in the feature for a worst case of one stopped turn on a thread the sender demonstrably owns.
- **Answers `REPLY_NOTHING_TO_STOP`** for no bound session and for `ValueError` from `interrupt_stream` — which is slightly wider than "no active stream" (it also covers a detached session and "Environment not found"), collapsed on purpose: the sender can act on the same thing in each case, and splitting them would start describing the server's internals to an external sender. The distinction survives in the log.
- **Says nothing on success** (the `STREAM_INTERRUPTED` subscriber's settled marker *is* the acknowledgement) **and nothing on an unexpected failure** either — by then the interrupt has already been requested and the marker may land anyway.

Email never reaches any of this, structurally: its `inbound.text` is `format_email_as_message(...)`'s forwarded wrapper, never the sender's bare words, so it cannot equal `/stop` after a strip.

### Streaming settings

Added to `backend/app/core/config.py`:

| Setting | Default | Purpose |

| `CHANNEL_STREAM_UPDATE_INTERVAL_SECONDS` | `3.0` | Minimum seconds between two rewrites of the same draft. **A value `<= 0` means "flush immediately on every event"** — no debounce and, importantly, no sleeping, which is what the tests set so they can observe a patch without waiting on a timer. Conservative by default because Chat's write quota (~60/min) is per **space** |
| `CHANNEL_STREAM_SEAL_TARGET_CHARS` | `3400` | Soft seal threshold, measured on the **translated** draft, comfortably under the 4096 hard cap so the seal has room to prefer a good boundary |

### Why in-memory relay state is not the ephemeral-cache trap

The relay, the stream it tees off, and the bus handlers that consume it share **one process and one task lifetime**. If the process dies the stream dies with it, so no later completion can arrive needing state that no longer exists — the state's lifetime is designed to equal the lifetime of the thing it describes. A draft stranded by a crash is healed by the next turn's "working on your message…" patch of the same `status_message_id`. This is the opposite shape to the plugin-marketplace ephemeral-cache failure, where state was *assumed durable across restarts*.

### The finalize divergence policy

The final tail is the **relay's own accumulated text**, not the stored `SessionMessage` content — decided with the user, not incidental. The two differ after webapp-action stripping and `<cinna_attach>` materialization, and the reader has been watching this one. Phrased as the property to keep: the standing draft is the **best text available**, normally a superset of the row and bounded-lossy against it by one flush interval — `STREAM_INTERRUPTED` is emitted before `_finalize_agent_message`, and mid-stream the message row is only refreshed about every two seconds. Mismatches are logged, never reconciled.

### Three deviations from the plan, adopted after review

The plan file (`docs/plans/google_chat_streaming_updates_plan.md`) is the historical record and still contains the superseded instructions. Where the two disagree, **the code is right**:

1. **The bus handlers do not call `relay.stop()`.** The plan's Phase 3 has `handle_stream_completed` stop the relay; `STREAM_COMPLETED` fires once per *LLM batch*, so that would stream batch 1 live and leave every batch after it silent. `ChannelRelayEventHandler.on_complete` / `on_error` are the sole owners, and they fire once per turn.
2. **`take_tail` returning `None` means "the relay failed" and routes to the full-text path**, never to `clear_binding_status`. The plan reads the empty/absent cases as interchangeable; they are three different instructions and conflating the first two loses an answer that exists (see the table above).
3. **A forced mid-fence seal re-opens with the *same marker run*** the block opened with, not a hardcoded ```` ``` ````. `markdown_to_chat` closes a fenced block only on a fence repeating the opening marker character, so a `~~~` (or four-backtick) block re-opened with three backticks would leave the remainder's own fence unable to close it and render the rest of the answer as one runaway code block.

### Turn identity and the delivery ledger

The relay above answers "what does this turn say" correctly by construction: it is created per turn. This section is about the arm that has no relay — email, App MCP, a relay that declined to attach or broke — and about the bookkeeping that makes both arms auditable afterwards. **Unlike the streaming work above, this one does add a migration** (`1367eb81ac66`, the `channel_turn_delivery` table); it still adds no endpoint and no OpenAPI client regeneration.

**The bug.** `handle_stream_completed` resolved the text to deliver through `_last_agent_message` — the newest `role="agent"` row in the session by `sequence_number`. A session outlives a turn, so that query is not scoped to the turn that just completed: on any turn that wrote no agent row at all it answers with the **previous** turn's answer, and the pipeline delivered it into the thread as though it answered the new question. Email is the worse case rather than an exotic one — it declares `supports_status_notice=False`, so no relay ever attaches there and **every** email reply resolved through that query.

The fix is not a better query. It is for the emitter to state which row its batch wrote, and for the consumer to deliver that row and nothing else.

#### The event-meta contract

`AGENT_MESSAGE_ID_META_KEY` (`"agent_message_id"`, defined in `app/models/events/event.py` — the one module both sides already import — re-exported under the same name by `channel_outbound_service.py`, and passed by the emitters as `**{AGENT_MESSAGE_ID_META_KEY: ...}` at every emission site, so producer and consumer share one symbol and a rename is one edit that cannot fail silently) rides the meta of the terminal stream events: a **stringified UUID**, or an explicit **`None`**. Three states of that key, three different instructions:

| Meta state | What it means | What `handle_stream_completed` does |
|---|---|---|
| key present, uuid string | this batch wrote that agent `SessionMessage` | deliver **that** row's text and nothing else — except a **tool-only** row, whose stored events prove the turn said nothing and whose content is the finalize placeholder: it delivers the compact tool summary instead (see [Tool-only turns](#tool-only-turns-the-compact-summary)). A row that is empty, whitespace-only, or has since been deleted reads as "the turn said nothing" |
| key present, `None` | the batch wrote no agent message at all — a command stream, a batch that never got an assistant event | settle the notice. **Never** fall back to the newest row; that fallback *is* the bug |
| key **absent entirely** | an event emitted by code predating this key — a rolling deploy, a stale fixture | the legacy `_last_agent_message` query, logged at debug. Wrong on a turn that produced nothing, right on the overwhelmingly common turn that produced one, and such an event carries nothing better to be right with |

`meta.get(key)` collapses the last two into one, and they are opposites, so the consumer reads with a `_MISSING` sentinel instead. The middle row rests on a serialization fact that was **verified empirically rather than assumed**: an explicit `None` survives both hops between emitter and consumer — `_emit_activity_event`'s `**extra_meta` splat, and then `EventPublic.model_dump(mode="json")` in `event_service.emit_event` — arriving as a *present key with a null value* rather than being dropped as empty. Had either hop dropped it, every "this turn said nothing" would degrade silently into the legacy arm and the whole fix would be inert on exactly the turns it exists for. `tests/unit/test_stream_turn_identity_meta.py` pins the splat half explicitly, asserting present-and-`None` against absent as a pair so the *distinction* is what is under test; the `model_dump` half is Pydantic's treatment of a plain `dict[str, Any]` field and is not separately pinned — worth knowing before anyone "tidies" empty values out of either hop.

#### Five emission sites, one finalized id

There are **five** places in `sessions/message_service.py` that stamp the key, not four:

1. the command stream's post-action event (`STREAM_COMPLETED` / `STREAM_ERROR` / `STREAM_INTERRUPTED`, whichever the command ended as) — a literal `None`;
2. `STREAM_INTERRUPTED`, emitted from inside the streaming loop;
3. the **mid-stream** `STREAM_ERROR`, also inside the loop;
4. `STREAM_COMPLETED`, after finalize;
5. the outer `STREAM_ERROR` in the generator's own `except`.

**Only `STREAM_COMPLETED` names a *finalized* row.** The two in-loop events fire before `_finalize_agent_message` has run, so what they name is a row **mid-write**:

- `STREAM_INTERRUPTED` names the row created on the first assistant event, whose content is whatever `_flush_streaming_to_db` last checkpointed — a partial, roughly two seconds stale. And its `None` is **not durable**: the finalize that runs after the loop breaks can retroactively create a row, so "this turn wrote nothing" may be false by the time anything reads it.
- The mid-stream `STREAM_ERROR` returns before finalize entirely, so the row it names is never finalized at all.
- The outer `STREAM_ERROR` names whatever the batch had written when it blew up — the finalized row if the exception came after finalize, the mid-stream row if before, `None` if the stream never saw an assistant event — so it is not a guarantee either.

Hence `handle_stream_completed` is the only handler that ever **loads** the row. The other two use the id as a key and nothing more — see the close-out below. A reader that wants "the settled text of this turn" must take it from the completion event, not from whichever terminal event happened to arrive.

`_finalize_agent_message` was changed to **return the id of the row it actually wrote**, and its caller reassigns its local from the return value. That is not tidiness: the function creates a row itself whenever the caller's local is unset or its row has gone, so a caller emitting its stale local would tell a channel consumer "this turn produced no agent message" about a turn that produced one.

#### `_last_agent_message` survives with exactly one caller

The legacy missing-key arm, and only that. Its docstring says so and says why, and the rule is worth repeating here because a second caller is the bug coming back: **it must never again be used for turn attribution.** A session outlives a turn; "the newest agent row" answers a question no caller on this path is asking.

#### `_UNREADABLE`: a failed read is not "nothing to deliver"

`_agent_message_text(db, raw_id)` is total, and gives **three** answers where a naive version gives two:

- a `str` — the text to deliver;
- `None` — **there is nothing to deliver for this turn.** An unparseable id, a row that has since been deleted, a row whose content is empty or whitespace. Three outcomes folded into one because each means the same thing to the caller and each is a fact actually established;
- `_UNREADABLE` (a typed singleton, a class rather than a bare `object()` so the caller keeps its narrowing) — **the read itself raised**, so nothing was established.

The fourth outcome does not fold into the third, and the asymmetry is load-bearing. `None` routes to `clear_binding_status`, which **deletes** the status notice. That is right when the turn genuinely said nothing and catastrophic when the read merely failed: a relay that narrated a partial answer into that notice and then broke leaves the reader's only copy of that text standing there, and a transient `OperationalError` on the row lookup would delete it — for a reply that exists in `SessionMessage` and will never be sent again. So `_UNREADABLE` **returns early and leaves the notice exactly as the relay left it**. It is the same direction the tail contract forbids for `take_tail` returning `None`, for the same reason, and folding it into `None` would have been a regression against the pre-turn-identity code, where such a raise propagated to the handler's outer `except` and left the notice alone.

#### The command-turn decision

A command stream (`/run:*`, dispatched as a `routing="command_stream"` batch by `collect_pending_batches`) writes exactly **one** `SessionMessage`, with `role="system"`, and never an agent row. Its terminal event therefore carries `agent_message_id=None`, stated explicitly at the emission site.

Before this change, a Google Chat sender typing `/run:check` got the *previous* turn's answer rewritten into the notice as though it answered the command. That is fixed by turn identity, **not** by inventing command-output delivery: a command's output stays a web-UI artefact, and the channel-visible result is that the notice is cleared and nothing is posted. Command streams also never attach a relay, so a command turn writes no ledger rows at all. Email cannot originate a command in the first place — its inbound text is `format_email_as_message`'s forwarded wrapper, never the sender's bare words, so it never starts with `/`.

#### Tool-only turns: the compact summary

A batch whose stream held only tool events still writes an agent row — `message_service`'s finalize fallback gives it the literal `"Agent response"` as content. The web UI never shows that placeholder (it renders the stored `streaming_events`, so the reader sees the tool blocks); a channel reader has no event renderer, and used to be sent the placeholder verbatim.

`channel_tool_summary.py` is the channel-side equivalent of the UI's `ToolCallBlock`, in its **compact** register only: one line per tool call inside a single fenced code block (which `markdown_to_chat` masks and passes through untouched on Chat; email's plain-text body shows the fence as literal backticks — cosmetic, accepted), custom labels for the tools the UI special-cases (`Read file: path`, `Edit file: path`, `Run: command`, `Search web: query`, …), and a generic `Tool: name` for the rest. **Never a file's contents or a patch body** — a channel message has no expand/collapse, so either would be the whole screen — but tool *arguments* (the command line, the query, the URL) do appear, truncated, exactly as the UI's compact blocks show them; in a group space that makes a command the agent ran visible to every reader of the thread. Paths are shortened by stripping `/app/workspace/`, lines are capped at 100 chars, the block at 15 summary lines plus at most one `… and N more` overflow line (16 rendered lines), and consecutive identical lines collapse to one with `(×N)`.

The decision is made on the stored **events**, never by comparing content against the placeholder literal: `handle_stream_completed`'s uuid arm asks `tool_only_summary_for_message` for a summary, which answers only when the row's events hold at least one `tool` event and **no** assistant event with non-blank content. A turn that said anything delivers what it said, exactly as before — tool activity alongside prose stays invisible on channels, the same deliberate trade the streaming feature made when it deferred tool narration. One hook covers both arms: with no relay the uuid arm is the only delivery path, and with one, a tool-only turn gave the relay nothing, so its `("", False)` tail routes to the same arm. Rows with no stored events (pre-event rows, trimmed metadata) answer no summary and keep the legacy content delivery. The summarizer is total — any failure answers `None`, and the delivery proceeds with what it had.

#### The `channel_turn_delivery` ledger

The durable counterpart to the relay's in-memory state: **one row per external message a channel turn wrote** — the rolling draft, each slice sealed off it, and the final text the completion settles. Schema and the nullable-FK argument are in [Database Schema](#channel_turn_delivery); `channel_turn_delivery_service.py` holds every read and write. Three things it buys, and nothing else:

- **Idempotency at completion.** `STREAM_COMPLETED` fires once per LLM batch and can arrive twice for one batch (a redelivered bus event, a racing flush). A `final` row for that batch's agent message is the record that says "already answered", and `turn_already_settled` is the one place in the feature that **suppresses a delivery**. Safe on a multi-batch turn by construction — each batch writes its own agent message, so batch 2 asks about an id batch 1 never settled. It is keyed on the binding as well as the message id, not because a message id belongs to two threads but because the one suppressing gate should be keyed on everything its caller knows. A **`failed`** final row deliberately does not count: a row recording a delivery that did not reach the thread is a reason to try again, not a reason to stop. Any failure of the check itself answers `False`, for the same reason.
- **An observable divergence check** (below).
- **Crash knowledge.** Sealed messages are final — the relay advances past them and never offers that text again — so a process that dies mid-turn leaves messages standing in a thread that nothing else records. Recording the turn's *first* draft as well is what makes that record exist at all.

**Boundary writes only.** Rows are written at three moments: a **fresh draft** message (the turn's first, and the one that opens after each seal), a **seal**, and the **final** delivery. The rolling ~3-second draft patches write **nothing**, ever — they rewrite a message that already has its row, they are ephemeral by design, and persisting them would turn one row per turn into hundreds. The grain is **one row per external message, never one per flush**. A seal settles the draft row it was rewriting **in place** rather than inserting beside it: the draft and the message it sealed are the same external message, and a second row would leave the draft standing in the ledger as a message that is neither a draft nor anywhere. Every write is best-effort — a lost ledger write costs observability, never a reply.

**Adoption, and why `session_message_id` is nullable.** The relay seals mid-stream holding only `session_id` / `binding_id` / `channel_id`; the agent message id is handed over **only** by the terminal event, at the end of the batch. Every alternative required the relay to *infer* which row it was writing — "the newest agent message in this session", "the one whose metadata says it is streaming" — which is the exact inference this feature exists to delete. So a boundary write records what it honestly knows and leaves attribution `NULL`, and `settle_turn` **adopts** every pending row on the binding once the emitter has named an id, renumbering them `0..n-1` in delivery order (above whatever that message already owns, so a retry cannot collide with its own first pass). `settle_turn` is the only place `session_message_id` is ever filled in, and the id always came from the event.

**Offsets are batch-scoped, not turn-scoped.** A `sealed` row's `visible_char_end` / `content_sha256` measure the relay's delivered prefix from the start of its **LLM batch** (`_ledger_batch_base`, advanced at each `take_tail` hand-over), not from the start of the turn. The answer a prefix is checked against is that batch's own `SessionMessage`, so a turn-cumulative offset would report a divergence on every multi-batch turn. Both sides are measured in the relay's **visible space** (`_visible`, borrowed from the relay through a lazy import rather than re-modelled, so there is one model of which control tags finalize strips) and both go through `delivered_prefix_key`, whose `lstrip` cancels the one systematic offset between them — the canonical text is `.strip()`ed at finalize, the relay's buffer is not. Interior and trailing whitespace inside a *prefix* is deliberately **not** stripped: a seal cuts at a paragraph break, so its trailing newlines sit in the middle of the finished answer.

`take_tail` also **releases** the ledger's draft row at each batch hand-over and bumps the part index. Bus handlers never stop a relay, so a multi-batch turn keeps feeding the same relay; holding the id would let the next batch's seal reach back and rewrite a row the completion had already settled as `final`.

**The divergence check is purely observational.** `_check_prefix` asks whether the finalized canonical answer still starts with the `visible_char_end` characters the relay recorded having sealed into the thread. On a match it does nothing; on a mismatch it marks that sealed row `diverged` and logs a WARNING. **Delivery is identical either way** — the tail went out before the check ran, exactly as it did before this table existed. That is not caution, it is the finalize divergence policy above: the settled reply is the relay's own accumulated text, decided with the user, and "deliver the remainder instead" would have quietly reversed that decision. Two further facts a maintainer needs before touching it:

- The candidate seals are the rows **this invocation adopted**, not a re-query on the message id. Adoption is deliberately greedy — it takes every pending row on the binding so a previous turn's rows cannot leak forward — so a re-query would also return rows an earlier pass over the same message had attributed and compare this turn's answer against a prefix that is not this turn's. The `ORDER BY visible_char_end DESC` carries an explicit `IS NOT NULL` for the same class of reason: Postgres sorts `NULL`s first under `DESC`, and without it a row with no recorded offset would be picked as "the max" and silently no-op the whole check.
- **A genuine divergence is not reachable through the product today.** Both sides come from the same accumulated assistant text — the relay fed on the events finalize later joined into the row — and both are normalised through the same `_visible` and the same strip rules, so in practice the comparison is between a prefix and a superset of itself. That is precisely why the policy is "log it and see if it ever fires" rather than "handle it": the check exists to turn a silent assumption into a question the logs can answer, and a `diverged` row appearing at all is news worth chasing rather than a state the code is expected to reach.

**The close-out.** `handle_stream_error` and `handle_stream_interrupted` end a turn without a completion, so their pending rows would otherwise stay `NULL` forever and be adopted by the **next** completion on that thread — recording a previous turn's sealed message inside a turn it was never in, and then feeding the divergence check a prefix from the wrong turn. A check that cries wolf is worse than no check when the policy is "revisit only if the logs show it firing". So both handlers call `_close_out_unsettled_ledger`, which is `settle_turn` with `write_final=False` and `canonical_text=None`: attribution only, no `final` row, nothing compared.

Two properties make that legal in a handler whose documented contract is that it may not read its event's row:

- **The prohibition is on the row's *content*, not on its *id*.** What `handle_stream_interrupted` must not do is read text that is a mid-stream checkpoint — a partial of a partial, or the previous turn's text on a row not yet rewritten. The close-out loads no text and makes no claim about what was settled; the id is used as a foreign key and nothing else. It is deliberately routed **around** `_settle_turn_ledger`, whose convenience read of the canonical text would be exactly the forbidden read on this path.
- **It cannot change delivery.** It sits in a `finally` that neither raises nor returns, below all five branches of the interrupted handler — a `finally` of that shape cannot alter which branch ran or what it returned, every send above has already been awaited, and the helper is total. And because it writes no `final` row it can never satisfy `turn_already_settled`, so a close-out can never be the reason a later real completion withholds a reply. A second invocation finds nothing pending and commits nothing.

The interrupted handler still refuses to **read** the ledger, and that refusal stands: "was anything delivered this turn?" is a question the ledger cannot answer *for this turn* here, because the only key available is the binding, and rows keyed by binding alone belong to whatever ran on this thread most recently — the recency inference this whole feature deletes. Writing to it once every delivery decision has been made and acted on is a different act.

**The `notice` role was dropped, and the reason is simplicity.** The design sketch carried a fourth role for the status notice adopted by `adopt_status_notice`; three roles cover every message the ledger actually needs to describe, and a fourth bought nothing. (An earlier argument — that a `NOT NULL` FK made such rows unwritable — dissolved the moment the column became nullable, and is not the reason.) `ChannelThreadBinding.status_message_id` remains **authoritative** for "which message do I patch next", exactly as it was before this table existed; the `draft` row mirrors it, and nothing in the delivery path ever reads the ledger to make that decision, so the mirror is a record and never a second source of truth.

### Known degradations (deliberate)

Named here because each one is a trade someone will otherwise try to "fix"; the sender-facing statements are in [business logic — Known Limitations](server_channels.md#known-limitations).

- **A stranded unclosed tag opening at the head of a draft suppresses further seals for that turn.** Every candidate slice contains it, so `_has_open_tag` rejects them all and the forced cut walks back into the same opening. The draft then freezes near the cap and everything still arrives through `_deliver`, which chunks. No data loss; live narration stalls. Fixing it means deciding a tag is not a tag.
- **A partial tail hides a *trailing* unfinished tag, and a tag mentioned once in prose with nothing after it is truncated with it.** `_unfinished_tag_start` uses `rfind` per tag (a still-arriving tag is necessarily its own kind's last occurrence) and then the **earliest** of those candidates (the outermost open tag, so a `<cinna_attach>` literal inside a still-arriving `<webapp_action>` body cannot win over the tag containing it). That narrows the divergence; it does not close it, and only the interrupt/error endings are affected — the identical reply through `handle_stream_completed` keeps the text.
- **`_flush` holds a pooled connection across each adapter round trip** (up to `_MAX_SEALS_PER_FLUSH + 1` of them), once per interval per concurrent streaming turn, and the adapter's 429 backoff can stretch one. The relay's lock is held across those awaits too, so `take_tail` can wait out one flush's retries before answering — accepted rather than fixed, since dropping the lock around the awaits is exactly what would let a tail be taken between a seal's send and the offset advance.
- **Multi-worker `/stop`.** `active_streaming_manager` is a process-local dict, so a `/stop` landing on a worker other than the one running the stream reports "nothing running" while the turn continues. Rides the existing single-process assumption this feature already documents for its schedulers; it does not add a new one.
- **`STREAM_INTERRUPTED` fires once per interrupted batch**, so a turn whose second batch is also interrupted acknowledges twice. Suppressing it would mean per-turn state in a handler whose whole virtue is having none.
- **Tool-activity narration in the draft is deferred by decision**, not missing by oversight.
- **A command batch that precedes an LLM batch in the same pending set clears the notice mid-turn.** `collect_pending_batches` partitions a turn's pending messages into contiguous same-routing batches, and `handle_stream_completed` fires per **batch**; a `command_stream` batch honestly reports `agent_message_id=None`, so the handler settles — and, with nothing to put in the slot, deletes the notice. The LLM batch behind it then posts a fresh one. Cost: a flicker and one extra message; no text is lost. **Do not "fix" it by gating the clear on a relay being attached** — that would strand the spinner on the common single-batch "turn produced nothing" path, reintroducing the exact bug the previous feature shipped to fix. The handler is per-batch and has no way to know a turn is over.
- **A process crash mid-turn strands pending ledger rows, and the next turn adopts them.** Adoption is greedy by design (every pending row on the binding), and the close-out only runs in a handler that actually fires — a killed process runs none. The next completion on that thread therefore stamps the dead turn's rows with its own message id and the divergence check compares its answer against the wrong prefix, producing a spurious `diverged`. Operationally: **before treating a `diverged` WARNING as a real mismatch, rule out a crash on that binding.**
- **`take_tail` runs before the idempotency gate**, so a duplicate `STREAM_COMPLETED` *consumes* batch N+1's accumulated tail before `turn_already_settled` returns — the gate suppresses the **send**, not the consumption. Narrow: it needs a redelivery landing mid-turn on a multi-batch turn. Not fixed because `take_tail` must be called before the DB session is opened (it waits on the relay's flush lock, and that flush needs a pooled connection of its own — see the tail contract above), so closing it means new peek-without-advance relay semantics in the most delivery-order-sensitive code in the feature. The trade taken is a rare lost increment over a redesign of the part that must not be got wrong.

## Extension Seam

Adding a new **webhook** channel type is: write a module implementing `ChannelAdapter` (`validate_config`, `verify_inbound`, `send_message`, `get_setup_instructions`, plus the `capabilities` property) and add one entry to `CHANNEL_ADAPTERS` in `adapters/registry.py`. A **polled** transport (a second one after email) subclasses `PolledChannelTransport` instead, implements `poll(channel)` in place of `verify_inbound`, and declares `inbound_mode="polled"` in `capabilities` — both the subclass and the declaration are required and must agree, or `_assert_declared_modes_agree()` refuses to let the app boot. No migration and no pipeline change either way — `channel_type` is a plain indexed string column, validated against the registry only at create/update time in the service layer, not in the model, and `ChannelPollService` picks up a new polled type automatically via `channel_types_with_inbound_mode("polled")`. The admin UI follows the registry: a newly registered adapter shows up as a card in the type picker immediately and is configurable through a raw JSON config editor without a frontend change. Adding an entry to `frontend/src/components/Admin/ServerChannels/channelTypes.ts` upgrades that to a typed form (labelled, validated config fields + type-specific credential copy) — recommended, but not a prerequisite for registering the adapter.
