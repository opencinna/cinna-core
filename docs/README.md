# Cinna Core

A conversational AI agent platform where users create custom AI agents, run them in isolated Docker environments, and interact through persistent chat sessions. Agent developers publish versioned bundles to a catalog; other users install them. Agents can be scheduled, triggered by email/webhooks, and exposed via A2A and MCP protocols.

**Stack:** FastAPI + PostgreSQL | React + TypeScript + TanStack | Docker isolation | SQLModel ORM

## Core Idea

The platform separates three distinct layers:

- **Agent** (logical definition) — what the agent does: custom prompts, credentials, SDK configuration
- **Environment** (runtime instance) — where it runs: a Docker container with the agent's workspace, tools, and files
- **Session** (conversation) — how users interact: a persistent chat thread with independent message history

One agent can have multiple environments (for testing, production, or rollback via blue-green deployment). One environment can host multiple sessions that share the same file workspace but maintain separate conversation histories.

Agents operate in two modes:
- **Building mode** — development state; agent uses a larger context window, can create/modify scripts and configure integrations
- **Conversation mode** — execution state; agent runs pre-built workflows with a lightweight prompt for faster, cheaper responses

Sessions can be started manually, by automated triggers (CRON, email, webhook), or by other agents via handover. External systems can connect through A2A (Agent-to-Agent protocol) or MCP (Model Context Protocol).

## Glossary

| Term | Definition |
|------|-----------|
| **Agent** | User-defined AI assistant with custom prompts, credentials, and SDK configuration |
| **Agent Environment** | Runtime instance (Docker container or remote server) where an agent executes |
| **Session** | Persistent chat conversation between a user and an agent environment |
| **Message** | Single communication unit within a session (user or agent) |
| **Activity** | Logged event or summary of agent actions within a session |
| **Credential** | Encrypted API key or service account used by agents (e.g., Gmail, Odoo) |
| **AI Credential** | LLM provider API key (Claude, OpenAI, etc.) for agent runtime |
| **Knowledge Source** | Git-based repository of documentation agents can query via RAG |
| **Agent Plugin** | Marketplace capability that extends agent functionality |
| **Input Task** | User-submitted task that goes through refinement before agent execution; extended with short-code IDs, comments, attachments, status history, and subtask delegation |
| **Task Trigger** | Automated rule (CRON, webhook, date) that creates tasks for an agent |
| **Agent Bundle** | Publisher-owned, versioned packaging of an agent identified by a reverse-DNS bundle ID. Publishing an agent creates a bundle; each publish creates an immutable revision |
| **Bundle Revision** | Immutable snapshot of a bundle's workspace content (scripts, docs, knowledge, files, prompts, SDK settings, agent schedules, agent-row metadata: description, example prompts, status refresh command, agent API / A2A / webapp enablement flags, SDK config, and the full A2A capability contract) taken at publish time |
| **Install** | A user's running copy of a published bundle — an `Agent` row seeded from a bundle revision with its own persistent App Data volume |
| **App Data** | Per-user, per-bundle persistent storage volume (`/app/workspace/app-data`) that survives uninstall and reattaches on reinstall |
| **Guest Share** | Token-based, time-limited, revocable link that gives unauthenticated (or authenticated) viewers chat-only access to a specific agent install; protected by a 4-digit security code, scoped to conversation mode, and optionally exposes a read-only environment panel |
| **Handover** | Agent-to-agent task delegation within the platform |
| **Improvement Request** | An `AgentImprovementRequest` row: a consent-gated, one-directional, one-time share of a frozen session snapshot (transcript + tuning-relevant runtime context, including the prompts and MEMORY files that formed the system prompt) from the session owner to the agent's owner — the bundle publisher for a consumer install, or the requester themselves otherwise. Raised via a session's "Improve Agent" menu item or `/session-improve`; reviewed from a Configuration-tab card or `cinna improve` CLI verbs; downloadable as a self-describing ZIP archive. Frozen at consent — nothing reads the source session again — and has no withdrawal in v1. |
| **Workspace** | Isolation boundary for user's agents, sessions, and resources |
| **AI Function** | LLM utility for text generation, classification, extraction with multi-provider cascade fallback |
| **Disclaimer** | An admin-configurable, server-wide Markdown notice shown at login in a non-dismissible modal. Superusers enable/disable it and choose when it appears (`new_users` — once per browser, `every_login` — once per session). Acknowledgement is tracked in versioned browser storage; editing the text or mode increments the version and re-shows the notice to all users. |
| **Email Confirmation** | A per-account marker (`email_confirmed`) that gates all non-recovery outbound email. New users start unconfirmed and click a link in a confirmation email; Google-OAuth users and superusers are auto-confirmed. Unconfirmed accounts are limited to 5 standalone agents; confirmed accounts are limited to 50; superusers are unlimited. |
| **Admin-managed AI credential** | An `AICredential` row provisioned by a superuser on behalf of a target user (`is_admin_managed=True`). Owned by the user and fully participates in existing per-user plumbing; read-only through the user-facing CRUD (owner may use and set as default, but cannot edit/delete/re-key). |
| **Account config** | The native-client credential bundle returned by `GET /external/account-config` — a list of provider descriptors with decrypted API keys, consumed by Cinna Desktop/Mobile to auto-create local LLM providers on login. |
| **`current_user` record** | A synthetic, reserved entry appended to every agent environment's `credentials.json` (`id="current_user"`, `type="current_user"`). Built host-side from the install owner's `User` row — carries `username`, `full_name`, `email`, `email_confirmed`, a `custom_details` map of user-authored `UPPER_SNAKE` key/value pairs, and four locale/communication preference fields: `timezone` (IANA zone, nullable), `language` (nullable), `locale` (BCP-47 formatting locale, nullable), and `conversation_style` (`ai_default` / `concise_direct` / `friendly_chatty`, always present). Not a real `Credential` row; never redacted; unredacted in `credentials/README.md`. Scripts access it via the standard dict-comprehension: `creds["current_user"]`. |
| **User's Details** | The free-text `KEY = value` content a user types in **Settings → My profile → User's Details**. Parsed/normalized into the `custom_details` block inside the `current_user` credentials.json record. Stored as `details_raw` (verbatim, for editor re-open) and `details_parsed` (`{UPPER_SNAKE: "value"}` map) on the `User` row. Editing triggers a fan-out re-sync to all running environments of all agents the user owns via `event_user_details_updated`. The same fan-out is triggered when the user updates any locale or communication preference (`timezone`, `language`, `locale`, `conversation_style`) from the profile settings, since those fields also ride the `current_user` block. |
| **Environment Critical State** | A persisted flag (`critical_state=true`) on an `AgentEnvironment` that coexists with `status="running"`: the Docker container is up, but a post-start provisioning step (package install, credential sync) failed. Sessions, chat, terminals, and logs remain available; CRON-scheduled runs and manual "Run now" are blocked until the owner resolves the issue and rebuilds. Distinct from `status="error"` (container not running). |
| **Agent Env Action Log** | Append-only table (`agent_env_action_log`) recording every significant environment operation — rebuild, setup, package install, credential sync, cron-skip — with full, untruncated error detail. The data source for the env-card "Show details" modal. Rows are written by the lifecycle and the scheduler; never updated; deleted only via CASCADE. |
| **Building Mode** | Agent environment state for configuration and development |
| **Conversation Mode** | Agent environment state for executing tasks and chat |
| **Agent User** | Default role for new signups — can install, chat, and manage settings; cannot create agents or publish bundles |
| **Agent Developer** | Admin-promoted role — unlocks agent creation, building mode, publishing, and all developer UI |
| **A2A** | Agent-to-Agent protocol for cross-platform agent communication |
| **MCP** | Model Context Protocol - exposes agents as tool servers to external LLM clients |
| **App MCP Server** | Universal MCP endpoint that routes messages to agents by AI classification. As of Phase 5 of the channels & identity unification, a singleton `ServerChannel` (`channel_type="app_mcp"`, the platform's `authenticated` transport) — admin kill switch, `visibility` + grants, per-user agent scope, all resolved by `ChannelPolicyService` like every other channel. Routes over exactly what a caller owns (`ChannelCandidateProvider`) plus their enabled identities (`IdentityCandidateProvider`, opt-in, off by default); no route, assignment, or per-agent toggle exists any more |
| **Router Trigger Prompt** | Short natural-language sentence on an agent (and snapshotted into bundle revisions), one of the two fields (with `example_prompts`) every routing consumer — App MCP, Server Channels, identity Stage 2 — classifies against. Bundle install and apply-update **do** propagate it — `InstallService` copies `revision.router_trigger_prompt` onto the installed agent row in both paths. What Phase 5 of the channels & identity unification removed is propagation into a *route*: there is no `AppAgentRoute` left to auto-populate, so the copied prompt is now itself what makes the install routable. Editable by the owner via the focused `PATCH /agents/{id}/router-trigger-prompt` (no developer gate) or the generic agent update |
| **Identity Routing** | Person-level routing candidate available to **every** surface, not just App MCP — users expose themselves as a named identity that other users can address by name, resolved by two-stage routing (Stage 1 picks the person, Stage 2 picks one of their agents; `match_method` is `only_one` or `ai`). `IdentityCandidateProvider` supplies the candidates and each surface composes them into its own ballot: App MCP Stage 1, and (since Phase 3 of the channels & identity unification) Server Channels Pass 1, gated there on the sender's own `allow_identity_routing` opt-in. The session opens in the identity owner's workspace either way. |
| **Identity Agent Binding** | Configuration linking one of a user's agents to their identity, with a trigger prompt and per-caller access control |
| **Identity Binding Assignment** | Per-caller access record granting a specific user access to a specific identity agent binding. Its two booleans point in **opposite directions** and are routinely confused: `is_active` is the identity *owner's* control over who may reach them, while `is_enabled` is the *caller's* own per-person opt-out of reaching that owner (the row is keyed by `target_user_id`, and `toggle_identity_contact` filters on it). One person-level `is_enabled` toggle governs every surface — App MCP and Server Channels alike — deliberately not duplicated per channel |
| **MCP Connector** | Configuration that connects an agent environment to an external MCP server |
| **Agent Webapp** | Lightweight data dashboard (HTML/CSS/JS) served from an agent's workspace via shareable URLs |
| **Webapp Share** | Token-based public access to an agent's webapp for unauthenticated viewers |
| **Agent REST API** | A capability-narrowed HTTP API that a producer agent builds from plain Python functions decorated with the `cinna_api` SDK and exposes through the platform proxy. The powerful upstream credential stays in the producer container; consumers get only the surface the producer chose to expose. A deterministic, no-LLM-at-call-time code-to-code channel (contrast with A2A and MCP). |
| **`agent_api` credential** | A `CredentialType.AGENT_API` credential storing `{ base_url, token, spec_url, label, producer_agent_id }` — it **is** the connection between a consumer agent and a producer's REST API. Created by the "Connect Agent API" helper, it rides the existing credential sync / whitelist / redaction pipeline; `token` is redacted in agent prompts. Deleting it disconnects (cascade-deletes the token). Cross-user sharing is safe because the shared value is the narrowed proxy, not the upstream secret. |
| **`agent_api_token`** | Opaque scoped token (SHA256 hash at rest, 8-char display prefix) that authenticates consumer calls to a producer agent's REST API. Internal machine credential — never created or revoked by hand: it is minted by the connect helper and bound to its `agent_api` credential via `credential_id` (`ON DELETE CASCADE`), so deleting the credential is the only way to revoke. Never expires. `read_only_override` may only narrow the producer's `policy.yaml`, never widen it. |
| **`owner_identity_token` (agent_api caller identity)** | A synthetic, host-computed `credentials.json` entry (`id="owner_identity"`, `type="owner_identity_token"`) injected into a consumer env that has ≥1 `agent_api` connection — a sibling of the `current_user` record. It carries a narrow, audience-restricted (`aud="agent_api_caller"`) JWT the agent sends on Agent REST API calls; the proxy verifies it, resolves the *install owner*, **strips** it, and injects trusted `X-Cinna-Caller-*` headers so the producer learns who is calling. Anonymous-by-default (absent/expired ⇒ no headers, never an error); never reaches the producer. Not a real `Credential`; never redacted; re-minted on every credential sync. |
| **Agent REST API access grant** | An `agent_api_access_grant` row, one per `(producer_agent, user)`, by which a producer's owner assigns **capability scopes** to individual platform users from the **Access & Scopes** card (gated by the `agent_api_identity_enabled` opt-in flag). The proxy resolves the grant **live** on every call and injects `X-Cinna-Caller-Scopes` (space-separated); editing scopes takes effect on the next call. The producer is the primary enforcer (`caller.scopes` in the `cinna_api` SDK); the platform optionally hard-denies scope-gated endpoints declared in `policy.yaml` at the edge. |
| **Agent REST API — connection vs. key** | The two products behind one `agent_api` proxy, discriminated by `AgentApiToken.kind`. A **connection** (`kind="connection"`) wires one platform agent to another: anonymous by default, machine-only token, never shown, synced into the consumer's `credentials.json`. A **key** (`kind="external"`, see below) hands a human-operated caller outside the platform the same access. Both ride the identical proxy, `policy.yaml`, and live scope-grant machinery, so a producer's authorization code (`caller.user_id`, `caller.has_scope(...)`) is the same for either caller — one authorization path, not two. |
| **`agent_api` external key** | A hand-issued `agent_api_token` (`kind="external"`) that lets a caller outside the platform — a laptop script, server, or cron job — call a producer agent's REST API as if it were a peer agent. Bound at mint time to a `subject_user_id` (immutable — reassigning identity is revoke + re-issue, never an edit) and optionally an expiry; minting is gated by the producer's `agent_api_external_access_enabled` opt-in, which also acts as a live kill switch on every call. Revealable (once, then again on demand) only via `POST /credentials/{id}/agent-api-key/reveal`, which audits every reveal (`AGENT_API_EXTERNAL_KEY_REVEALED`); the generic `with-data` credential-detail endpoint strips the token for a key instead of showing it. Never synced into `credentials.json`, never shareable (`allow_sharing` forced off), and categorized under **My Credentials** rather than Automatic. Scopes live on the same `agent_api_access_grant` row a connection's caller would use — the key answers *who*, the grant answers *what*. |
| **Agent-to-Agent MCP Connector** | A connector flagged `is_agent_to_agent=true` on `mcp_connector` that a producer agent owner creates to expose their agent as a peer MCP server for other *agents* (rather than external LLM clients). Managed from the Integrations → MCP Connectors card's dedicated sub-tab. Reuses the full MCP connector infrastructure (token verifier, server registry, direct tokens) unchanged; the flag drives producer sub-tab grouping and the consumer picker discoverability. Requires `agent-developer` role to create. |
| **`mcp_provider` credential** | A `CredentialType.MCP_PROVIDER` credential that **is** the connection between a consumer agent's SDK and a remote MCP server — either another platform agent's agent-to-agent connector (`auth_mode="agent2agent"`) or an arbitrary external MCP server (`fixed_token` / `oauth_dcr` / `none`). Created by the "Connect MCP Provider" helper; rides the credential sync / whitelist / redaction / sharing pipeline. Unlike every other credential type, it is **never written to `credentials.json`**: the token is injected into the SDK runtime config (OpenCode `"mcp"` block / Claude Code `options.mcp_servers`) via a per-mode MCP manifest (`user_mcp.json`). Deleting it disconnects and cascade-deletes the bound direct token (agent2agent only). |
| **Account CLI Token** | A `CLIToken` row with `token_type="cli-account"` and `agent_id=NULL`. Created by exchanging an account setup token. Scoped only to the `/account/*` route group — cannot authenticate per-agent sync, exec, workspace, or building-context routes. Carries a 7-day rolling expiry. Stored in `.cinna/account.json` on the developer's machine. |
| **Child Token (CLI)** | A standard `token_type="cli"` `CLIToken` minted programmatically by `POST /account/agents/{id}/mint`. Carries `minted_by_account_token_id` as provenance. Authenticates the unchanged per-agent sync/exec endpoints; revoked individually or by cascade when its parent account token is revoked. |
| **System Notification** | A platform-generated alert about a backend event (e.g. a session error), dispatched to the event owner via email. Distinct from agent-authored messages and the in-app activity feed. Governed by the Notification Catalog and per-user preferences. |
| **Notification Catalog** | The code-only registry (in `notification_catalog.py`) of every system notification type the platform supports. Each entry defines user-facing copy, the default opt-in state, the email template filename, the subject builder, and the dedup key. Adding a new type requires only a new enum value, a catalog entry, and a built email template — no schema migration. |
| **App Sync** | Zero-knowledge server-side sync substrate for native clients (Cinna Desktop, future Cinna Mobile). Stores E2E-encrypted documents partitioned by `collection`; the server never holds a key that can decrypt them. |
| **App Sync Record** | One row in `app_sync_record` representing a single synced entity (a note, a job, a folder, etc.). Keyed by `(user_id, collection, client_entity_id)`; carries an opaque ciphertext payload and a per-user monotonic `seq` for delta pulls. |
| **User Master Key (UMK)** | A per-account 256-bit random key that is the root of the App Sync key hierarchy. Generated once on the first device; never transmitted or stored in plaintext anywhere — the server holds only wrapped (encrypted) copies in `app_sync_key_envelope`. |
| **Key Envelope** | A row in `app_sync_key_envelope` containing the UMK sealed/wrapped under one unlock method (`device`, `recovery`, or `passphrase`). The server stores and returns the `wrapped_key` verbatim and cannot open it. |
| **Skin** | A registered visual overlay (`SkinDefinition` in `frontend/src/config/themes.ts`) selected independently of light/dark mode, applied via `data-skin="…"` on `<html>`. Pure CSS-variable overlay across three tiers — shadcn semantic tokens, Tailwind palette scales, decorative `--skin-*` tokens — with no component-level opt-in. Client-side only (`localStorage`), no backend model. |
| **Device Pairing** | Mechanism for sharing the UMK with a new device via a hardened commit-then-reveal handshake. The joining device generates an ephemeral keypair and a commitment (`blake2b(pubkey ‖ nonce_J)`) and calls `POST /pairing/start`. A trusted unlocked device discovers the request from `GET /pairing/inbox`, posts its `sealer_nonce` via `POST /pairing/inbox/{id}/sealer-nonce`, and seals the UMK via `POST /pairing/inbox/{id}/complete` after the joiner reveals its nonce and the commitment is verified client-side. A 6-digit SAS (`trunc6(blake2b(pubkey ‖ nonce_J ‖ nonce_S))`) is compared out-of-band. The server is a dumb relay: it stores and forwards opaque strings and never verifies the commitment or decrypts the UMK. |
| **Server Channel** | Admin-configured, server-wide inbound transport instance (`ServerChannel`, e.g. Google Chat, Email) that lets people outside the platform message agents. A `webhook` transport (Google Chat) is reached through an unguessable webhook URL; a `polled` transport (Email, since Phase 4 of the channels & identity unification) has no URL at all and is instead pulled by a scheduler — see `ChannelCapabilities.inbound_mode`. Owns its own transport trust model (non-secret `config` + Fernet-encrypted, write-only `encrypted_secrets`, or — for a transport whose credential lives elsewhere, like email's referenced SMTP server — `needs_outbound_credentials=False`), a fail-closed comma-separated email whitelist, and an `auto_register_users` toggle. Superuser-only CRUD via the Channels tab on `/admin/server-configuration`. |
| **Channel Thread Binding** | A `ChannelThreadBinding` row pinning one external channel thread (`thread_key`) to one platform `(user, agent, session)` triple — the conversation state of Server Channels. Created before the session exists (during auto-install) so parked messages have somewhere to land; `pending_install` → `active`, and `failed` self-heals by deletion + re-routing on the next inbound message. A thread belongs to exactly one person — a different sender posting into a bound thread, or the loser of a binding-creation race, is declined rather than routed. |
| **Channel Visibility & Grant** | Two of `ServerChannel`'s four admin-owned availability defaults. `visibility` is `"public"` (every platform user may use the channel) or `"restricted"` (only users with a `server_channel_user_grant` row); a public channel needs no grant rows and never gets any — their absence there means the question was never asked, not that nobody is allowed. Being granted is access, not enablement; both are resolved together by `ChannelPolicyService`. |
| **Channel User Setting** | A `channel_user_setting` row: one person's optional, per-channel override of `ServerChannel`'s admin defaults (`is_enabled`, `agent_scope`, `pinned_agent_id`, `allow_identity_routing`). Absence of the row means "the channel default applies" — it is created lazily, on the user's first edit in Settings → Channels, never at channel-create or account-create time (auto-registered senders and later-created users would otherwise never get one). Resolved against the channel's defaults by `ChannelPolicyService`, the sole place the inherit rules live; `allow_identity_routing` is the one field that never inherits (`NOT NULL DEFAULT false`, no channel-level default): it is the **sender's own** consent that a message of theirs may be routed into somebody else's workspace, where they can read it — never the receiver's gate. It governs **channel and App MCP** identity routing only: External A2A identity access is authorized by its own mechanism (`ExternalAccessPolicy.require_identity_access` plus the owner's binding assignments) and is **not** closed by this switch. Read on every message since Phase 3 of the channels & identity unification (gating the identity half of the Pass-1 ballot, and re-checked before ingesting on an already-bound identity thread), surfaced in Settings → Channels, and audited on transition via `SERVER_CHANNEL_IDENTITY_ROUTING_CHANGED` (severity `medium`). |
| **Channel Agent Scope** | The `agent_scope` resolved per user per channel — `"all"` (every owned agent is a routing candidate, the default), `"list"` (only the agents on the user's `channel_user_agent` list), or `"none"` (no agent routes until the user opts one in). An out-of-scope owned agent is recorded in the routing trace as a skip (`SKIP_NOT_IN_CHANNEL_SCOPE`) rather than silently absent, and routing Pass 2 (catalog auto-install) does not run unless the resolved scope is `"all"` — a decided product semantic, not `allow_auto_install` re-read. |
| **Pinned Channel Agent** | A user's `channel_user_setting.pinned_agent_id` — "always route my messages on this channel to this one agent of mine." Skips classification entirely, records its own routing-trace `match_method="pinned"`, outranks both the `only_one` short-circuit and Pass 2 auto-install (a pinned channel never auto-installs, even when the pin fails to resolve — the sender's instruction stands whether or not the platform can honour it), and has its ownership re-checked at resolution time since the foreign key only guarantees the agent still exists, never that this user still owns it. |
| **Server Auto-Install List** | The server-wide `ServerAutoInstallBundle` list of catalog bundles eligible for Pass-2 channel routing — classified by router trigger prompt only when none of a sender's own installed agents match. List membership is never an implicit permission grant; `CatalogService.user_can_install` still gates every candidate per user. |
| **Routing Decision / Routing Trace** | A `RoutingDecision` row — the durable, superuser-only record of one LLM-mediated routing choice: every candidate considered including rejected ones with a `skip_reason`, the rendered classifier prompt, raw model response, provider/model attempts, verdict, latency, and (message-text-gated) the sender's own words. Every row also carries the **`origin`** that produced it — `server_channel` / `email` / `app_mcp` / `simulate`, with `identity` reserved and unemitted because identity routing is a *stage* inside another origin's decision — and a **`channel_id`**, which since Phase 6 of the channels & identity unification is populated on every live surface (App MCP is a singleton `ServerChannel`, so it has one too). Captured in memory by `RoutingTrace` at the router chokepoint, persisted once the decision settles. See [Auto Routing Tuning](application/routing_tuning/routing_tuning.md). |
| **Reachability Verdict** | A backend-computed, plain-language sentence (one of **16** codes, each with a matching test) explaining why a routing decision went the way it did and what to change. Split by origin for *wording only*, never for the underlying finding: as of Phase 5 of the channels & identity unification, a channel decision and an App MCP decision are diagnosed by the identical logic — ownership and wording (e.g. an owned agent unreachable because it has neither a router trigger prompt nor example prompts) — differing only in the wording each origin gets. Phase 6 of the channels & identity unification replaced the two-way channel-or-App-MCP split with an origin→profile map of **five** remedy profiles (`routing_reachability_service.py`) — `channel`, `email` (the channel profile under its own name), `app_mcp`, an origin-neutral `generic` default, and a reserved `identity` — so an origin the map does not know degrades to origin-neutral wording rather than silently inheriting App MCP's. The six App-MCP-only route-based codes this entry used to describe (e.g. a standalone agent unreachable because it has no `AppAgentRoute`) are deleted outright, not merged, since the route mechanism they diagnosed no longer exists. The headline output of [Auto Routing Tuning](application/routing_tuning/routing_tuning.md). |
