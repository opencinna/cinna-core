# UI/UX Guidelines — the house pattern library

This is the single source of truth for **how a surface is structured**: which user story it serves, where it lives (card / dialog / sheet / page), how dense it may be, which controls are visible, and which house pattern it reuses. It is read by:

- `cinna-core-ui-designer` — produces the **UI Specification** for a plan (`cinna-core.ui.design`) and reviews built surfaces against it (`cinna-core.ui.review`).
- `cinna-core-ui-developer` — implements frontend phases from the specification.
- `cinna-core-developer` / `cinna-core-code-reviewer` — whenever they touch or review a frontend file.

Implementation conventions (React Query, routing, toasts, the generated client) live in [frontend_development_llm.md](frontend_development_llm.md). This document is about **composition**, not wiring.

The rules carry numbers on purpose. A rule with a number can be checked without taste; a rule without one gets argued. Thresholds are policy until the [lessons log](#10-lessons-log) changes them.

---

## 1. The four user stories

Every surface is classified **before** it is designed. A surface that serves two stories at once is two surfaces.

| Story | The user's intent | What the surface looks like |
|---|---|---|
| **Create** | "Set it up fast, with as few actions as possible." | ≤ 3 fields → one dialog. More → a wizard of ≤ 4 steps with a stepper. If the form's shape depends on a *type*, choosing the type **is step 1** (tile/pill picker, [pattern 4](#p4-type-picker--detail-route)) — never a `<Select>` at the top of a long form. Required fields only; everything with a sensible default is pre-filled; advanced options collapsed behind one "Advanced" disclosure. |
| **View** | "What do I have here?" A glance, not a control panel. | Compact rows or summary cards. **Passive** state (badge, star, "Default", "Managed", expiry) is visible. **Mutating** controls (delete, set-default, edit) are not: they live in an overflow menu or appear on hover. Delete is never a default-visible control. |
| **Edit** | "Show me the whole configuration, structured." | The full form, grouped into titled sections, in a Dialog (one section, ≤ 8 fields), a Sheet (2–3 sections) or a dedicated route (more, or with sub-lists). Explicit Save / Cancel with dirty tracking. Never inline in a list row. |
| **Manage list** | "Find, sort, filter, act on many." | Dedicated route with `DataTable` (search, pagination, per-row overflow menu). A card elsewhere shows only a **preview** of this list ([pattern 5](#p5-preview-list--show-all)). |

Create and Edit share one form component when the fields are the same and the create story needs no type step. When they differ, do not force the create story through the edit form.

## 2. Placement decision table

| Situation | Rule |
|---|---|
| **A card** | One concern, named by the title. **≤ 7 logical blocks** (a block = one field group, one button row, one summary row, or **one list as a whole** — rows are counted by the list-cap rule, not here). If the spec has more, split the card or promote the concern to a tab / route. |
| **Card header** | Every card: `CardTitle className="flex items-center gap-2 min-w-0"` holding **one lucide icon `h-5 w-5`** and a noun title, then `CardDescription` (one sentence) full-width below. The icon is part of the skeleton, not decoration: the spec names it per card (§7 item 8) and a card without one fails R15. Header actions (the P3 primary button) sit on the title row, never beside the description. Siblings in one grid share this treatment — a header that differs from its neighbours' is a finding even when the card is fine alone. |
| **Card width** | Half-width in the tab's `grid grid-cols-1 lg:grid-cols-2 gap-6 items-start` grid. **Nothing in a card grid spans two columns.** A table that genuinely needs its columns also needs search or pagination, which makes it a Manage-list route ([P9](#p9-manage-list-route)), not a card; a name column plus a few checkbox or toggle columns is a list of rows (each row's toggles are one control — see "Toggles on rows") and fits half width. "This card reads badly at half width" means the card is too big, not that the grid is wrong. |
| **Card height** | Bounded and predictable. Nothing inside a card may grow the card without a user action that says so (a "Show all" link, a tab switch). Expand-in-place is allowed only for read-only detail (a log line, a description). A state toggle (Enable, Default) must not change the card's height — if enabling reveals a form, that form is a dialog. |
| **List inside a card** | Show the **5** most relevant items (recent, enabled, favourites first) and a "Show all (N)" link to a dedicated route or a full-height Sheet. Never render an unbounded list in a card. This applies to entity lists; a selection checklist inside a wizard step or dialog is not a list in a card — it gets `max-h-[40vh] overflow-y-auto` when its length is data-driven. |
| **Row anatomy** | Every entity row in the product is `Common/ListRow.tsx` inside a `ListRowGroup`, and reads the same way left to right: **status dot → identity tile → name (+ ≤ 1 badge) / metadata line → flags → inline action → On/Off → `⋯`**. The order is not the author's choice — `ListRow` renders `flags` before `children`, so a passive indicator can never end up right of the menu. **No border on a row.** A card is already a bordered box; a border per row draws five more boxes inside it and the eye counts boxes before it reads names. Rows are separated by the group's single `divide-y` hairline and a hover strip, nothing else — which also buys the name the ~24 px the 1024 yardstick is always short of. |
| **Row state** | On/off, active/revoked, current/superseded is the **leading dot** (`status`), never a `Badge`. "Active" printed on every live row is the most repeated and least informative word in a list, and the negative case is already carried by `muted`. The wording lives in the dot's tooltip and its `sr-only` label, so the state is still readable and still announced. Tones: `on` / `off` / `warning` / `error`, painted from `--success`, `--muted-foreground`, `--warning`, `--destructive`. A row with no on/off or health state has no dot. |
| **Row height** | A row is **one line by default**. The metadata line is optional and expensive: it adds a line of height to *every* row in the list, so it earns its place only when it is the fact that tells two rows apart (a schedule's cadence, a person's email, a channel's transport). Everything else that is true of the row but that nobody scans the list by — a token's prefix and last-use time, a share link's session count, a handover's prompt, when a thing was created — goes into the **detail flag**, `RowInfo`: an `Info` glyph, always last in the flags cluster, whose tooltip lists those facts one per line. It is the house answer to "this is useful but not worth a line", and it reads as one affordance across the product. A short word that *is* scanned for (a channel's type, a share link's code, a team's task prefix) is a `Badge` on the title line, which costs no height — give it `h-5` so a badged row is exactly as tall as an unbadged one, since the default badge is 2 px taller than the `text-sm` title beside it. |
| **Badge budget** | A row's title line carries **one** `Badge` by default, and **at most two**. The second is earned only by a fact in one of two families, never both: an **identity** fact (version) and an **origin** fact (who made it — `author`, or the word that stands in for it when a source has no author, e.g. `Local`). Anything else true of the row is a `RowFlag` or a Details fact. The arithmetic matters because "at most one" was written as an absolute and then overridden, in a comment, by every list that hit it — a rule every instance argues with is not a rule, it is a note. Two tests before adding a badge: *does another source's row spend this slot on something else?* (if yes, it is the same slot, not a new one) and *would a user scan a list for this word?* (if no, it is a flag). Both were how the addons row settled on `version` + `Local`, with `Published` demoted to a flag — the same fact, one budget. |
| **Absent facts** | A fact that is missing renders **nothing**. No "No version", no "Not set", no "None" chip on a row. The failure is the one "Row state" already names for `Active`: an absence is true of *most* rows in a young list, so the chip becomes the most repeated and least informative word in it, on precisely the rows with the least other information — and it costs the name 60–90 px to say so. Absence is legitimate in exactly two places: a **fact list** in a detail dialog or a settings card, where "Not configured" is the answer to a question the reader asked ("No version in SKILL.md"), and a **form**, where a placeholder says what will happen if the field is left alone. If the user needs prompting to supply the missing thing, the prompt belongs on the control that supplies it, not on every row that lacks it. |
| **Choice-control ARIA** | A control that picks **one of n** announces as a radio: `role="radiogroup"` on the container, `role="radio"` + `aria-checked` on each option. A control that toggles **each of n** independently announces as a toggle: `aria-pressed`. Getting this wrong tells a screen-reader user that a choice is a switch they can turn off. It applies to **hand-rolled** controls as much as to Radix ones — the same rule lives in `Common/TooltipToggleItem` for `ToggleGroup`, but it was filed there as a Radix story, so the next author building a cloud of `<button>`s did not find it. Radix additionally swaps which attribute it emits per group `type`, which is why a component styling off ARIA needs both selectors; a component styling off a class needs only the correct attribute. |
| **Fact labels** | In a fact list, the **label is a noun** ("Catalog installs", "My agents", "Repository") and the **value carries its unit** ("3 people", "3 agents", "16 MB"). Not a predicate ("Used in my agents"), which reads as a sentence fragment beside its noun siblings, and not a bare number whose unit lives only in the label — because the same number then appears elsewhere in the product with a different unit attached and the two stop being recognisably one fact. A pair of numbers that need a sentence to reconcile them usually needs units instead. |
| **Row flags** | A passive per-row fact the user reads but cannot click — a mode, a scope, a kind, "no allowed senders" — is a `RowFlag`: one `h-3.5 w-3.5` glyph with a required tooltip and `sr-only` label. Not a `Badge`: badges cost the name 60–90 px each, and a list carries the same two or three of them on every row. Flags are **muted by default**; colour (`warning` / `error`) is reserved for the flag that means something is wrong, so a coloured glyph still means something when it appears. The `Badge` that survives on a row is the one carrying a word the glyph cannot ("CLI link"), and there is at most one. |
| **Row actions** | **1 primary** action inline (the reason the user comes to the row: Run, Copy, Test, expand a read-only detail). **≤ 2** inline in total, counting the On/Off control. Everything else — and **always** Edit, Delete, Disable, Set-default — in the `⋯` `RowActionsMenu` ([pattern 3](#p3-compact-row--overflow-menu)). Destructive items last in the menu, `variant="destructive"`, confirmed with `AlertDialog` (never `window.confirm`). A row whose **only** action is its purpose (Disconnect on a session, Revoke on a key) may show that one action inline instead of a menu of one item; when it is destructive, hover-reveal it — `ListRow` always carries `group`, so the control just needs `opacity-0 group-hover:opacity-100 focus-visible:opacity-100`. A confirm that a menu item opens is owned by the **row**, and a list-level confirm is driven by a `deleteTarget` the item sets: a `DropdownMenuItem` unmounts on select and would take a nested trigger's pending state with it. |
| **Toggles on rows** | Enabled/disabled is the **status dot** plus an Enable / Disable item in the `⋯` menu. Nothing else, on most lists. When toggling is the row's *primary purpose* (a channel list, an identity contact list), it is promoted to an inline `OnOffToggle` — the `Power` / `PowerOff` ghost icon button, the same glyph pair the menus use, so the action reads identically whether it sits on the row or in the menu. **Never a `Switch` on a row:** a switch is a wide grey pill whose meaning is carried entirely by which end the knob sits at, so a list of them is a list of identical shapes; it duplicates the dot, and during a pending write it can contradict it. (`Switch` remains right for a card-level auto-saving boolean — one control, with a label beside it.) The glyph names the **action**, not the state: the state is the dot's job. A control on a row acts on that row's entity only; a control that acts on a different entity (a person inside a channel row) belongs on that entity's own surface. A **segmented multi-toggle** (shadcn `ToggleGroup type="multiple"`, `components/ui/toggle-group.tsx`; reference row: `Admin/AccessPolicy/CompanyAiCredentialRow.tsx`; ≤ 4 short segments — roles, modes) is **one** control for the budget when the whole set is one field of the row's entity: it may be the row's inline action in place of the power button, auto-saving one write per click, with the same `⋯` menu beside it. Five or more segments is a dialog. **Yardstick at 1024:** a half-width card column is ~340 px (1024 − 256 sidebar − 64 page padding − 24 gap, halved), ~292 px inside the card, and — borderless — ~276 px of row; the whole segment group must stay ≤ ~130 px so the name keeps ≥ 120 px, which means 3–5-character segment labels ("User · Dev · Admin") with the full label on `aria-label` and a `Tooltip`, and the short labels living beside the long ones in the shared label module, not in the component. |
| **Inline forms** | At most **one** inline form open at a time per card, and only for a single-field quick edit (rename, one textarea). Anything with ≥ 2 fields → dialog. N rows must never render N forms. |
| **Disclosure depth** | **2 levels**: card/list → dialog/sheet/route. A dialog never opens another dialog (an `AlertDialog` confirm is the one exception). A success screen *links* onward (to the created entity's row or page) instead of nesting the next step. A **value picker** inside a form dialog (choose an agent, a user, a model) is a `Popover`/command list anchored to its field, not a second `Dialog`; an existing picker dialog is tolerated only if it returns one value and closes itself. Shared controls meant to live inside dialogs (`ListModelsButton`, `UserAllowlistPicker`) must therefore never open a `Dialog` of their own. **Chained** is not nested: a dialog that closes and then opens an informational dialog ("these environments are affected") is allowed. |
| **Interaction model** | One per card: **either** auto-saving controls (Switch / Select that persist on change, with a toast) **or** edit-through-a-form (a Save / Cancel form, or P2 summary rows that open a dialog). Never both in the same card — an auto-saving `Select` beside two summary→dialog rows is a violation even when each piece is fine alone. (An auto-save card *may* hold one P2 summary row whose dialog edits a value too long for an inline control, such as a pattern list — the rule is about the card body's controls, not about where a long value is typed.) |
| **Complex configuration** | Its own tab (`HashTabs`, as on the agent page) or its own route. Not a taller card. |
| **Page toolbar** | *Where you are* and *how much of it you are looking at* are two questions and must not share a control vocabulary. Section navigation inside a page is a **segmented control**: one bordered track (`inline-flex … rounded-lg border bg-muted/50 p-1`) holding the sections, the current one filled with `bg-primary text-primary-foreground` — never a raised `bg-background` tile (darker than its own track on the dark skin, so the selected segment reads as a hole) and never `bg-accent` (the hover colour, so on and hovered-off look alike). The subset **filter** is **one** control: a `Filters` button opening a `DropdownMenuRadioGroup`, with the active subset written on the trigger (`Filters · Installed`) so a short grid always says why it is short. Both sit on one `justify-between` row. Reference: `Catalog/{CatalogSectionTabs,CatalogFilterMenu}.tsx`. A row of filter pills under a row of navigation pills is eight identical controls with nothing but their labels to tell navigation from filtering — which is what the catalog shipped, and what a user reads as "these buttons all look the same". |
| **Choosing one entity in a form** | A field that picks one entity out of many (an agent, a user, a model) is a **trigger + `Popover`**, never an inline list of every candidate and never a second `Dialog` (§2 "Disclosure depth"). The trigger is `Select`-shaped and carries the chosen entity in the vocabulary it has everywhere else in the product — its `AgentBadge`, not its name — or a placeholder. The popover holds the search box and the candidate list, returns one value and closes. **No "Change" button beside the value:** the trigger is how it is changed, and a second verb next to a value that is itself a control is one control too many. The `X` beside the trigger is the only way to *empty* the field, and exists only where the field is optional. Reference: `Common/AgentSelectorDialog.tsx` (`AgentSelectorList mode="single"`), after `ListModelsButton` and `UserAllowlistPicker`. |
| **A card under a document** | A column that holds a card whose height is *user content* — a rendered `SKILL.md`, a log, a description someone wrote — has room for exactly one card, and it is that one. A list card placed under it starts below the fold on every real record and stays there; it is not "further down the page", it is gone. Move it to the fixed-height column, and prefer hanging it off the fact that names it (the revisions Sheet opens from the Version fact) over spending a card on it — a door costs no height. |
| **Empty state** | Every list has one: **≤ 1 sentence** + a button or link to the primary Create action (the card header's Add button satisfies this when the card has one; a sentence that names another page must link to it). Not just "No items." |
| **Sections inside one card** | Allowed when they are facets of **one** concern (2FA: passkeys / authenticator / recovery codes). Separated with `Separator`, each with a small heading. Three sections about three different concerns is three cards. |
| **Icons** | Every icon-only button has a `Tooltip`. Icon size `h-3.5 w-3.5` inside `h-7 w-7` ghost buttons on rows; `h-4 w-4` elsewhere. |
| **Confirmation** | Destructive and irreversible actions confirm with `AlertDialog` naming the entity ("Delete schedule *Nightly sync*?"). A plain `Dialog` is acceptable only when the confirmation must show fetched impact data (what else breaks if this credential goes) — it still names the entity and ends in one destructive button. Reversible actions (disable, unfavourite) do not confirm; they toast with the result. |
| **Row as the control** | When a row's primary purpose is to *open its detail* (an installed addon, a skill inside a plugin) and it carries no inline action, the **whole row** is the Details control — click, Enter and Space open it — rather than a `BookOpen` button in the action cluster. `ListRow` renders `div`s, so the wrapper is a `div role="button" tabIndex={0}` with a written `biome-ignore` (a real `<button>` cannot contain them; the catalog cards make the same trade). Three things the wrapper must do: **no `rounded-*`** — the group's `divide-y` hairline is a border *on the wrapper*, so a radius rounds the separator and the list stops matching every other list; guard the click with `currentTarget.contains(target)` (portaled menus and dialogs bubble React events up this tree, so a click inside the uninstall confirm would otherwise open Details under it) **and** `target.closest("button")` (the `⋯` trigger is the row's, not Details'); and ignore clicks **while a write is pending** — a disabled trigger no longer receives the click, so it falls through to the row. Focus ring `focus-visible:ring-inset`. |
| **Pending on rows** | A write in flight is *shown*, not just disabled: a `Loader2 animate-spin` takes the `⋯` menu's slot, `h-7 w-7`, with a `Tooltip` **naming the wait** ("Updating…", "Uninstalling…", "Saving…") and an `sr-only` copy of it. A greyed-out trigger reads as broken for the several seconds a container sync takes, and the user clicks it again (see "Row as the control" for where that click lands). Which label: the mutation that is running, not a generic "Working…". |
| **Links in a fact list** | A URL or a route in a detail dialog's fact list (repository, homepage, "Open in the catalog") is a **plain text link** — `hover:underline`, `truncate`, `target="_blank"` with `rel="noopener noreferrer"` for external — and **no external-link glyph**. The glyph adds a second icon to a line that already has a label and a value, and the truncated URL already says where it goes. Reserve `ExternalLink` for a bare button whose label does not say it leaves the page. |
| **Copying a visible value** | A value that is *already on screen* (a commit hash, an id, a token prefix) and exists to be pasted is its own copy control: the value rendered as a `<button type="button">` in `font-mono`, a `Tooltip` reading **"Click to copy"**, a success toast ("Commit hash copied") and the clipboard failure toast. Never add a second boxed input for it. `Common/CopyableValue` (label + boxed value + copy button) is for values that are **not** otherwise shown and that the user reads *as* a field — a webhook URL, the `/start` link, a path — not for a fact line. |
| **Timestamps** | Every server timestamp is rendered through `Common/RelativeTime` (relative label, full local date on hover), and every relative *string* (a `RowInfo` fact, a card's "Checked 3 minutes ago") through its `formatRelativeTimestamp`. **Never `formatDistanceToNow(new Date(x))`** on a wire value: the backend serialises naive UTC with no zone suffix, and `new Date("…T10:00:00")` reads that as *local* time, so the label is off by the viewer's UTC offset — a bug that is invisible in UTC and obvious everywhere else. `parseTimestamp` is the one parser (A11). |
| **Dialog body** | A dialog whose body is data-driven (a fact list, a skill list, a document pane) gets `DialogContent className="max-h-[85vh] overflow-y-auto overflow-x-hidden … [&>*]:min-w-0"`. Two reasons, both learned: the content grows with the data and must scroll inside the viewport, and `DialogContent` is a **CSS grid**, whose children default to `min-width: auto` — one long unbreakable word or one `truncate` row widens the dialog sideways until the children are told to shrink. Long prose gets `break-words`; a wide table or code block scrolls inside its own pane (`overflow-x-auto`), never the dialog. **Initial focus:** Radix focuses the first focusable element on open; if that is a control with a `Tooltip` (a click-to-copy value), the tooltip opens over nothing the pointer is near. Then `onOpenAutoFocus={(e) => { e.preventDefault(); e.currentTarget.focus() }}` — the body takes focus, Tab still reaches every control in order. |
| **Read-only drill-down** | A read-only dialog that lists *n* items each with a document of its own (a plugin shipping a dozen skills, each with a `SKILL.md`) does **not** swap the document into its own body: with *n* rows plus a pane it overflows the viewport and the pane's scroll fights the dialog's. Each row opens its **own** read-only dialog, subtitled with where the reader came from ("Part of the plugin X"). This is the named R8 exception for **read-only detail of a read-only list**; it is not a licence for a form to open a form. A row that *is* one item shows its document inline. |
| **Wire strings** | A display fallback on a wire string uses `\|\|`, not `??`: an absent version, author or description arrives as `""` as often as `null` (a manifest with no `version` syncs as an empty string), and `??` happily prints "v" with nothing after it. On the server, empty-string-means-absent is normalised to `None` at the projection (`plugin.version or None`) so other clients do not repeat the trap. |
| **The same entity, before and after** | A thing that appears in two lists — a catalog entry in the Add dialog and the same entry once installed — reads the **same** in both: same badges (version, author), same glyphs (kind, modes), same Details dialog shape. When one side lacks a fact the other has (the installed row has an author, the search result does not), the fix is to carry the fact on both payloads, not to badge one list and not the other. And a list of things to add **excludes what is already added**: a muted "already installed" row is a second row for the same thing. |
| **Wizard step header** | Step 2 of a wizard is titled by the thing chosen in step 1 — its name (linked to where it lives, in a new tab so the wizard stays put), its version badge, its description as the `DialogDescription` — not by a generic verb phrase ("Enable it for") with the choice echoed in a bordered box below. The body asks the step's question; the header says what it is being asked about. |
| **Scrolling lists and the far edge** | Inside a capped scrolling container (`max-h-… overflow-y-auto`), the rightmost flag or control of every row sits **under the scrollbar**. Give the container `pr-2`, and put a control the user must *click* (Details) after the badges on the title line rather than in the action cluster. A tooltip-only glyph (`RowInfo`) in that position is unusable. |
| **Rendered documents** | A markdown document a user reads (a `SKILL.md`, a README) is **rendered**, through `Chat/MarkdownRenderer` (no `rehype-raw` — raw HTML stays inert) in `prose prose-sm dark:prose-invert max-w-none`, with YAML frontmatter split off (`utils/skills.splitSkillFrontmatter`) because its keys are already the dialog's title and description. A `<pre>` of prose is a wall. A raw-copy affordance is only added when a user asks for it (it was removed on request here). |

## 3. House patterns

Each pattern names a reference implementation in this codebase. Reuse the reference's structure and class names; do not reinvent the skeleton.

**Shared card skeleton (every card pattern, P1–P3, P5, P7):** `Card` → `CardHeader className="pb-3"` → `CardTitle className="flex items-center gap-2 min-w-0"` with one lucide icon `h-5 w-5` + noun title (+ the P3 primary `Button size="sm"` on the same row, pushed right) → `CardDescription` one sentence, full-width → `CardContent`. Reference for the header: `frontend/src/components/Agents/AgentSchedulesCard.tsx`. A pattern below describes only what it adds to this.

### P1. Concern card → modal
**Use for:** a configuration concern whose editor is large (prompts, descriptions, long text).
**Reference:** `frontend/src/components/Agents/AgentConfigTab.tsx` — Information and Agent Prompts cards.
**Skeleton:** `Card` → `CardHeader` (icon + title, one-line description) → `CardContent` with a `flex gap-2 flex-wrap` row of `Button variant="outline"` items, each opening one modal. The modals are rendered once at the bottom of the tab component, controlled by boolean state. The card itself shows **no** form fields. The buttons name the thing they open ("Description", "Workflow Prompt") — the one place where a noun label is right.
**States:** none needed beyond the modal's own loading/saving.

### P2. Summary row → edit dialog
**Use for:** a small set (1–4) of named settings, each with a few fields. The inline `Pencil` is the "only action" case of §2 Row actions: the moment a row also gets Delete / Disable / Set-default it becomes a P3 row with a `⋯` menu.
**Reference:** `frontend/src/components/UserSettings/AICredentials.tsx` — "Default SDK Preferences" rows + `SDKModeEditDialog`.
**Skeleton:** per setting, `div.flex.items-start.justify-between.gap-3.rounded-md.border.px-3.py-2.5` with an icon tile, a label (`text-xs text-muted-foreground`), the current value (`text-sm font-medium`) and secondary lines; a single `Button variant="ghost" size="icon" className="h-7 w-7"` with `Pencil` opening the dialog. The dialog holds the whole form for that setting.
**States:** skeleton rows while loading; the value line says "Not configured" when empty.

### P3. Compact row + overflow menu
**Use for:** any list of entities with more than one action (schedules, handovers, credentials, connectors, revisions, channels, tokens, shares, sessions).
**Reference:** `frontend/src/components/Common/ListRow.tsx` (the row), `Common/RowActionsMenu.tsx` (the `⋯`), `Common/OnOffToggle.tsx` (the inline power button); as a whole row, `frontend/src/components/Agents/ScheduleRow.tsx` and `Agents/BundleRevisionRow.tsx`.
**Skeleton:** header = the shared card skeleton (icon + title) with the one primary `Button size="sm"` on the title row, `CardDescription` full-width below them (a description squeezed beside a button wraps to 5 lines at 1024). Body = a `ListRowGroup` of `ListRow`s. **Do not hand-write the row.** Its props are the anatomy:

```tsx
<ListRowGroup>
  {items.map((item) => (
    <ListRow
      key={item.id}
      muted={!item.enabled}
      status={{ tone: item.enabled ? "on" : "off", label: "Enabled" }}
      icon={<span className="flex h-6 w-6 …"><Bot className="h-3.5 w-3.5" /></span>}
      title={item.name}
      meta="every day · next 09:00"          // one line, ≤ 2 facts joined by " · "
      flags={
        <>
          <RowFlag icon={Terminal} label="Script trigger — …" />
          <RowInfo facts={["Prefix ab12…", "Created 3 Mar", "Never used"]} />
        </>
      }
    >
      <OnOffToggle … />                       {/* only when toggling is the row's purpose */}
      <RowActionsMenu label={`the schedule ${item.name}`}>…</RowActionsMenu>
    </ListRow>
  ))}
</ListRowGroup>
```

`title` is `text-sm font-medium truncate`; `meta` is **optional** (see §2 "Row height" — omit it and the row is one line high) and, when present, one `text-xs text-muted-foreground` line of **≤ 2 facts** joined by ` · ` (cadence · next run). Further facts go to `RowInfo` or the edit dialog. Menu order: secondary actions, `DropdownMenuSeparator`, destructive item(s). Edit opens a dialog ([P2](#p2-summary-row--edit-dialog) style form). A **kind** is a `RowFlag`, not a third badge, so the name keeps its width at 1024; when the kinds have no glyphs (AI providers — no brand marks are shipped), the kind is the first fact of the metadata line instead.
**Hover-reveal variant:** when the list is dense (≥ 10 rows) or a View row carries a visible mutating/destructive control (a menu-only row stays visible — hiding the one control costs discoverability with no density to pay for it), that control gets `opacity-0 group-hover:opacity-100 focus-visible:opacity-100`; `ListRow` already carries `group`. Passive indicators (dot, flags) stay visible; their toggle affordance moves to the menu.
**States:** loading skeleton rows (`h-[48px] w-full rounded-md`); empty state with the Create action; per-row pending disables that row's menu trigger and its inline control — scoped to the row, never to the list (`mutation.variables?.id === item.id`, since one observer describes only its latest call).

### P4. Type picker → detail route
**Use for:** creation where the form depends on a chosen type.
**Reference:** `frontend/src/components/Credentials/AddCredential.tsx` → `frontend/src/routes/_layout/credential/$credentialId.tsx`.
**Skeleton:** a dialog with a search input and grouped pill/tile buttons (`inline-flex items-center gap-1.5 rounded-full border px-3 py-1.5 text-sm font-medium`), grouped under `text-xs font-semibold uppercase tracking-wide text-muted-foreground` headings. Choosing a type creates the entity with defaults (or carries the type in state) and lands on the type-specific form: a dedicated route for large entities, step 2 of a wizard for small ones. **Allowed variant:** a type that has no meaningful empty draft (an OAuth connection, a key that must be bound at creation) routes to its own create dialog instead of the shared route — the reference does this for "Connect MCP Provider" and `agent_api`. When the landing is a `?new=1` detail route, secondary cards (sharing, danger zone) stay hidden until the first save so the Create story is not shown Edit-only concerns.
**States:** "No types match …" for the search; pending ring on the chosen tile.

### P5. Preview list + Show all
**Use for:** a card that summarises a list the user manages elsewhere (recent sessions, recent runs, last invitations).
**Reference:** `frontend/src/components/Agents/AgentHandovers.tsx` + `HandoverRow.tsx` + `AllHandoversSheet.tsx` (cap 5, Show all → Sheet, shared row component so card and Sheet cannot drift). Second instance: `UserSettings/DesktopSessionsCard.tsx` (hover-revealed single destructive action, Sheet). Both render through `Common/PreviewList.tsx` (cap, four states, Show-all link, and the `ListRowGroup` that separates the rows) — use it for every further P5 card. Third instance: `Agents/AgentBundleTab.tsx` → `BundleRevisionRow` + `AllRevisionsSheet`.
**Skeleton:** card shows the first **5** rows in [P3](#p3-compact-row--overflow-menu) style (often with **no** row actions at all), a count in the title or description ("3 of 12"), and a `Button variant="link"` "Show all (N)" that navigates to the manage-list route (or opens a full-height `Sheet`). **Route vs Sheet:** a Sheet when the full list needs no search, sort or pagination and the entity has no lifecycle of its own (handovers); a route ([P9](#p9-manage-list-route)) the moment any of those appears. The Sheet is a second disclosure level, so its rows carry the same `⋯` menu and nothing opens a further dialog except the row's own edit/confirm. The empty state and the "Show all" target may live on another route (the card previews a list managed elsewhere) — then they link there. Sorting: most recent / most relevant first.
**States:** empty state in the card; the "Show all" link hidden when N ≤ 5.
**Accepted variant:** a read-only per-row detail list (execution logs) may open in a `Dialog` with `max-h-[60vh] overflow-y-auto` and a stated cap ("last 50") instead of a route or Sheet.
**The connected-machines shape** (`UserSettings/DesktopSessionsCard.tsx` + `AppSessionRow`, and `LocalDevelopmentCard.tsx` + `CliSessionRow` built to match it) is the settled answer for a **View list whose only mutation is "cut this one off"** — connected apps, CLI sessions, sessions, devices. It is the one place a metadata line is not negotiable: the row's second line says *what disconnecting would cost* ("v0.2.11 · last used 2 days ago", "3 agents synced · 1 desktop session"), which is the fact the decision turns on. There is **no `⋯` menu** — a menu holding one item costs a click and hides the only thing the row does — and no visible destructive button either: the single `Unplug` is hover-revealed. Preview 5, "Show all (N)" to a Sheet. Reuse this shape whole rather than re-deciding it; two cards on the Security tab already read as one list because of it.

### P6. Wizard
**Use for:** Create stories with > 3 fields or with a type decision.
**Reference:** `frontend/src/components/Admin/InviteUserDialog.tsx` for the two-step flow and per-step validation. As of 2026-09-07 the reference has the stepper header and its success panel (`InviteSuccessPanel.tsx`) links onward instead of nesting a dialog; the AI-credential hand-off lands on `/admin/ai-credentials` via a search param that opens the controlled dialog there.
**Skeleton:** `Dialog` with a stepper header ("1 Who · 2 Provisioning"); either one `<form>` per step or one form with hidden step panes (the reference does the latter — it keeps typed values and per-step Enter semantics; both are conformant), Back / Next / Create in `DialogFooter`, validation per step, ≤ 4 steps. Final step may be a review summary. The success state is a panel with links ("Open user", "Copy invitation link"), never another dialog.
**States:** per-step errors inline; the whole wizard disabled while submitting.

### P7. Section-divided single card
**Use for:** one concern with 2–3 facets that share a lifecycle.
**Reference:** `frontend/src/components/UserSettings/Security/SecurityTab.tsx` (2FA: passkeys / authenticator / recovery codes).
**Skeleton:** one `Card`; sections as `<section>` blocks with an `h3.text-sm.font-medium` and a one-line description, separated by `Separator`. Each section has at most one control row. If any section needs a form, that form is a dialog.
**Not for:** three different concerns that happen to be adjacent settings (anti-pattern A1).

### P8. Tabs for domains
**Use for:** an entity with several configuration domains (agent: Configuration / Integrations / Credentials / …).
**Reference:** `frontend/src/routes/_layout/agent/$agentId.tsx`, `frontend/src/routes/_layout/settings.tsx`, `HashTabs` in `frontend/src/components/Common/HashTabs.tsx`.
**Skeleton:** `HashTabs` with each tab's content being the two-column card grid. A tab is the right home for a concern that would exceed the card budget; a new top-level route is right when the concern has its own list/detail lifecycle.

### P9. Manage-list route
**Use for:** the Manage-list story.
**Reference:** `frontend/src/routes/_layout/admin/users.tsx` + `frontend/src/components/Common/DataTable.tsx` + `frontend/src/components/Admin/columns.tsx`.
**Skeleton:** page header (title, one primary Create button, optional secondary), `DataTable` with column definitions, per-row `UserActionsMenu`-style overflow menu, server- or client-side pagination. Filters as a toolbar above the table, never as a side card.

## 5. Component vocabulary — when, not how

| Component | Use when |
|---|---|
| `Card` | One concern on a tab grid. |
| `Dialog` | Create (≤ 3 fields), Edit (one section), Wizard, type picker. `sm:max-w-md` for forms, `sm:max-w-2xl` for editors. |
| `Sheet` | Edit with 2–3 sections, or a "Show all" list for entities without a route. |
| `AlertDialog` | Confirm destructive actions. Only dialog allowed on top of a dialog. |
| `DropdownMenu` | Row overflow actions (`EllipsisVertical` trigger), header "more" actions. |
| `Tabs` / `HashTabs` | Domains of one entity; URL-addressable sections. |
| `Table` / `DataTable` | Manage-list routes. Not inside half-width cards. |
| `ListRow` / `ListRowGroup` | Every entity row in a card or Sheet. Never hand-roll the row (`Common/ListRow.tsx`). |
| `RowFlag` | A passive per-row fact as a tooltipped glyph — mode, scope, kind, "no credential". Muted by default; colour means something is wrong. |
| `RowInfo` | The row's detail flag: the `Info` glyph whose tooltip carries the facts that are true but not scanned for. Last in the flags cluster. |
| `RowActionsMenu` | The `⋯` overflow on a row (`Common/RowActionsMenu.tsx`) — it owns the button, the size, the tooltip and the row-naming `aria-label`. |
| `OnOffToggle` | A row's inline enable/disable, only when toggling is the row's purpose (`Common/OnOffToggle.tsx`). |
| `RelativeTime` | Every rendered server timestamp (`Common/RelativeTime.tsx`); `formatRelativeTimestamp` / `parseTimestamp` from the same file for a string. Never `new Date(x)` on a wire value (§2 Timestamps, A11). |
| `CopyableValue` | Label + boxed value + copy button, for a value the user reads *as a field* and that is not otherwise on screen (a webhook URL, a path). Not for a fact line — a visible hash is its own click-to-copy button (§2 Copying a visible value). |
| `MarkdownRenderer` | A document the user reads (`SKILL.md`, README) — rendered, frontmatter split off, never a `<pre>` of prose (§2 Rendered documents). |
| `Loader2` | Only as the row's named pending state in the `⋯` slot (§2 Pending on rows) or inside a `LoadingButton`. Still no spinners in card bodies — those are `Skeleton`s. |
| `Badge` | A short scanned-for word on a row's title line (a channel's type, a share link's code) or passive state elsewhere (Default, Managed). **≤ 1 per row**, and never for enabled/disabled — that is the status dot. In a `DataTable` cell a tone-dot + label line is an accepted third form of passive state next to a `Badge` column (two chips flatten two unequal facts); it is not a hand-rolled badge. |
| `Switch` | Auto-saving boolean in an auto-save **card** — one control with a label beside it. **Never on a list row**: rows use the status dot plus a menu item, or `OnOffToggle` when toggling is the row's purpose. |
| `Tooltip` | Every icon-only button. |
| `Skeleton` | Loading state of rows and summary values. |
| `Pagination` | Manage-list routes; never in a card. |
| `Separator` | Facets inside a P7 card; menu groups. |
| `Alert` | Inline warning that changes what the user can do on this surface (locked control, missing prerequisite). Not for success feedback — toasts do that. |

Primitives that do not exist yet are extracted at the **second** consumer, from two real shapes, not designed speculatively at the first: `EmptyState`. Added 2026-09-07: `Common/QueryErrorAlert.tsx` (error state with Retry; use it for R10's error branch), then `Common/ListRow.tsx` (`ListRowGroup`, `ListRow`, `RowFlag`, `RowInfo`), `Common/RowActionsMenu.tsx` and `Common/OnOffToggle.tsx` — extracted from a dozen real rows at once rather than two, which is what a unification pass is.

## 6. States and copy

- **Loading:** `Skeleton` rows shaped like the real rows. No spinners in cards.
- **Empty:** one sentence saying what will appear here + the primary action. In cards: text + button; on routes: centred block.
- **Error:** an `Alert variant="destructive"` in place of the content with a Retry; never an empty state pretending nothing exists (`isError` must be handled separately from `!data`).
- **Pending:** disable the triggering control, keep the layout stable (no layout shift on save). When the triggering control unmounts on click (a menu item), the pending state moves to the thing it opened (the confirm's buttons) or to the row — and on a row it is *visible*: a spinner in the menu's slot with a tooltip naming the wait (§2 Pending on rows), and a row that is itself a control ignores clicks meanwhile. Escape / outside-click must not close a dialog mid-request.
- **Result feedback that stays:** never. Success is a toast; only a state that still needs the user's action ("created but not their default key") stays, as an `Alert` with the action, and clears itself when the state resolves.
- **Feedback:** success and failure via `useCustomToast`; never inline success text that stays.
- **Copy:** titles are nouns ("Schedules"), descriptions are one sentence, buttons are verbs ("Add schedule") except P1 buttons, which name what they open; destructive buttons name the effect ("Delete schedule"). No "Manage" / "Settings" as button labels inside a settings page.
- **A label is not a state readout:** a control says what it does, the same way every time — "Add to agent", never "Add to another agent" once the reader has installed it once. A label that rewrites itself to reflect the reader's history makes the same button look like two, for a fact the surface already states in its own line ("Used in 3 of my agents"). Pluralisation and a name inside a confirm are not this; changing the *verb phrase* by state is.

## 7. Design checklist (used by `cinna-core.ui.design`)

For every surface the plan adds or changes, the UI Specification answers, in this order:

1. **Surface** — name, route, host (which tab / grid / dialog).
2. **Story** — Create / View / Edit / Manage-list. If two, split.
3. **Placement** — card / dialog / sheet / route / tab, with the §2 row that justifies it.
4. **Pattern** — P1–P9 reused, or "new composition" (which triggers screenshots, §9). For a list, also name the **row shape**: the plain P3 row, the segmented-multi-toggle row (`CompanyAiCredentialRow`), or the connected-machines shape (P5). Naming an existing shape is the point — a list that re-decides its own row is how the product ended up with A10.
5. **Density budget** — number of blocks (≤ 7), rows shown (≤ 5), visible actions per row (≤ 2) and the menu contents.
6. **Interaction model** — auto-save or form.
7. **States** — loading / empty / error / pending copy. For a row with writes, the pending *label* per mutation ("Updating…").
7a. **Facts and values** — for a detail dialog or fact list: which timestamps (→ `RelativeTime`), which links (plain, no glyph), which values are click-to-copy, which document is rendered; the dialog's overflow strategy (§2 Dialog body) and, when a list has *n* documents, the drill-down (§2 Read-only drill-down).
8. **Components** — from §5, plus any new primitive to add; for a card, the **header icon** (lucide name) is named here.
9. **Anti-patterns touched** — from §4, fixed or deferred with a reason.
9a. **Siblings** — for a card: the header treatment and width of the other cards in the host grid, and the statement that this card matches them (or the §2 row that lets it differ). The designer reads the host anyway; this line is what makes the comparison happen.
10. **Verification** — "checklist review" or "checklist + screenshots" per §9, with the URLs and click paths to capture.

| R20 | *(rows, facts)* ≤ 2 badges on a title line and the second is an identity **or** an origin fact, never a third of either; an absent fact renders nothing on a row; fact labels are nouns and values carry their units (§2 Badge budget, Absent facts, Fact labels). |
| R21 | *(any scrolling container, any choice control)* A capped `overflow-y-auto` container has `pr-2` so its rightmost flag is not under the scrollbar; a one-of-n control announces `radiogroup`/`radio` + `aria-checked` and a toggle announces `aria-pressed`, hand-rolled controls included; a control that unmounts on activation moves focus somewhere deliberate (§2 Scrolling lists and the far edge, Choice-control ARIA). |

| R22 | *(page toolbars, single-entity fields, labels)* Navigation and filtering do not share a control vocabulary — sections are a segmented control with a `--primary` on-state, the filter is one `Filters` menu; a field that picks one entity is a trigger + `Popover` with no "Change" beside the value; no control label changes its verb phrase with the reader's history (§2 Page toolbar, Choosing one entity in a form, §6 Copy). |

**Score 0–10 per surface** = 10 − (number of *no* among R1–R10). An *n/a* counts as satisfied: a form dialog has no rows, so R4–R6 are n/a and do not cost it points. R11–R22 are gates, not points: a *no* on any of them is reported as a finding and blocks PASS until fixed, but does not change the score.

**Verdict:** **PASS** = score ≥ 8 **and** none of **R4, R5, R7, R8** is *no* (these are the overload rules — an unbounded list, a row with visible Edit/Delete, N inline forms, a dialog in a dialog — and any one of them is ITERATE regardless of score). **FAIL** = score ≤ 5. Everything else is ITERATE. When ≥ 7 checks are n/a (a small dialog), say so and judge on the applicable ones; do not pad the score.

## 9. When screenshots are required — the complexity gate

Playwright screenshots (`node frontend/scripts/ui-shot.mjs`) cost time and see whatever data the dev database holds. They are **not** part of reviewing a simple surface, and they are never a substitute for the checklist. Use them only when the composition cannot be judged from the JSX:

Screenshots apply to surfaces **added or changed in the phase under review**. Unchanged neighbours and pre-existing dialogs are reviewed from code even if they would qualify below. At most **2 captures per surface** (one composition view, one interaction state); more is a sign the surface should be judged from code. When several cards move together (a tab switched to the grid), the thing inspected is the **host**: book the captures once against the tab, not per card.

Screenshots **required** when any of these holds for a changed surface:
- It is a **new composition** — no P1–P9 pattern covers it, or a pattern is used in a new host (e.g. first P5 instance).
- A **new route or tab** is added, or a card is moved between grids / tabs.
- It has **expand/collapse, drag, resizable panes, or a dense list (≥ 10 rows visible)**, or a stepper with > 2 steps.
- Its layout **depends on data length and the dev database actually holds enough rows to show it** (> 5). An uncapped `map` over 1 row proves nothing a screenshot can add; R4 is judged from code.
- The review found an **ITERATE** on a composition rule (R2, R3, R14) that cannot be settled from the JSX — card height against neighbours, wrapping, alignment.
- The user asked for a visual check.

Screenshots **not required** (checklist review of the JSX suffices):
- A form dialog, a summary row, a confirm dialog, a new menu item, a badge, copy changes — anything that is a straight instance of P1, P2, P3, P6, P7 with the reference's skeleton.
- Backend-driven changes where the frontend only rebinds fields.

Rules when screenshots *are* taken:
- The docker frontend on `:5173` is nginx serving the **image's** build, not the working tree; a capture there shows yesterday's code and proves nothing. `ui-shot.mjs` therefore never uses it: it reuses a Vite dev server on `:5199` or starts one for the run.
- Capture only the surfaces named in the spec's Verification line, at 1440 and 1024 (390 only for surfaces that claim mobile support). Dialogs and sheets are captured with `--element "[role=dialog]"`; pages with the default full-page mode (the tool expands the app's inner scroll region); themes with `--theme light|dark`.
- If a state cannot be reached with the tool (a wizard step that needs typed input, a list the dev database cannot populate), report **"required but not capturable"** and review that state from the JSX. Do not fake it.
- Do not create or modify data to make a screenshot look better; if the dev database lacks data for the state under review, say so and review the empty state instead.
- Findings from screenshots are about **composition** (height, alignment, overflow, density). Content seen in a screenshot (names, emails, keys) is test data and is never quoted in a report.
